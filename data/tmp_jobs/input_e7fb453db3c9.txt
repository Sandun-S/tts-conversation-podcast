</Person1><Person2> "What is infrastructure as code?"
</Person2><Person1> "Infrastructure as code lets you describe, through code, the infrastructure you need for your application. You maintain both your application code and everything needed to deploy it in a central repository. Advantages: consistent configurations, improved scalability, faster deployments, and better traceability. Memory: consistent, scalable, fast, traceable."
</Person1><Person2> "What is an ARM template?"
</Person2><Person1> "JavaScript Object Notation, JSON, files that define the infrastructure and configuration for your deployment. The template uses a declarative syntax. Declarative syntax builds the structure and elements that outline what resources look like, without describing the control flow. It is different from imperative syntax, which uses commands for the computer to perform. Imperative scripting focuses on specifying each step in deploying the resources."
</Person1><Person2> "Make that concrete."
</Person2><Person1> "Declarative says: I want a storage account with these properties. Imperative says: first create a resource group, then run this command, then check if it exists, then create it. With a template you declare what you intend to deploy, not the sequence of commands to create it. You specify the resources and their properties, and Azure Resource Manager deploys them in an organised and consistent manner. An analogy: declarative is ordering a dish in a restaurant, imperative is writing the recipe step by step for the chef."
</Person1><Person2> "Benefits of ARM templates."
</Person2><Person1> "Automation and infrastructure as code: the template becomes part of your infrastructure and development projects, stored in a source repository and versioned like application code. Idempotent: you can deploy the same template many times and get the same resource types in the same state. Orchestration: Resource Manager creates resources in the correct order, and in parallel when possible, so template deployments finish faster than scripted deployments. The notes illustrate that there is only one call to process a template, as opposed to several calls for scripts. Built in validation: Resource Manager checks the template before starting the deployment to make sure it will succeed. Modularity: break complex templates into smaller reusable components, link them together at deployment time, or nest templates inside others. Deployment history: in the portal you review the history and state of deployments, with values for all parameters and outputs. CI and CD integration: with tools like Azure Pipelines, to automate release pipelines. With Azure DevOps and ARM template tasks you continuously build and deploy."
</Person1><Person2> "Memory trick for the benefits."
</Person2><Person1> "Versioned, idempotent, ordered and parallel, validated, modular, tracked, pipeline ready. Or just remember the big three: declarative, idempotent, validated."
</Person1><Person2> "Idempotent explained once more."
</Person2><Person1> "Deploy it ten times, get the same result as deploying it once. If nothing changed, nothing changes. If you change a parameter, only that change is deployed. Resources are created only if they do not exist, and updated only if there is a change. That makes templates safe to re run."
</Person1><Person2> "The file structure."
</Person2><Person1> "The notes list eight elements. One: schema, required. Defines the location of the JSON schema file that describes the structure of JSON data. The version you use depends on the scope of the deployment and your JSON editor. Two: contentVersion, required. Defines the version of your template, such as one dot zero dot zero dot zero. You use it to document significant changes and make sure you deploy the right template. Three: apiProfile, optional. A collection of API versions for resource types, so you do not have to specify an API version for each resource. Four: parameters, optional. Values provided during deployment, through a parameter file, command line parameters, or the portal. Five: variables, optional. Values used to simplify template language expressions. Six: functions, optional. User defined functions available within the template, to simplify repeated complicated expressions. Seven: resources, required. The actual items you want to deploy or update in a resource group or a subscription. Eight: outputs, optional. Values returned at the end of the deployment."
</Person1><Person2> "Required versus optional."

</Person1><Person2> "What is the problem with the template we built?"
</Person2><Person1> "The storage account name is hardcoded. You can only use the template to deploy that same storage account every time. To deploy one with a different name you would have to create a new template, which is not practical for automation. The SKU is hardcoded too, so you cannot vary the type of storage account per environment. Recall the scenario: each partner deployment may need a different type of storage account. The fix: parameters."
</Person1><Person2> "What are parameters?"
</Person2><Person1> "ARM template parameters let you customise the deployment by providing values tailored to a particular environment. You pass different values depending on whether you are deploying to development, test, production or others. For example the template used the Standard underscore LRS SKU; make the SKU a parameter and pass in the SKU for this deployment. You can supply values at the command line or by using a parameter file. In the parameters section you specify which values can be input at deployment. You are limited to two hundred fifty six parameters in a template. Parameter definitions can use most template functions."
</Person1><Person2> "The properties of a parameter."
</Person2><Person1> "Name, then: type; defaultValue; allowedValues, an array; minValue and maxValue for integers; minLength and maxLength for strings or arrays; and metadata with a description. Memory trick: type, default, allowed, min and max values, min and max lengths, metadata."
</Person1><Person2> "Allowed types."
</Person2><Person1> "Seven: string, secureString, int, boolean, object, secureObject and array. The notes write integers; the type name in JSON is int. Memory: string, secure string, int, bool, object, secure object, array."
</Person1><Person2> "Recommendations."
</Person2><Person1> "Use parameters for settings that vary by environment, such as SKU, size or capacity. Use them also for resource names that you want to specify yourself for easy identification or naming conventions. Provide a description for each parameter. Use default values whenever possible. Security rule: never hardcode or give default values for usernames and passwords in templates. Always use parameters for usernames and passwords or secrets. Use secureString for all passwords and secrets. If you pass sensitive data in a JSON object, use secureObject. Template parameters with secureString or secureObject cannot be read or harvested after deployment of the resource."
</Person1><Person2> "Using a parameter."
</Person2><Person1> "In the parameters section, define it. In the resource use the expression open bracket parameters open paren single quote storageAccountType single quote close paren close bracket. The syntax: square brackets, the parameters function, the parameter name in quotes. When you deploy you provide a value. Memory trick: name, condition, type, value, copy."

Resources are created only if they do not exist and updated only if there is a change."
