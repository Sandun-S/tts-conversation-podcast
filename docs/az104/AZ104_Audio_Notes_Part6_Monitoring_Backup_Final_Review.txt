CHAPTER ONE. AZURE MONITOR BASICS
------------------------------------------------------------

Azure Monitor is the umbrella service for collecting, analyzing and acting on telemetry. It handles two main kinds of data.

Metrics are numbers sampled over time, like CPU percentage or available memory. They're lightweight, near real time, and stored for 93 days.

Logs are rich records, like event logs, activity logs and diagnostic logs. They're stored in a Log Analytics workspace, and you query them using Kusto Query Language, KQL.

The Activity log is a subscription level log that records management operations, like who created or deleted a resource. It answers the question, who did what, and when, at the control plane.

Diagnostic settings are how you send a resource's platform logs and metrics to a destination: a Log Analytics workspace, a storage account for archive, or an event hub for streaming.

For virtual machines, the Azure Monitor Agent, AMA, collects data from inside the guest operating system, like event logs, performance counters and syslog. Host level metrics, like CPU, are available without an agent. Guest level data, like memory inside the OS, needs the agent.

Memory hook. Metrics are numbers over time. Logs are records queried with KQL. Inside the guest needs the agent.

CHAPTER TWO. DATA COLLECTION RULES AND XPATH
------------------------------------------------------------

Question 58. You must collect only the Windows system events with Event ID 4648, from two specific servers. Which query language goes inside the Data Collection Rule? XPath. You answered correctly.

A Data Collection Rule, DCR, defines three things: what data to collect, how to transform it, and where to send it. You attach the rule to machines through an association.

The logic is about timing. XPath filters at collection time, inside the DCR, deciding what gets ingested. KQL runs later, after the data is in Log Analytics, to analyze it. WQL belongs to WMI and T-SQL belongs to databases, so neither applies.

Memory hook. Filter on the way in equals XPath. Analyze after it's stored equals KQL.

CHAPTER THREE. ALERTS, ACTION GROUPS AND THE ITSM CONNECTOR
------------------------------------------------------------

An alert has three parts. The alert rule, which defines the condition and scope. The action group, which defines what happens when it fires. And the alert itself, the fired instance.

Alert types. Metric alerts watch numbers, like CPU over 80 percent. Log alerts run a KQL query on a schedule. Activity log alerts fire on management events, like a VM being deleted. Smart detection and service health alerts also exist.

Action groups are reusable lists of notifications and actions. Notifications include email, SMS, push and voice. Actions include Automation runbooks, Azure Functions, Logic Apps, webhooks, and ITSM connections.

Question 81. You have on premises System Center Service Manager and you want an alert when a VM's available memory drops under ten percent. What do you do first? Deploy the IT Service Management Connector, ITSM. You answered correctly.

The reasoning: Azure alerts can create work items, like incidents, inside ITSM tools such as Service Manager, but only if the connector is deployed and connected first. An automation runbook, a function app, or a plain notification doesn't give the integration.

Memory hook. Alerts into an ITSM tool like Service Manager equals ITSM Connector first, then action group.

CHAPTER FOUR. AZURE BACKUP AND THE TWO VAULT TYPES
------------------------------------------------------------

Azure Backup uses two kinds of vault, and the exam tests which workload goes where.

The Recovery Services vault is the older, broader vault. It backs up: Azure virtual machines, Azure Files shares, SQL Server and SAP HANA running inside VMs, on premises machines through the MARS agent, and on premises workloads through Azure Backup Server or System Center DPM. It also hosts Azure Site Recovery for disaster recovery.

The Backup vault is the newer vault. It backs up: Azure Disks, Azure Blobs, Azure Database for PostgreSQL, and Azure Kubernetes Service. Think of it as the vault for newer data sources.

Questions 36 and 37. You have a Backup vault and a Recovery Services vault. Which resources can the Backup vault protect? Disk01, the managed disk. Which can the Recovery Services vault protect? VM01, the virtual machine.

Why the web app and the SQL database don't belong. An App Service web app has its own built in backup feature. An Azure SQL Database has automated backups with point in time restore. Neither uses these vaults.

Memory hook. Recovery Services vault equals VMs, Files, SQL in VMs, and on premises. Backup vault equals Disks, Blobs, PostgreSQL, AKS. VM goes with Recovery Services. Disk and Blob go with Backup vault.

CHAPTER FIVE. BACKUP BONUS TOPICS
------------------------------------------------------------

Backup frequency recap from Part 3. Blob vaulted backup is daily or weekly. Azure Files backup can be hourly, up to 24 snapshots a day. VM backup is typically once a day.

Backup policy. Defines schedule and retention. Retention can be daily, weekly, monthly and yearly points.

Soft delete. Backups are kept for 14 days after deletion by default, so you can recover from accidental or malicious deletion. Enhanced soft delete and immutability can add further protection.

Vault redundancy. You pick LRS, ZRS or GRS for the vault's backup storage before you protect anything. GRS with cross region restore lets you restore in the paired region.

Restore options for a VM. Create a new VM, restore disks, replace existing disks, or restore individual files. Individual file recovery works by mounting the recovery point as a drive.

Azure Site Recovery. Replicates VMs to another region for disaster recovery, so you can failover. It's different from backup. Backup protects against data loss and corruption. Site Recovery protects against whole site outage. Backup is about restore points. Site Recovery is about continuity.

CHAPTER EIGHT. EXAM DAY STRATEGY AND FINAL RAPID FIRE
------------------------------------------------------------

Strategy. First, read the last line of the question first, so you know what's actually being asked. Second, underline keywords: least privilege, minimal administration, immediately, first step, only. Third, for scope questions, draw the hierarchy quickly in your head: management group, subscription, resource group, resource. Fourth, for true or false sets, treat each statement alone, because the same scenario can flip between statements. Fifth, for case studies, quickly scan the requirements and the technical details before answering, since exact facts decide the answer. Sixth, eliminate wrong answers by the word "only" and by features that belong to a different service. Seventh, don't spend more than two minutes on a question. Flag it and move on. Eighth, in questions with "does this solution meet the goal", remember that the same scenario repeats with different solutions, and usually only one works.
