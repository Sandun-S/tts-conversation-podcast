</Person1><Person2> "How does a service actually use zones? I remember three words."

</Person1><Person2> "Give me a memory trick."

</Person1><Person2> "Why is the availability zone idea so tested?"
</Person2><Person1> "Because of the difference between availability set, availability zone and region pair. </Person1><Person2> "Now region pairs."
</Person2><Person1> "Each Azure region is paired with another region within the same geography, which is a country or area boundary like the United States, Europe or Asia Pacific. For example East US is paired with West US, North Europe with West Europe, and Southeast Asia with East Asia."
</Person1><Person2> "What does the pairing give me?"
</Person2><Person1> "Several benefits, all about disaster recovery. Pairs stay inside the same geography, with an exception we will mention, so data stays within the same legal and tax boundaries. Four: some services use the pair automatically. </Person1><Person2> "You said exception. Brazil."

The notes call this out specifically, so remember Brazil South is the one directional pair."
</Person1><Person2> "And some regions have no pair at all."
</Person2><Person1> "Right. Some newer regions do not have a paired region; they rely on availability zones for resilience inside the region. So do not assume every region has a pair. If a question says a region with no pair, then zone redundancy is the tool."
</Person1><Person2> "Why is there a minimum of three hundred miles?"
</Person2><Person1> "Close enough for acceptable latency for replication, far enough to be a different disaster zone. That is the design logic. And remember the order of facts: pairs are in the same geography, at least three hundred miles apart, with the Brazil exception."
</Person1><Person2> "Now sovereign regions."

</Person1><Person1> "Episode two. The Azure management hierarchy: resources, resource groups, subscriptions and management groups. This is the backbone of governance, because Azure Policy, role assignments and budgets all attach to this tree and flow downward."
</Person1><Person2> "Draw the tree for me, bottom to top."
</Person2><Person1> "Bottom, a resource. A resource is a manageable item you create in Azure: a virtual machine, a storage account, a virtual network, a web app, a database. Above that, a resource group, a logical container holding related resources. Above that, a subscription, the billing and access boundary. Above that, management groups, which hold subscriptions. At the very top, the tenant root group. Four levels of management scope: management group, subscription, resource group, resource."
</Person1><Person2> "Start with resource groups. What are the rules?"
</Person2><Person1> "Rules worth memorizing. One: every resource must be in exactly one resource group. You cannot create a loose resource. Two: a resource can only be in one resource group at a time, though you can move it to another group later. Three: resource groups cannot be nested. You cannot put a resource group inside a resource group. It is flat. Four: you cannot rename a resource group after creation. If you need a different name you create a new one and move the resources. Five: deleting a resource group deletes every resource inside it. That is a cascade delete, and that is also why people use resource groups for lifecycle: create a dev environment in one group, throw the group away when finished. Six: the resource group has its own location, which only stores metadata about the resources. Resources inside can be in different regions from the group, though many organizations keep them aligned. If the region of the group has an outage, you cannot manage the metadata, but the resources keep running elsewhere."
</Person1><Person2> "What do people group by?"
</Person2><Person1> "Typically by lifecycle and ownership: all resources that are deployed, updated and deleted together, for one application, or one environment, or one team. A useful rule from the notes: resources with the same lifecycle belong together. Also, actions on a group apply to everything inside it: apply a policy, a lock or a role assignment on the group and every resource in it inherits it."
</Person1><Person2> "Does grouping affect networking? I always wonder if two resources in different groups can talk."
</Person2><Person1> "Resource groups do not isolate networking. A virtual machine in group A can use a virtual network in group B, if you have permission. The group is for management, not for network boundaries."
</Person1><Person2> "Now subscriptions."
</Person2><Person1> "A subscription is a unit of management, billing and scale. Three jobs. First, a billing boundary: each subscription gets its own invoice, so you can see costs per department or project. Second, an access control boundary: you can assign roles at subscription scope, and permissions flow down to all groups and resources inside it. Third, a scale boundary: each subscription has limits and quotas, like the number of virtual machine cores in a region, so organizations split workloads across subscriptions to avoid hitting them. A subscription is linked to a Microsoft Entra tenant; it trusts that tenant to authenticate users. One subscription trusts exactly one tenant. But one tenant can have many subscriptions."
</Person1><Person2> "How many subscriptions would an organization have?"
</Person2><Person1> "Many. </Person1><Person2> "Now management groups. Why do we need them above subscriptions?"
</Person2><Person1> "Imagine five hundred subscriptions. Assigning a policy to each one is painful. A management group is a container for subscriptions. </Person1><Person2> "What are the limits?"
</Person2><Person1> "Facts from the notes, memorize them. A hierarchy of management groups can be nested up to six levels deep, not including the tenant root group and not including the subscription level. </Person1><Person2> "What is the tenant root group?"
</Person2><Person1> "Every directory gets one top management group automatically, called the Tenant Root Group, and its identifier is the tenant ID. </Person1><Person2> "Give me an example hierarchy."
</Person2><Person1> "A company called Contoso. Under the Tenant Root Group, a management group called Contoso. </Person1><Person2> "How does inheritance behave for roles and policy together?"
</Person2><Person1> "The same direction: parent to child, top to bottom. Role assignment at management group gives access to everything below. </Person1><Person2> "Where does a tag fit?"
</Person2><Person1> "Tags are name and value pairs on resources, groups or subscriptions, for metadata like cost center. Tags are not inherited by default. You can use a policy with the modify effect to copy a tag from the resource group to its resources. That's covered in Azure Policy episodes."
</Person1><Person2> "Which scope is the best place for each control? Make it practical."
</Person2><Person1> "Billing and quotas: subscription. Lifecycle and cleanup: resource group. Broad policy and access across many subscriptions: management group. Too high and you over grant; too low and you create management overhead."

</Person2><Person1> "Create a Marketing management group, put both subscriptions in it, assign the policy to that management group. If they had been in the same management group as engineering you would reorganize or use assignment exclusions."
</Person1><Person2> "And scenario two: someone accidentally created one resource group named incorrectly and wants to rename it."
</Person2><Person1> "Cannot rename. Create the new resource group and move supported resources into it, then delete the old group. Not all resource types can move, and moving takes locks on source and target during the move, but the resource keeps running."

</Person1><Person1> "Episode three. Microsoft Entra ID: what it is, how it differs from on premises Active Directory, its editions, and Entra Domain Services. You told me this is a weak area, so we go slowly, with a lot of comparisons."
</Person1><Person2> "Start from the basics. What is Entra ID?"
</Person2><Person1> "Microsoft Entra ID, formerly Azure Active Directory, is Microsoft's cloud based identity and access management service. It does two big things. Authentication: proving who you are, with passwords, multifactor, passwordless. And authorization: deciding what you can access, through tokens, groups, roles and conditional access. It is the identity system behind Microsoft three sixty five, Azure, and thousands of other software as a service applications. Spoken: Microsoft three sixty five."
</Person1><Person2> "So how is it different from the Active Directory Domain Services running on a server in a company basement?"
</Person2><Person1> "Here is the comparison to memorize. Active Directory Domain Services, AD DS, is a server role on Windows Server. It is infrastructure you install, patch and back up on domain controllers. Entra ID is a platform as a service, a multi tenant cloud service where Microsoft runs the infrastructure. You do not deploy domain controllers for it."
</Person1><Person2> "Differences in structure."
</Person2><Person1> "AD DS has a hierarchy: forests, domains, organizational units, OUs, and group policy objects, GPOs. Entra ID is flat. There are no OUs, no forests, no domains in the same sense, and no group policy. Instead of GPOs, you use Intune for device configuration, and conditional access for access rules. AD DS has a computer object class for domain joined machines. Entra ID does not have a computer class; it has a device object class instead, which represents registered, joined or hybrid joined devices."
</Person1><Person2> "And protocols."
</Person2><Person1> "This is huge. AD DS uses LDAP for directory queries and Kerberos and NTLM for authentication. Entra ID does not support LDAP or Kerberos in the classic sense. It uses modern web protocols: SAML, WS Federation, OpenID Connect and OAuth two point zero for authentication and authorization. For queries it exposes REST APIs, the Microsoft Graph, over HTTP and HTTPS. So an old application that does LDAP bind to check a user cannot talk to Entra ID directly. That is exactly why Entra Domain Services exists, later in this episode."
</Person1><Person2> "How do I remember it?"
</Person2><Person1> "AD DS: LDAP, Kerberos, OUs, GPOs, computers, you manage servers. Entra ID: Graph, SAML, OIDC, OAuth, flat, devices, Microsoft manages the service. Old protocols versus web protocols, hierarchy versus flat."
</Person1><Person2> "Now tenants. This confuses people."
</Person2><Person1> "A tenant is a dedicated, isolated instance of Entra ID that your organization gets when it signs up for a Microsoft cloud service. A tenant is also called a directory, and it has a tenant ID, a globally unique identifier."
</Person1><Person2> "The relationship between subscription and tenant."
</Person2><Person1> "Straight from the notes. Each Azure subscription trusts exactly one tenant. But one tenant can be trusted by many subscriptions. It is one to many from tenant to subscriptions. You can move a subscription to a different tenant, called changing the directory, but doing that removes existing role assignments, since the users are in the old directory. Also, a user or guest can belong to or be invited into multiple tenants, but any one session works within one directory at a time, and you switch with the Directory plus subscription filter or the switch directory button."
</Person1><Person2> "What objects live in a tenant? Application and service principal I keep mixing up."
</Person2><Person1> "Good, slow down here. An application object is the global definition of an app: it lives in the tenant where the app is registered, the home tenant, and describes the app: its name, redirect URIs, permissions it needs. A service principal is the local instance of that application in a specific tenant: the identity that actually receives permissions and role assignments in that tenant. Think of it as the object instance. One application object can have a service principal in many tenants, for example, a multi tenant app used by other customers. When you do a role assignment to an application, you really assign it to its service principal. Managed identities are a special kind of service principal that Azure manages for you, no secrets to store."

</Person1><Person1> "Episode seven. Azure Policy, part one: the governance idea, cloud adoption guidance, design principles, the control plane and data plane, and the greenfield and brownfield flows. This is the conceptual foundation for the next two policy episodes."
</Person1><Person2> "What is Azure Policy, in one breath?"
</Person2><Person1> "A service to create, assign and manage policies that enforce rules and effects over Azure resources so they stay compliant with your standards. Policies are written in JSON and called policy definitions. A policy initiative is a collection of definitions grouped toward one goal, so you can assign them as one item. Policy enforces standards and assesses compliance at scale."
</Person1><Person2> "The notes start with the Cloud Adoption Framework."
</Person2><Person1> "The Microsoft Cloud Adoption Framework for Azure gives guidance for cloud architects and business leaders, across the adoption life cycle. Within it, the Govern methodology covers cloud governance: managing cloud usage in the organization, addressing regulatory compliance, security, operations, cost management, data, resource management and AI. Governance is a continuous process with five steps. One: build a governance team. Two: assess cloud risks. Three: document cloud governance policies. Four: enforce cloud governance policies, with automated tools plus manual oversight. Five: monitor cloud governance. Complete all five, then iterate steps two to five continuously."
</Person1><Person2> "And policy considerations."
</Person2><Person1> "Three: business risk, document risks and tolerance by data classification and application criticality; policy and compliance, convert risk decisions into policy statements; and process, establish processes to monitor violations. </Person1><Person2> "Azure Policy's role."
</Person2><Person1> "Azure's primary governance tool. It governs current and future resources, provides guardrails, centralized compliance tracking in a single repository, a compliance dashboard with aggregated view and drill down to resource and policy, prevents misconfiguration, and brings resources into compliance with bulk remediation for existing resources and automatic remediation for new ones. It reduces external approval processes, increasing developer productivity."
</Person1><Person2> "Useful governance actions listed."
</Person2><Person1> "Allowed regions only; geo replication rules for data residency; allowed virtual machine sizes; consistent tags; recommend system updates on servers; multifactor authentication for subscription accounts; require diagnostic logs sent to a Log Analytics workspace. </Person1><Person2> "Azure Resource Manager."
</Person2><Person1> "ARM is the deployment and management service for Azure, a management layer to create, update and delete resources. Operations split in two planes. Control plane: manages resources in your subscription. Data plane: access to capabilities of the resource instances."

</Person2><Person1> "Azure Policy operates in the control plane, integrated with ARM, which manages template based deployments, RBAC, auditing, monitoring, tagging, and so on. Same API everywhere, uniform results. Example: create a storage account and have a policy mandate encryption."
</Person1><Person2> "And data plane?"
</Person2><Person1> "The data plane is where data operations happen: uploading and downloading blobs, querying SQL, reading Key Vault secrets. Requests go directly to data endpoints, bypassing ARM, and the service handles them through its own resource provider. Permissions are often service specific, like RBAC data actions or ACLs. Azure Policy can reach into the data plane through resource provider modes, where services implement a policy extension. Six listed: Microsoft dot Kubernetes dot Data for clusters, pods, containers, ingresses; Microsoft dot KeyVault dot Data for vaults and certificates; Microsoft dot Network dot Data for Virtual Network Manager custom membership policies; Microsoft dot ManagedHSM dot Data for Managed HSM keys; Microsoft dot DataFactory dot Data to deny Data Factory outbound domain names; Microsoft dot MachineLearningServices dot v two dot Data for machine learning model deployments, reporting compliance for new and updated components."
</Person1><Person2> "Which of those are fully supported and which are preview, because the definitions section had a split?"
</Person2><Person1> "The definition table says: Kubernetes, Key Vault and Network are fully supported, limited to built in policies; Managed HSM and Data Factory are in preview."
</Person1><Person2> "Now greenfield versus brownfield."
</Person2><Person1> "The two scenarios ARM handles. Greenfield: policy first. A policy already exists, and you create or update a resource. The request passes through layers, including RBAC and Azure Policy, and note: Policy comes after RBAC. If you lack permission, the request fails at RBAC and Policy is not even called. If you have permission, the request goes to Policy and is evaluated. For updates you send only the delta, and Policy needs the full current state, so it merges the delta with the current resource to compute the target state, then evaluates that."
</Person1><Person2> "Brownfield."
</Person2><Person1> "Resource first: resources already exist and you assign a new policy. Evaluation happens through a compliance scan, automatically every twenty four hours or manually triggered. Duration is unpredictable. Policy reads all existing resources in scope. Example: policy that prohibits resources outside West Europe. Existing resources elsewhere are not deleted but flagged noncompliant, while future creation outside West Europe fails."
</Person1><Person2> "Interesting. So a deny policy does not delete?"
</Person2><Person1> "Correct. Deny only blocks new or updated requests. Existing noncompliant resources just show as noncompliant. To fix them you remediate, or move or delete them yourself, or use remediation tasks for modify and deployIfNotExists."
</Person1><Person2> "A scenario."
</Person2><Person1> "Question: after assigning a policy that requires a tag, existing resources lack the tag and none were blocked. Why? Because it's brownfield; deny blocks new creation or updates; existing show noncompliant after the scan. Another: user cannot create a VM, error says they are not authorized, not mention of policy. That's RBAC failing first."
</Person1><Person1> "Recap. Governance five steps and five disciplines. Policy in control plane via ARM, data plane via resource provider modes. RBAC first, Policy second. Greenfield is evaluated at request time, brownfield by scan every twenty four hours. Next: policy resources and definitions."
</Person1><Person1> "Episode eight. Azure Policy resources and the anatomy of a policy definition, including modes, conditions, operators, functions and every effect. This is the dense one."
</Person1><Person2> "Six policy resources. List them."
</Person2><Person1> "Definitions, initiatives, assignments, exemptions, attestations, remediations. Six. Memory line: define, group, assign, exempt, attest, remediate."
</Person1><Person2> "Definitions first and scope."
</Person2><Person1> "A definition describes compliance conditions and the effect when the condition is met. Where you save a definition, the definition location, which is a management group or subscription, decides the scope to which it can be assigned. Put it in the container shared by all resources you want to use it on. Scope under the root: management group, subscription, resource group, resource; lower inherit from higher."
</Person1><Person2> "Initiatives."
</Person2><Person1> "Also called a policy set. A group of definitions you assign as one item. Example: several tagging policies in one tagging initiative. Defined with JSON. The initiative tracks compliance toward a larger goal, such as regulatory frameworks. Built in policy: a definition generated by Azure resource providers, available by default; a group of those is a built in initiative. Custom policy: written by you when no built in policy fits; group them as a custom initiative. Microsoft for Sovereignty provides custom initiatives and compliance mappings in an industry policy portfolio on GitHub, to expand on built in ones, for sovereignty needs of government and finance."
</Person1><Person2> "Assignments."
</Person2><Person1> "Assignments define which resources a definition or initiative evaluates. Created in portal, API or command line, at management group, subscription or resource group scope. Optional parts: resource selectors, for gradual rollout based on location or type; overrides, to change the effect without changing the definition; enforcementMode, which can be disabled for what if testing; excluded scopes, to exclude inner containers or resources; noncompliance messages; parameter values. For a deployIfNotExists policy, a managed identity, system assigned or user assigned, must be assigned so remediation can deploy. Inclusion and exclusion are the two scope properties."
</Person1><Person2> "Exemptions."
</Person2><Person1> "Exempt a resource hierarchy or an individual resource from evaluation. Exempt resources count toward overall compliance but are not evaluated, or are temporarily waived. They are created as a child object on the resource or hierarchy after assignment, not at assignment time. Effect similar to excluded scope. Two categories: Mitigated, the intent is met another way; Waiver, noncompliance is temporarily accepted. Exemptions can have an expiry date."
</Person1><Person2> "Attestations and remediations."
</Person2><Person1> "Attestations set the compliance state of resources or scopes targeted by manual policies. Each applicable resource needs one attestation per manual policy assignment. Design manual policies to target the boundary needing attestation. Remediations: policy remediation tasks bring resources into compliance for modify or deployIfNotExists assignments. Newly created or updated resources applicable to those effects are automatically remediated; existing noncompliant ones need a remediation task."
</Person1><Person2> "Now the anatomy of a definition JSON."
</Person2><Person1> "Elements: displayName, a string up to one hundred twenty eight characters. description, up to five hundred twelve characters. policyType, read only: BuiltIn, Custom, Static; static is regulatory compliance policy owned by Microsoft. mode. version, optional. metadata, optional, up to one thousand twenty four characters, with version, category, preview, deprecated, portalReview. parameters, optional. policyRule, with if and then."
</Person1><Person2> "Modes."
</Person2><Person1> "Resource Manager modes: All, which evaluates resource groups, subscriptions and all resource types; and Indexed, which evaluates only resource types that support tags and location. The notes' table text is repetitive, but the standard distinction is that, so use Indexed for tag and location policies, and All when you must evaluate resource groups and subscriptions too. Resource provider modes: Kubernetes, Key Vault, Network fully supported with built ins; Managed HSM and Data Factory in preview."
</Person1><Person2> "Parameters."
</Person2><Person1> "Reduce the number of definitions by making them reusable. Properties: name, type, metadata, defaultValue, allowedValues, schema. Types: String, Array, Object, Boolean, Integer, Float, DateTime. Metadata: description, displayName, strongType, assignPermissions. Strong type gives a portal picker, such as a location list. Example definition: Allowed locations, mode Indexed, parameter listOfAllowedLocations of type Array, and the rule: if location is not in the list and location is not global and type is not B two C directories, then effect deny. B two C directories are excluded because their location field is not a region."
</Person1><Person2> "Logical operators."
</Person2><Person1> "not inverts. allOf requires all conditions, like and. anyOf requires one or more, like or. Can be nested; example, allOf containing a not on tags containsKey application and type equals storage accounts. That means storage accounts missing the application tag."
</Person1><Person2> "Conditions."
</Person2><Person1> "Fields: properties of the request payload, like name, fullName, kind, type, location, ID, identity type, tags, tag by name, and property aliases. Value: evaluate an expression or function result. Count: how many members of an array meet criteria; field count and value count; the current function returns the array member being evaluated. If a function errors, the policy results in deny; avoid by disabling enforcement mode during tests."
</Person1><Person2> "Operators."
</Person2><Person1> "equals, notEquals, like, notLike with wildcard, match, notMatch, matchInsensitively, notMatchInsensitively, contains, notContains, in, notIn, containsKey, notContainsKey, less, lessOrEquals, greater, greaterOrEquals for dates, strings or integers, and exists for Boolean. In the notes' example, a value of resource group name like star netrq, and type notLike Network slash star."
</Person1><Person2> "Functions."
</Person2><Person1> "ARM template functions are available except a few, and user defined functions. utcNow can be used outside defaultValue in policy, returning ISO eight six oh one date time. Policy only functions: addDays, field, requestContext apiVersion, policy, which returns assignmentId, definitionId, setDefinitionId, definitionReferenceId, ipRangeContains, and current, which works only inside count."
</Person1><Person2> "Now the effects. List them."
</Person2><Person1> "Nine: disabled, append, modify, deny, denyAction, audit, auditIfNotExists, deployIfNotExists, manual."
</Person1><Person2> "Detail."
</Person2><Person1> "Disabled: turns the policy off; checked first; lets you disable one assignment. Append: adds fields to the request on create or update; mostly obsolete since modify can do it. Modify: add, update or remove properties or tags during creation or update, altering the ARM request; uses a managed identity for remediation of existing resources. Deny: blocks a request that does not meet standards. DenyAction: blocks requests based on intended action; currently only DELETE supported. Audit: creates a warning event in the activity log for a noncompliant resource but does not block. AuditIfNotExists: audits resources related to the one matching the if condition that lack the properties in the details. DeployIfNotExists: runs a template deployment when the condition is met, to deploy a related resource. Manual: self attest compliance through attestations."
</Person1><Person2> "Synchronous and asynchronous."
</Person2><Person1> "Disabled, append, modify, deny, denyAction: synchronous evaluation, at request time. Audit, auditIfNotExists, deployIfNotExists: asynchronous, after the request is accepted. Manual: manual attestation."
</Person1><Person2> "Interchangeable ones."
</Person2><Person1> "Audit, deny and modify or append are often interchangeable. AuditIfNotExists and deployIfNotExists are interchangeable. Manual is not interchangeable. Disabled is interchangeable with any. Multiple policies can apply to a resource, each independent; the net result is cumulative most restrictive. If one denies, it is denied, even if another audits."
</Person1><Person2> "A common exam style."
</Person2><Person1> "Require a tag: deny or modify. Add a tag automatically: modify or append. Make sure every VM has the monitoring extension: deployIfNotExists. Just report: audit. Prevent deleting critical resources at scale: denyAction, versus locks which are per resource. Check a related resource exists, like backup: auditIfNotExists."
</Person1><Person1> "Recap. Six resources. Definition: if condition then effect. Nine effects. Cumulative most restrictive. Next: evaluation, enforcement mode, safe deployment and events."
</Person1><Person1> "Episode nine. Azure Policy, part three: evaluation triggers and timing, compliance states, enforcement mode, safe deployment with rings, and reacting to policy events."
</Person1><Person2> "When does Policy evaluate?"
</Person2><Person1> "Triggers from the notes: a policy or initiative is newly assigned to a scope; an assigned one is updated; a resource is deployed or updated in a scope with an assignment, through ARM, REST or SDK; a subscription is created or moved in a management group hierarchy with a policy targeting the subscription type; a policy exemption is created, updated or deleted; the standard compliance evaluation cycle; the machine configuration resource provider is updated with compliance details by a managed resource; and an on demand scan."
</Person1><Person2> "Timing."
</Person2><Person1> "Automatic full scan every twenty four hours. For brownfield, trigger manually with the command az policy state trigger scan. When you assign a new policy, a delay of up to thirty minutes can occur before it takes effect, because the ARM cache holds session data. To bypass, sign out and back in. Scan duration depends on: size and complexity of definitions, number of policies, scope size, and system load. Scans are low priority and synchronous in the notes' wording, so they can take minutes or tens of minutes even for small environments. Do not conclude failure too early."
</Person1><Person2> "Compliance states."
</Person2><Person1> "Non compliant, compliant, error for template or evaluation error, conflicting for two or more assignments in the same scope with contradicting rules, such as two policies appending the same tag with different values, protected for resources covered by a denyAction assignment, and exempted or unknown, where unknown is the default state for manual effect definitions. When multiple states apply, the overall state is ranked in that order, one wins over another. Compliance percentage: compliant plus exempt plus unknown divided by total, where total includes compliant, non compliant, unknown, exempt, conflicting and error."
</Person1><Person2> "Enforcement mode."
</Person2><Person1> "A property of the assignment that deactivates enforcement of effects. It lets you test results on existing resources without triggering the effect or Activity Log entries. This is the what if. Values: Enabled, JSON value Default, effect enforced during create or update, remediate manually yes, activity log yes. Disabled, JSON value DoNotEnforce, effect not enforced, remediate manually yes, activity log no. Not specified means Default. Remediation tasks can still be started for deployIfNotExists policies when DoNotEnforce is set."
</Person1><Person2> "How is it different from the disabled effect?"
</Person2><Person1> "Disabled effect prevents evaluation from happening at all. Enforcement mode disabled still evaluates and reports compliance but does not take the action. So with a deny policy and DoNotEnforce, a bad resource gets created but is reported noncompliant. Good question to remember: which setting lets you see impact of a deny policy without blocking? enforcementMode DoNotEnforce."
</Person1><Person2> "Safe deployment."
</Person2><Person1> "Applying policy to production blindly can cause surprises. Treat policy as code: definitions in source control, test and validate changes, automate. Two aspects. First, start new policy assignments with enforcementMode disabled, especially for deny and modify. Second, deploy in rings: smaller subsets first, then larger, starting with test and dev, then production."
</Person1><Person2> "The steps."
</Person2><Person1> "One: create the definition at tenant root scope. Two: create an assignment, define rings one to five using resource selectors, assign to a specific scope, ring five first, enforcementMode disabled. Three: compliance check and application health check on ring five. Four: repeat for each non production ring. Five: update the assignment if needed and reassign with enforcementMode enabled. Six: repeat checks. Seven: repeat for non production rings. Eight: deploy gradually to production, smaller subset first."
</Person1><Person2> "Why resource selectors?"
</Person2><Person1> "They let one assignment target resources by location or type for gradual rollout. Overrides then adjust the effect without editing the definition, for example, set deny in one ring and audit in another."
</Person1><Person2> "Events."
</Person2><Person1> "Azure Policy emits events when state changes, pushed through Azure Event Grid to event handlers, with no polling. Event Grid provides reliable delivery, retry policies, dead letter delivery, routing, filtering and multicasting through Event Grid subscriptions. Event handlers: Azure Functions, Logic Apps, custom HTTP listeners, any webhook. Use: trigger a remediation workflow or notify when compliance changes."
</Person1><Person2> "Summary points the notes list."
</Person2><Person1> "Careful design, testing so governance does not disrupt operations, logical operators, supported effects, start with enforcement off, deploy in rings."
</Person1><Person2> "Scenario drill."
</Person2><Person1> "One: you assign a deny policy for allowed locations and want to see which resources would be affected, without blocking. Set enforcement mode DoNotEnforce. Two: a new policy was assigned and resources do not show compliance yet. Wait for the scan, up to twenty four hours, or run trigger scan; also the thirty minute propagation delay. Three: an exempt resource still appears in compliance reports. Yes, counted as exempt, included in percentage. Four: you need to notify a team when a resource becomes noncompliant. Event Grid with an Azure Function or Logic App. Five: two policies in one scope add the same tag with different values. Conflicting state."
</Person1><Person1> "Recap. Evaluation: triggers, every twenty four hours, thirty minute delay, trigger scan. States: seven. Enforcement mode versus disabled effect. Rings. Event Grid. Next: Azure RBAC."
</Person1><Person1> "Episode ten. Azure role based access control, RBAC, from the official notes. Who, what, where; the allow model; NotActions; inheritance; the portal tasks; and audit logging with its retention numbers."
</Person1><Person2> "Start with the problem it solves."
</Person2><Person1> "Two concerns of organizations moving to the cloud. One: when people leave, they lose access to cloud resources. Two: balance autonomy and central governance, for example let project teams create virtual machines while central IT controls the networks. Entra ID and Azure RBAC together achieve this."
</Person1><Person2> "Subscriptions and tenant again."
</Person2><Person1> "Each subscription is associated with one Entra tenant. Users, groups, service principals and managed identities receive access through authorization mechanisms such as role assignments; being in the directory does not itself grant access to resource management. An important warning in the notes: disabling an on premises account is not a guarantee that cloud access ends immediately. For a synced identity the change must reach Entra ID, and existing tokens or sessions can remain valid for a while. Follow the access revocation procedure, and review Azure role assignments separately in offboarding, because blocking sign in and removing authorization are different actions."
</Person1><Person2> "What is Azure RBAC?"
</Person2><Person1> "An authorization system built on Azure Resource Manager giving fine grained access management. Example: one employee manages virtual machines, another manages SQL databases, in the same subscription. You assign a role to users, groups or applications at a scope: management group, subscription, resource group or single resource. Child scopes inherit permissions from the parent; inheritance does not add permissions to the role itself. Reader at a resource group means view only."
</Person1><Person2> "Two role systems."
</Person2><Person1> "Azure RBAC manages access to Azure resources at the four scopes. Entra roles administer directory resources, users, groups, applications. They are separate. A subscription is tied to one tenant but that does not automatically give directory admins access to resources. Billing permissions are also distinct from role assignments. A Global Administrator does not automatically have access to Azure resources. For the exam: remember this, and that a Global Administrator can elevate access, with the elevate access toggle, to become User Access Administrator at root scope."
</Person1><Person2> "When full control is needed?"
</Person2><Person1> "Assign Owner at subscription scope for full resource administration and delegation. For narrower tasks, use a job function role or an access administration role such as Role Based Access Control Administrator at the smallest suitable scope."
</Person1><Person2> "Scenarios from the notes."
</Person2><Person1> "Allow one user to manage VMs in a subscription and another to manage virtual networks. Allow a database administrator group to manage SQL databases. Allow a user to manage all resources in a resource group. Allow an application to access all resources in a resource group."
</Person1><Person2> "Where in the portal?"
</Person2><Person1> "Access control IAM, identity and access management, blade, present on many scopes. Tabs include Check access, Role assignments, Roles, Deny assignments. Example: Alain assigned Backup Operator for a resource group shows under the group's Access control IAM, Role assignments."
</Person1><Person2> "How does it work: the three elements."
</Person2><Person1> "Who, what, where. Security principal, the who: user, group, service principal or managed identity. Role definition, the what: a collection of permissions, such as read, write, delete. Scope, the where. Role assignment binds them. To grant, create an assignment; to revoke, remove it."
</Person1><Person2> "Role definitions and the structure."
</Person2><Person1> "Management permissions use Actions and NotActions. Data permissions use DataActions and NotDataActions. Fundamental built in roles: Owner, full access including delegation. Contributor, create and manage all resources but cannot grant access. Reader, view only. User Access Administrator, manage user access. Custom roles if built in ones are insufficient. Azure has more than two hundred built in roles at the summary, and the list exercise says more than seventy; so the current number is over two hundred."
</Person1><Person2> "Scope inheritance example."
</Person2><Person1> "Marketing group, Contributor, sales resource group. Contributor permissions apply in the sales group. A group with Contributor at the subscription inherits it for all groups and resources."
</Person1><Person2> "The allow model."
</Person2><Person1> "Assignments are additive. If one grants read and another grants write, the user has both, subject to deny assignments and role assignment conditions. NotActions excludes operations from the wildcard Actions of a role; Actions minus NotActions is what it grants. Important: NotActions is not a deny. Another assignment can grant the excluded operation. A deny assignment can block an operation even if a role grants it; deny assignments are created by Azure features like deployment stacks and blueprints, not manually by customers."
</Person1><Person2> "Contributor exclusions."
</Person2><Person1> "Actions star, with exclusions: Microsoft dot Authorization star slash write and star slash delete, so no role assignment changes; elevate access; sharing an image gallery; and managing a deployment stack's deny settings. </Person1><Person2> "Deployment tools."
</Person2><Person1> "Bicep or ARM templates to author resources, role assignments and policy assignments. Template specs store and version templates but do not provide lifecycle management or deny.
