<Person1> "Welcome back to Study Deep Dive. Episode seven: Azure Storage fundamentals. Accounts, redundancy, access tiers, Data Lake, blob types, blob inventory and object replication. This covers questions eleven to fourteen, forty four and fifty six. These are the ideas you need before the security and data protection details in the next episode."
</Person1><Person2> "Begin with the account itself."
</Person2><Person1> "A storage account is a namespace for your storage data, with a unique name, three to twenty four characters, lowercase letters and numbers, globally unique because it forms the DNS name. Inside it you can have Blob storage, Azure Files, Queue storage and Table storage. Each service has its own endpoint: blob dot core dot windows dot net, file dot core, queue dot core, table dot core, and dfs dot core for the Data Lake API."
</Person1><Person2> "Account types."
</Person2><Person1> "The standard type is general purpose version two, shown as StorageV2. It supports all four services and all tiers, and it's the default. Premium types are specialized: Premium block blobs, kind BlockBlobStorage, for low latency blob workloads. Premium file shares, kind FileStorage, for high performance Azure Files, supporting SMB and NFS. Premium page blobs for page blob workloads. Older types, general purpose version one and the legacy Blob Storage account kind, still exist, and the exam writes BlobStorage when it means a blob only account. Question fourteen asked which account kinds support object replication for the destination, and the answer was StorageV2 or BlobStorage only. FileStorage can't, because there are no blobs there."
</Person1><Person2> "Now redundancy in depth."
</Person2><Person1> "Locally redundant storage, LRS. Three synchronous copies in one datacenter in the primary region. Eleven nines of durability. Protects against disk and rack failures, but not against a datacenter outage. Zone redundant storage, ZRS. Three synchronous copies across three availability zones in the primary region. Twelve nines. Survives a zone failure, still in one region. Geo redundant storage, GRS. LRS in the primary, plus an asynchronous copy using LRS in the paired secondary region, hundreds of miles away. Sixteen nines. Geo zone redundant storage, GZRS. ZRS in the primary, plus LRS in the secondary. Sixteen nines, the strongest protection. And the read access versions, RA GRS and RA GZRS, where the secondary endpoint is readable at any time, not only after a failover."
</Person1><Person2> "Which are available for premium?"
</Person2><Person1> "Premium accounts support LRS and ZRS only, not geo redundancy. Standard supports all. Also, with GRS, the secondary data isn't readable unless you fail over, or use the RA variant. Failover can be customer initiated, which promotes the secondary, and the account becomes LRS in the new primary, so you reconfigure geo redundancy afterward. Replication to the secondary is asynchronous, so a failover can lose recent writes, the last sync time property tells you how far behind it is."
</Person1><Person2> "Now question forty four."
</Person2><Person1> "Account storage one needs: compatible with Data Lake Storage capabilities, optimized for infrequently accessed data cost, and automatic replication to another Azure region. Three of five options: hierarchical namespace, the Cool tier, and GRS. ZRS fails the third requirement, since ZRS stays in one region. The Hot tier fails the second, since Hot has the highest storage cost, optimized for frequent access. So pick one for each requirement, matching the exact words. Data Lake equals hierarchical namespace. Infrequent access equals Cool. Another region equals geo redundancy."
</Person1><Person2> "How could they twist it?"
</Person2><Person1> "Replace another region with another availability zone, and the answer is ZRS. Add the requirement that secondary data must be readable, and the answer is RA GRS. Replace infrequent with rarely accessed and kept for months, and it might be Cold or Archive, depending on whether offline is acceptable."
</Person1><Person2> "Explain the access tiers properly."
</Person2><Person1> "Hot, for data accessed frequently. Highest storage price, lowest access price. Cool, for infrequently accessed data, kept at least thirty days, lower storage price, higher access price. Cold, kept at least ninety days, cheaper still. Archive, for rarely accessed data kept at least one hundred eighty days, lowest storage price, but the blob is offline. You can't read an archived blob until you rehydrate it to Hot, Cool or Cold, which takes hours, standard priority up to fifteen hours, high priority under an hour for small blobs. The account default tier can be Hot or Cool, Archive is set per blob. Deleting or moving a blob before the minimum period incurs an early deletion charge. And lifecycle management rules move blobs automatically between tiers based on age or last access."
</Person1><Person2> "Hierarchical namespace."
</Person2><Person1> "It's the feature that turns blob storage into Azure Data Lake Storage Gen two. Without it, blob storage has a flat namespace: container, then blob names. A slash in a blob name is just a character, the folders are virtual. With hierarchical namespace you get real directories. Rename or delete of a directory is a single atomic metadata operation instead of copying every blob one by one. You get POSIX style access control lists on files and directories, along with RBAC. You get the dfs endpoint and the Data Lake APIs, and it's required for NFS version three and SFTP support on blob storage. It's also what big data analytics engines want. You enable it at creation, with the Enable hierarchical namespace option, and existing accounts can be upgraded in some cases, as a one way operation."
</Person1><Person2> "Question fifty six."
</Person2><Person1> "The case study: content organized in containers and file shares. data1 is in datastore1, which has hierarchical namespace enabled. data2 is in datastore2 without it. docs1 and docs2 are file shares. The question: across which containers and file shares can this content be organized? The planned change needs a directory structure. The answer: data1, docs1 and docs2. data1 qualifies because its account has hierarchical namespace. File shares have real directories by design, with or without hierarchical namespace, since hierarchical namespace is a blob feature. data2 fails because it's in a flat account."
</Person1><Person2> "The trap is thinking file shares need hierarchical namespace."
</Person2><Person1> "Exactly. Azure Files is a separate service with its own folder structure. Hierarchical namespace only concerns blob containers."
</Person1><Person2> "Blob types."
</Person2><Person1> "Block blobs, made of blocks up to about one hundred megabytes each in the newest service version, total up to about one hundred ninety terabytes. Used for documents, images, video, backups. Append blobs, optimized for append operations, made of blocks that you can only add to the end, with no modifications in place. Used for logs. Page blobs, a collection of five hundred twelve byte pages, optimized for random read and write, up to eight terabytes. Used as the backing for unmanaged VM disks, and managed disks use them under the hood. Question eleven: blob inventory for images, block blob. Memory: block equals general files, append equals logs, page equals disks."
</Person1><Person2> "Blob inventory in depth. Questions eleven and twelve."
</Person2><Person1> "Blob inventory gives you a report of your blobs and containers, with properties, on a schedule, instead of listing millions of blobs by API. You create an inventory policy on the account, made of rules. A rule has a name, whether it's enabled, a destination container where reports are written, a definition with the object type, either blob or container, a schedule, daily or weekly, a format, CSV or Parquet, schema fields to include, and filters, which include the blob types and the prefix matches. In the ARM template for the question, code segment A was the blob type to include, and code segment B was the prefix match."
</Person1><Person2> "Why was it images slash finance?"
</Person2><Person1> "Prefix matches in blob inventory and lifecycle policies are written container name first, then a slash, then the blob name prefix. The container is images, the prefix is finance, so images slash finance. Just finance has no container, so it matches nothing useful. Images slash star isn't a valid prefix and would not mean what you want. The report is generated once a day, into the images container in this question, which is a bit odd, since the report would sit beside the data, but it's what the requirement said. And the report writes as CSV."
</Person1><Person2> "Twist?"
</Person2><Person1> "Ask for blobs under a virtual folder, like images slash finance slash two thousand twenty six, which is container, then folder prefix. Or ask for Parquet instead of CSV. Or ask for append blobs, for logs."
</Person1><Person2> "Object replication, questions thirteen and fourteen."
</Person2><Person1> "Object replication asynchronously copies block blobs from a source container to a destination container, in another account, using replication rules. You can filter by prefix and minimum creation time, and you can copy only new blobs or also existing ones. Requirements. Both accounts must be general purpose version two or premium block blob. Blob versioning must be enabled on both accounts. Change feed must be enabled on the source. Replication is for block blobs only, not append or page blobs, and it works across regions or inside one region, even across subscriptions and tenants with permissions. The destination container is where replicated blobs land, so it must exist."
</Person1><Person2> "Question thirteen, which object must you create?"
</Person2><Person1> "A container, in the destination account. Why not the others? File shares belong to Azure Files, tables to Table storage, queues to Queue storage, none of which object replication supports."
</Person1><Person2> "Things that break object replication?"
</Person2><Person1> "Blobs in the archive tier can't be replicated until rehydrated, snapshots aren't replicated, and the destination container is writable only by the replication process, in practice, so don't plan to write there. Replication isn't instant and has no guaranteed time unless you enable replication time control in some configurations."
</Person1><Person2> "Where do soft delete, versioning, change feed and point in time restore fit?"
</Person2><Person1> "Soft delete keeps deleted blobs for a retention period. Versioning keeps prior versions automatically when a blob is overwritten. Change feed logs every create, modify and delete, in order. Point in time restore uses change feed, versioning and soft delete to restore block blobs to an earlier time. Object replication requires versioning and change feed. We'll connect them in the data protection episode."
</Person1><Person2> "Summarize."
</Person2><Person1> "Account kinds: StorageV2 is the default, premium kinds for performance, and premium only supports LRS and ZRS. Redundancy: another zone means ZRS, another region means GRS or GZRS. Tiers: Hot, Cool at thirty days, Cold at ninety, Archive at one eighty and offline. Data Lake equals hierarchical namespace, which is a blob feature, not a file share feature. Block, append and page blobs. Inventory prefix equals container name, slash, blob prefix. Object replication needs versioning on both sides, change feed on source, and a destination container. Next episode: storage security and data protection."
