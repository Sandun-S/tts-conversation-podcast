</Person1><Person2> "Questions twenty nine and thirty. Creating the registry and pushing."
</Person2><Person1> "On a workstation with Azure CLI and Docker, you've built an image invoiceservice dash img. You must create a new registry and push the image. Which command creates the registry? az acr create. Which command adds the image to the registry? docker push. Distractors: az acr build builds an image from source in the cloud and pushes it, it doesn't create the registry. az container create creates a container instance. docker create makes a local container from an image. az acr login authenticates Docker to the registry. docker pull downloads. docker tag adds a repository name and tag to an image, preparing it for the push but not uploading."

Five, to verify, az acr repository list. Notice the tag step is needed because docker push uses the registry in the image name, so the local name has to include the login server."
</Person1><Person2> "Authentication to the registry, questions fifteen to eighteen."
</Person2><Person1> "Four related questions. You manage ACR corpRegistry containing webappimage. Deploying an Azure Container Instance with the image fails with an error. You must ensure a container instance can be deployed successfully using the image. Four proposed solutions. Question fifteen: configure a private endpoint for corpRegistry. No. Question sixteen: enable the dedicated data endpoint. No. Question seventeen: assign AcrPull to ACR Tasks Network for Registry1. No. Question eighteen: set Admin user to Enable. Yes."
</Person1><Person2> "Explain each."
</Person2><Person1> "A private endpoint changes how you reach the registry, giving it a private IP. It doesn't give the container instance credentials. It could even make things worse, since an ACI outside the VNet couldn't reach the private endpoint. The dedicated data endpoint gives the registry regional data endpoints, so firewall rules can be narrow: instead of allowing wildcard blob storage, you allow a specific data endpoint name. It's a networking improvement, not authentication. Assigning AcrPull is the right type of fix, but the role has to go to the identity that actually pulls: the managed identity of the container instance, or a service principal whose credentials you provide. ACR Tasks Network is not that identity. The admin user gives the registry a username and password, which you pass to ACI as image registry credentials, so ACI can authenticate and pull."
</Person1><Person2> "You said yes to question seventeen."
</Person2><Person1> "Because the role name was right. The exam was checking whether you ask, to whom is it assigned? A role assignment is principal, role, scope. Right role, wrong principal, no effect. That's the same RBAC engine from episode one."
</Person1><Person2> "What are the proper authentication methods?"
</Person2><Person1> "Individual Entra identity, via az acr login, for developers. A service principal with a role like AcrPull, whose ID and secret go into pull configuration, good for headless systems. A managed identity with AcrPull, assigned to the ACI, AKS kubelet, App Service or Container Apps, which is the best practice with no secret. Repository scoped tokens, which give fine grained, limited access to specific repositories. And the admin account, a single shared account, disabled by default, good for testing, not recommended for production. Registry roles: AcrPull, AcrPush, AcrDelete, AcrImageSigner, and Owner, Contributor, Reader for management."
</Person1><Person2> "Why is it recommended not to use admin?"
</Person2><Person1> "It's a single shared credential, with two passwords, full push and pull, no audit trail per user, and it can't be scoped. But in an exam question that asks for the quickest way to make a pull work with credentials, enabling admin is accepted."
</Person1><Person2> "Now Azure Container Instances."
</Person2><Person1> "ACI runs containers without managing servers. You pay per second for CPU and memory. It's good for simple apps, task automation, batch jobs, build jobs. Containers are deployed in a container group, which is a collection of containers scheduled on the same host, sharing a lifecycle, resources, network and storage volumes, like a Kubernetes pod. Containers in a group share an IP address and port namespace and can talk to each other via localhost. You can expose a public IP with a DNS name label, or deploy into a VNet with a delegated subnet. Volumes can be Azure Files shares, empty directories, secrets, or cloned git repos. Restart policy: Always, OnFailure, Never. Linux containers support multi container groups, Windows containers are limited to a single container per group, and with some feature limits like no VNet."
</Person1><Person2> "Question thirty one, resources."
</Person2><Person1> "PodGroup1 hosts two ACI containers. svc api: request two CPUs, limit two CPUs. svc worker: request three CPUs, limit four CPUs. You need svc worker to use CPU without negatively affecting svc api. The answer: remove the resource limit for both containers. The reasoning from the documentation: the group's resources are allocated based on the sum of requests, five CPUs here. A request is a guaranteed minimum for the container, a limit is a maximum. If you don't specify a limit, the container's maximum usage is the same as its request. So after removing the limits, svc api can't exceed two, svc worker can't exceed three, so no container can burst into someone else's share."
</Person1><Person2> "Why is every other option wrong?"
</Person2><Person1> "Increasing svc api's limit to three allows it to burst, increasing contention. Increasing svc worker's limit to six is invalid since the group only has five CPUs from requests. Decreasing svc worker's limit to two is invalid because a limit must be equal to or greater than the request, which is three. Moving the worker to another group would work architecturally, but isn't required and changes the deployment. Rules to memorize: limit is greater than or equal to request, no limit means max equals request, group size is the sum of requests."
</Person1><Person2> "Azure Container Apps."
</Person2><Person1> "A serverless platform for running containers, microservices and jobs, built on Kubernetes, with KEDA for event driven scaling, Dapr for microservice building blocks, and Envoy for ingress, but without managing the cluster. Concepts: an environment is a secure boundary, a container app has revisions, which are immutable snapshots, scale rules include HTTP, TCP and event sources, and it can scale to zero. Container Apps runs Linux containers only, and supports managed identity to pull from ACR and to read Key Vault secrets, which is why question forty one used it."
</Person1><Person2> "App Service as a container host."
</Person2><Person1> "App Service can run custom containers on Linux plans, and on Windows plans with Premium v3 and Isolated tiers. It's good for web apps and APIs with managed scaling, slots, TLS and domains. AKS gives full Kubernetes control: node pools, including Windows node pools, networking, add ons, with more operational overhead."
</Person1><Person2> "Questions sixty two and sixty three. The table of services versus OS."
</Person2><Person1> "Which services support WinImg1, a Windows Server based image? App Service or Azure Container Instances only, not Container Apps. Which support LinuxImg1? All three: App Service, Container Apps and Container Instances. You picked Container Apps or ACI for the Windows image. The mistake: assuming a modern service supports both operating systems. Memory table. Linux: App Service yes, ACI yes, Container Apps yes. Windows: App Service yes, ACI yes, Container Apps no. So Container Apps equals Linux only."
</Person1><Person2> "Twist?"
</Person2><Person1> "Ask about an image that must scale to zero based on queue length, Container Apps, Linux. Ask about a Windows container needing VNet integration, App Service with VNet integration, since ACI Windows doesn't support VNet. Ask which service needs no orchestration, ACI."
</Person1><Person2> "Now App Service fundamentals."
</Person2><Person1> "An App Service plan defines the compute: region, operating system, size, and pricing tier. Many apps can share a plan and share its resources. Tiers: Free and Shared for dev and test on shared infrastructure; Basic for dedicated compute with manual scaling and custom domains; Standard adds autoscale, deployment slots, and backups; Premium adds more scale and slots, and better performance; Isolated runs in an App Service Environment inside your VNet. Scale up changes the tier or size, scale out changes the instance count. Autoscale uses rules or schedules. Always On keeps the app loaded. Regional VNet integration lets the app reach private resources, and private endpoints make the app reachable privately."
</Person1><Person2> "Deployment slots."
</Person2><Person1> "Available in Standard and above. A slot is a live app with its own hostname, running in the same plan. You deploy to staging, warm it up and test, then swap with production, which routes traffic with no downtime and can be rolled back by swapping again. Slot specific settings stay with the slot. You can do traffic splitting for testing in production."
</Person1><Person2> "Deployment methods and question one."
</Person2><Person1> "ZIP deploy, Web Deploy, FTP or FTPS, Git, GitHub Actions, Azure DevOps, container deployment. Basic authentication, with FTP and SCM credentials, can be disabled, forcing Entra based deployment. Question one asked: developers publish updates via Web Deploy using their Entra accounts, least privilege. The correct option: assign the Website Contributor role. App level and user level FTPS credentials aren't Entra credentials. Owner is too broad. Website Contributor allows managing web apps but not the plan and not access, which is least privilege for deployment."
</Person1><Person2> "Now certificates, question fifty seven."
</Person2><Person1> "AppSvc1 must use a certificate from SecVault1, a Key Vault. Four certificates: TlsCert1 and TlsCert2 in PKCS twelve format, TlsCert3 and TlsCert4 in PEM format. Which are usable? TlsCert1 or TlsCert2 only. App Service imports PFX, that is PKCS twelve, certificates from Key Vault. PEM isn't accepted directly. You selected all four."
</Person1><Person2> "More details about certificates in App Service."
</Person2><Person1> "Certificate options: a free App Service managed certificate, for a custom domain, auto renewed, but no wildcard and not for apex domains in some cases; a purchased App Service certificate; an imported certificate from Key Vault; an uploaded PFX; and a public certificate in cer format for outbound trust. Requirements for PFX: password protected with triple DES encryption, contains the private key, built using exportable keys, at least two thousand forty eight bits, includes the intermediate certificates in the chain. For Key Vault, App Service needs permission to read the vault, the App Service resource provider identity must have Get on secrets and certificates, or the right RBAC role. After import, you add a TLS binding to a custom domain, using SNI SSL, which is common, or IP based SSL. You can enforce HTTPS only and set a minimum TLS version."
</Person1><Person2> "Twist for the question?"
</Person2><Person1> "Ask which formats a Key Vault certificate must be to be used with App Service, PKCS twelve. Ask which certificate would work if converted, the PEM ones, since you can convert PEM to PFX with openssl. Ask which tier supports custom domain bindings with TLS, Basic and above."
