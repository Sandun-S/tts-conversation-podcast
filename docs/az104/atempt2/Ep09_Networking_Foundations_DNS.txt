</Person1><Person2> "Start with the virtual network."
</Person2><Person1> "A virtual network, VNet, is your private network in Azure. It's scoped to one region and one subscription. You give it one or more address spaces in CIDR notation, preferably from the private ranges ten dot zero dot zero dot zero slash eight, one seven two dot sixteen slash twelve, one nine two dot one six eight slash sixteen. You divide it into subnets. Address spaces must not overlap with other networks you plan to connect to, whether peered VNets or on premises, because overlapping ranges can't be routed."
</Person1><Person2> "What are the subnet rules?"
</Person2><Person1> "Azure reserves five addresses in every subnet: the first is the network address, the second is the default gateway, the third and fourth are for Azure DNS mapping, and the last is the broadcast address. So a slash twenty four has two hundred fifty six minus five, equals two hundred fifty one usable addresses. The smallest subnet you can create is slash twenty nine, the largest slash two. Some services need dedicated subnets with exact names: GatewaySubnet for VPN and ExpressRoute gateways, AzureBastionSubnet for Bastion with at least slash twenty six, AzureFirewallSubnet for Azure Firewall. Some use delegated subnets, like container instances on a VNet."
</Person1><Person2> "Default connectivity?"
</Person2><Person1> "Resources in a VNet can talk to each other across subnets by default, through the system route and the default NSG rules. They have outbound internet access by default, though default outbound access for new subnets is being retired in favor of explicit outbound methods, like NAT Gateway, a load balancer with outbound rules, or a public IP. Inbound from the internet requires a public IP and an NSG that allows it."
</Person1><Person2> "Now Azure DNS. Questions five, six, seven."
</Person2><Person1> "Azure DNS hosts DNS zones. There are two flavors, public and private. A public DNS zone hosts records for names resolvable on the internet, like northwind dot com. You delegate the domain from your registrar to the four Azure name servers shown in the zone. A private DNS zone hosts records resolvable only inside virtual networks that you link to the zone, like coldharbor dot net, and the zone name doesn't have to be a real internet domain."
</Person1><Person2> "What is auto registration?"
</Person2><Person1> "When you link a VNet to a private DNS zone, you can enable auto registration on that link. Then Azure automatically creates and maintains A records in the zone for the virtual machines in that VNet: coreapp1 dot coldharbor dot net pointing to the VM's private IP. It updates the record if the IP changes, and removes it when the VM is deleted. Auto registration exists only for private zones. A VNet can be linked with registration to only one private zone, but can be linked to other zones for resolution only. A zone supports up to a hundred registration links."

</Person1><Person2> "Questions eighty three to eighty five. DNS server selection."
</Person2><Person1> "Every VNet has a DNS setting: either Azure provided DNS, which uses the special virtual public IP one six eight dot sixty three dot one two nine dot sixteen, or custom DNS servers you list. </Person1><Person2> "What if a VM uses a custom DNS server and I need to resolve Azure private zone names?"
</Person2><Person1> "The custom DNS server must forward queries for those zones to Azure DNS at one six eight dot sixty three dot one two nine dot sixteen, or you use Azure DNS Private Resolver, a managed service for conditional forwarding between Azure and on premises."
</Person1><Person2> "Private endpoints and DNS."
</Person2><Person1> "A private endpoint is a network interface in your subnet with a private IP, connected to a specific Azure service resource, like a storage account blob service or a Key Vault. The service becomes reachable at that private IP. You can disable public access on the service. The catch: the service name, like mystorage dot blob dot core dot windows dot net, must resolve to the private IP for clients in your network. With Azure, you do this by creating a private DNS zone named after the service's private link zone, like privatelink dot blob dot core dot windows dot net, and linking it to the VNet. The public DNS name then has a CNAME to the privatelink name, which your private zone answers with the private IP."
</Person1><Person2> "Connect this to questions fifty nine and sixty."
</Person2><Person1> "Carlos Vega must link private DNS zone corezone1 dot com to the virtual network NetVnet1. Roles: Network Contributor and Private DNS Zone Contributor. Scope: directly on the two resources. Think about what the operation really does. A virtual network link is a child resource of the private DNS zone, so you need write on the zone: Private DNS Zone Contributor has Microsoft dot Network slash privateDnsZones slash star. And creating the link needs permission to join the VNet, Microsoft dot Network slash virtualNetworks slash join slash action, which Network Contributor includes. Neither role alone covers both. And Contributor, assigned at the resource group, would give far more than required."
</Person1><Person2> "The scopes again?"
</Person2><Person1> "The case study says least privilege, only at the scope actually required. NetVnet1 is in CoreRG2. corezone1 dot com is in CoreRG3. If you assign at either group alone, you cover only one resource. If you assign at both groups, you cover both resources, but also everything else in those groups, which breaks least privilege. So assign each role at the actual resource: Network Contributor on NetVnet1, Private DNS Zone Contributor on corezone1 dot com."
</Person1><Person2> "Peering. What do I need to know?"
</Person2><Person1> "VNet peering connects two VNets so resources communicate over the Microsoft backbone with private IPs, with low latency and no gateway. Regional peering works within a region, global peering across regions. It's non transitive: if A peers B, and B peers C, A and C don't communicate unless you peer them directly or route through an appliance or gateway. Address spaces can't overlap. Peering is configured on both sides, and each side has its own state, Initiated, then Connected when both exist. Options per peering: allow virtual network access, allow forwarded traffic, allow gateway transit, and use remote gateways. Peering across subscriptions or tenants requires appropriate permissions, Network Contributor at least, on both VNets."
</Person1><Person2> "Hub and spoke?"
</Person2><Person1> "A hub VNet holds shared services like a firewall, a VPN gateway and Bastion, and spokes hold workloads. Spokes peer to the hub. To let spokes use the hub's gateway, enable allow gateway transit on the hub side, and use remote gateways on the spoke side. For spoke to spoke traffic, you route through the hub firewall with user defined routes, covered in the next episode."
</Person1><Person2> "Summarize."
</Person2><Person1> "Subnets reserve five addresses. Public zone, private zone. Auto registration only in private zones with private IPs. A VNet registers with at most one private zone. NIC DNS beats VNet DNS, and the operating system is irrelevant. Private endpoints need private DNS zones. Linking a private DNS zone needs Private DNS Zone Contributor on the zone and Network Contributor on the VNet, at resource scope. Peering is non transitive.
