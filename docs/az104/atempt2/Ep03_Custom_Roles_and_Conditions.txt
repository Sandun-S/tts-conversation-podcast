<Person1> "Welcome back to Study Deep Dive. Episode three: custom roles and role assignment conditions. This covers questions two, three, four, sixty seven, sixty eight, seventy six, eighty nine and ninety. These questions look intimidating, but they are the most mechanical in the exam, because they follow strict syntax rules."
</Person1><Person2> "Start with why custom roles exist."
</Person2><Person1> "Built in roles are broad. Sometimes you need exactly one capability, like restart a virtual machine and nothing else. A custom role lets you write your own permission list. You can create it in the portal by cloning a built in role, by writing JSON and running az role definition create, or with PowerShell. The JSON you saw in questions sixty seven and sixty eight is a role definition."
</Person1><Person2> "Walk me through that JSON."
</Person2><Person1> "It started with the property roleName, vmOperatorRole. Then description. Then roleType. Then assignableScopes, which held one subscription scope. Then permissions, an array with one object containing actions, notActions, dataActions, notDataActions. The actions list gave a bundle of compute and network permissions: Microsoft dot Compute slash virtualMachines slash star, availability sets, scale sets, disk read write delete, network interface star, and join actions for NSG, public IP and subnets. Deployment actions and support actions too. The dataActions list was empty."
</Person1><Person2> "Question sixty seven. Which section must you update so users can sign in to the VMs?"
</Person2><Person1> "dataActions. Signing in to a virtual machine is a data plane operation, with actions Microsoft dot Compute slash virtualMachines slash login slash action for a normal sign in, and slash loginAsAdmin slash action for an administrator sign in. They are data actions, so they go in dataActions. Not actions. The wrong options: actions is control plane only. NotActions subtracts control plane. NotDataActions subtracts data plane. RoleType merely says built in or custom. AssignableScopes restricts where you can assign the role. Remember the sentence: what it can do to the resource is actions, what it can do inside the resource is dataActions."
</Person1><Person2> "And a practical point about signing in with Entra?"
</Person2><Person1> "The VM needs the Entra login extension, AADLoginForWindows for Windows or AADSSHLoginForLinux for Linux, and a managed identity for the extension. And the user needs one of the two login roles. Contributor or Owner doesn't give login. This was the Jordan puzzle in episode two."
</Person1><Person2> "Question sixty eight, restricting the role to one resource group."
</Person2><Person1> "assignableScopes. You replace the subscription scope with the resource group scope string, slash subscriptions slash id slash resourceGroups slash rg compute ops. Then the role can be assigned only at that group or below it. Notice assignableScopes does not grant permissions. It controls where you can use the role. Also you cannot assign a custom role at a scope that is not in its assignableScopes list."
</Person1><Person2> "Can assignableScopes have many entries?"
</Person2><Person1> "Yes, a list of subscriptions, resource groups, or a management group. A custom role with a management group in assignableScopes can be assigned in all subscriptions under it, but only one management group is allowed in assignableScopes. And the portal lets you use a custom role anywhere in assignableScopes."
</Person1><Person2> "Questions eighty nine and ninety. Permissions strings."
</Person2><Person1> "Question eighty nine. A custom role must let users perform all management operations on a virtual network, least privilege. The answer was Microsoft dot Network slash virtualNetworks slash star. The star is a wildcard matching every operation under that type: read, write, delete, join, peerings, subnets and so on. The other two options, virtualNetworks slash delete, and virtualNetworks slash write, cover only one operation each. All management operations means the wildcard, but only for virtual networks, not the whole Microsoft dot Network provider, which would be too broad."
</Person1><Person2> "And ninety?"
</Person2><Person1> "View the configuration settings of a storage account. The answer was Microsoft dot Storage slash storageAccounts slash read. That gives read of the account properties, settings and networking. The wildcard storageAccounts star would include write and delete, too much. And the third option, the blob read, is a data action on blob contents, and the wrong plane, and it is about data not configuration. A neat way to remember: the last word in the action string tells you what it can do. Star is everything, read is read, write is create or update, delete is delete, and an action like listKeys slash action is a special operation."
</Person1><Person2> "How do I read an action string?"
</Person2><Person1> "Provider, then resource type path, then operation. Microsoft dot Storage is the provider. storageAccounts is the type. blobServices slash containers is a sub resource path. Then read or write or delete or action. So Microsoft dot Storage slash storageAccounts slash blobServices slash containers slash blobs slash read is the blob contents read, and it appears in dataActions in the built in Storage Blob Data Reader role."
</Person1><Person2> "What about notActions? When do I use it?"
</Person2><Person1> "To carve exceptions out of a wildcard. For example actions Microsoft dot Compute slash virtualMachines slash star, and notActions Microsoft dot Compute slash virtualMachines slash delete. Everybody gets everything on VMs except delete. But remember, notActions is not a deny. If the user has another role that grants delete, they can delete."
</Person1><Person2> "Good. Now conditions. Questions two, three and four."
</Person2><Person1> "Role assignment conditions, also called attribute based access control, add an extra if statement to a role assignment. The role assignment grants the permission only when the condition is true. They are supported for certain Azure Storage roles, and the exam question seventy six asks where: blob containers and queues. Not file shares and not tables. Memory hook: blobs and queues yes, files and tables no."
</Person1><Person2> "How is a condition written?"
</Person2><Person1> "As a boolean expression with attributes. Attributes come from the request, like the action being attempted, from the resource, like the container name or blob path or index tags, from the environment, like the network the request comes from, or from the principal, like a custom security attribute on the user. The expression combines them with AND, OR and NOT. A common pattern is: NOT the action is a blob read, OR the container name equals archive."
</Person1><Person2> "Why NOT the action OR something? That looks backwards."
</Person2><Person1> "Because of how conditions are evaluated. The role assignment includes many actions, and the condition is evaluated for each action the role covers. If the action in the request is not part of what the condition mentions, then the condition should not get in the way, which is what the first half, NOT the action is a read, does. If the action is a read, then the first half is false, and the second half must be true for the request to pass. So the whole expression means: reads are allowed only in the archive container, and other actions are unaffected."
</Person1><Person2> "A formula for decoding."
</Person2><Person1> "Take the sentence NOT A OR B, and rewrite it as: if A, then B. Say it as: when the action is A, B must hold. For any other action, no extra requirement. That rewrite solves every condition question."
</Person1><Person2> "Let's apply it. Facts again."
</Person2><Person1> "Subscription Meridian. Storage account storagenorth has container archive with file1 dot dat, and container media with file2 dot dat. Storage account storagesouth has container archive with file3 dot dat. Priya has Storage Blob Data Reader at the subscription with RuleAlpha. RuleAlpha: NOT a blob read, OR container named archive. Sam has Storage Blob Data Owner at storagenorth with RuleBeta. RuleBeta: NOT a blob write, OR blob path contains two."
</Person1><Person2> "Question two. Priya reads file2 in media."
</Person2><Person1> "Action is a read, so the first half is false. Container is media, not archive, so the second half is false. False OR false equals false. Priya cannot read it. Also, her Reader role on the subscription doesn't give data access, so nothing else saves her. False."
</Person1><Person2> "Question three. Priya reads file3."
</Person2><Person1> "The container is archive, so the second half is true. True OR anything equals true. And the scope is the subscription, which covers any storage account, including storagesouth. True. Note that the condition mentions only the container name, not the account, so any archive container qualifies."
</Person1><Person2> "Question four. Sam reads file1."
</Person2><Person1> "The action is a read, which is not a write, so the first half, NOT a write, is true. True OR anything is true. Sam's scope is storagenorth which contains file1. True. Even though file1's path doesn't contain two, it doesn't matter."
</Person1><Person2> "Make me practice with variations."
</Person2><Person1> "Sam writes file1 dot dat: write means first half false, path doesn't contain two so second half false, denied. Sam writes file2 dot dat: path contains two, allowed. Sam reads file2: read is not write, allowed. Sam deletes file1: delete is a different action from write, depending on how the condition defines write, usually a separate action, so NOT a write is true and the delete passes. Priya reads file1 in storagenorth archive: allowed. Priya writes anything: she only has a Reader role, whose data actions don't include writes, so the role itself doesn't allow it. Priya lists the containers: that's a different action than blob read, so the condition doesn't apply."
</Person1><Person2> "That last point is subtle."
</Person2><Person1> "Remember that a condition only filters the actions it lists. The role's permissions decide what the role can do at all. The condition then narrows some of them. If an action isn't in the role, the condition can't add it."
</Person1><Person2> "Other things about conditions I should know?"
</Person2><Person1> "Conditions are stored on the role assignment, not on the role definition. You can add them in the portal, with a visual editor or code editor, or by using az role assignment create with the condition and condition version parameters. The current condition version is two point zero. You can use them to scope Storage Blob Data roles by container name, blob path, blob index tags, encryption scope, or by the private endpoint, or by network. And RBAC Administrator uses delegation conditions to restrict which roles can be assigned, and to which principal types."
</Person1><Person2> "How would that look for Sam in question seventy four?"
</Person2><Person1> "Sam gets the Role Based Access Control Administrator role, with a condition that says he may add or remove role assignments only if the role definition is Contributor. Then Sam can assign Contributor and nothing else. That is the full least privilege answer, and that's why this role is narrower than User Access Administrator."
</Person1><Person2> "Quick check. What should I remember for the exam?"
</Person2><Person1> "Custom role anatomy: actions, notActions, dataActions, notDataActions, assignableScopes. Login is a dataAction. Where it can be assigned is assignableScopes. The star wildcard for all operations on a type. Read for viewing configuration. Conditions work on blobs and queues. NOT A OR B means if A, then B. A condition cannot add permissions.
