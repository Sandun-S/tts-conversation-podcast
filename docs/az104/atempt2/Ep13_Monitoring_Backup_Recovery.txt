</Person2><Person1> "Azure Monitor collects, analyzes and acts on telemetry from Azure, on premises and other clouds. Two core data stores. Metrics: numerical time series, lightweight, near real time, platform metrics collected automatically and kept ninety three days, with custom metrics too. Logs: records with different structures, stored in Log Analytics workspaces, queried with Kusto Query Language, KQL. Activity log: a subscription level log of management operations, kept ninety days, which you can export. Resource logs, also called diagnostic logs: data plane logs from a resource, not collected unless you create a diagnostic setting. Diagnostic settings route logs and metrics to a Log Analytics workspace, a storage account for archive, an event hub for streaming, or a partner solution."
</Person1><Person2> "And the agent?"
</Person2><Person1> "The Azure Monitor Agent, AMA, collects guest OS data from VMs, scale sets and Arc enabled servers, replacing the older Log Analytics agent, which is retired. Host level metrics like CPU percentage need no agent. Guest metrics like memory inside the OS, and event logs, performance counters and syslog, need the agent and a data collection rule. VM insights uses AMA to give performance and dependency maps. Application Insights monitors applications. Network Watcher monitors networks. Workbooks, dashboards and Grafana visualize. Service Health tells you about Azure incidents; Resource Health, the health of your specific resource; Advisor gives recommendations."
</Person1><Person2> "Data collection rules. Question fifty eight."
</Person2><Person1> "The case study requires CollectRule1 to collect only the Windows system events with Event ID four six four eight from two servers, Node2 and Node4. Which type of query? XPath. A data collection rule defines three things: data sources, what to collect; destinations, where to send; and data flows, connecting streams to destinations, with optional transformations. For Windows event logs, the data source has xPathQueries that filter at the source, so only matching events leave the machine. An example filter looks like System bang star, open bracket, System, open bracket, EventID equals four six four eight, close brackets. You attach the rule to machines by a data collection rule association."
</Person1><Person2> "Why not KQL?"
</Person2><Person1> "KQL is the language you use to query data already stored in Log Analytics. In a DCR, transformations also use KQL, but those are ingestion time transformations on the stream, a separate feature, and the question is about what to collect from Windows Event Logs, which is XPath. WQL is for WMI. T-SQL is for SQL databases. The memory hook: filter at the source with XPath, analyze after ingestion with KQL."
</Person1><Person2> "Twist?"
</Person2><Person1> "They could ask which language for the Log Analytics query, KQL. Or what to use to collect syslog from Linux, a syslog data source with facilities and log levels, not XPath. Or what associates the rule to the VM, a data collection rule association."
</Person1><Person2> "Alerts."
</Person2><Person1> "An alert rule monitors a condition on a scope. Types. Metric alerts on numerical thresholds, static or dynamic. Log search alerts that run a KQL query on a schedule. Activity log alerts for management events, like a VM deleted. Service Health and Resource Health alerts. When an alert fires, it triggers an action group. Alert states: new, acknowledged, closed. Alert processing rules can suppress or route alerts, for maintenance windows. An action group is a reusable list of notifications and actions: email, SMS, voice and push to the Azure app; actions like Automation runbooks, Azure Functions, Logic Apps, webhooks, Secure webhooks, Event Hubs, and ITSM connections."
</Person1><Person2> "Question eighty one."
</Person2><Person1> "Subscription1 contains VM1. You have on premises System Center Service Manager. You need Service Manager to generate an alert whenever available memory on VM1 drops below ten percent. What do you do first? Deploy the IT Service Management Connector. The ITSM connector links Azure Monitor alerts to ITSM tools like Service Manager, ServiceNow, so that alerts create work items, like incidents. Without the connector, there's nothing to deliver the alert to Service Manager. Distractors: an automation runbook performs remediation after an alert, a function app is custom logic, a notification sends email or SMS. None integrate Service Manager. Sequence: connector, then connection, then an action group with an ITSM action, then an alert rule on available memory."
</Person1><Person2> "Next, backup. The two vault types."
</Person2><Person1> "Azure Backup stores recovery data in vaults. The Recovery Services vault supports Azure VMs, SQL Server and SAP HANA databases in Azure VMs, Azure Files, and on premises machines through the MARS agent, Microsoft Azure Backup Server, or System Center DPM. It's also the vault for Azure Site Recovery. The Backup vault, the newer vault, supports Azure Disks, Azure Blobs, Azure Database for PostgreSQL, and Azure Kubernetes Service. The two are different resource types, and the workloads don't overlap. A vault must be in the same region as the resources it backs up, for VMs and Files, though blob vaulted backup follows its own rules."
</Person1><Person2> "Questions thirty six and thirty seven."
</Person2><Person1> "The subscription has VaultA, a Backup vault, and VaultB, a Recovery Services vault. Resources: VM01, Disk01, WebApp01, SQLDB01. Question thirty six: which can VaultA back up? Disk01. Azure Disk Backup uses a Backup vault. Question thirty seven: which can VaultB back up? VM01. VM backup uses a Recovery Services vault. WebApp01 and SQLDB01 have their own built in backup and point in time restore, not these vaults. The exam explained Disk01: individual disks can be backed up through Disk Backup with a Backup vault, but with a Recovery Services vault, disks are protected as part of the VM backup."
</Person1><Person2> "How does disk backup work?"
</Person2><Person1> "Azure Disk Backup takes incremental snapshots on a schedule and keeps them in a snapshot resource group in your subscription. The vault's managed identity needs permissions: Disk Backup Reader on the source disk, and Disk Snapshot Contributor on the snapshot resource group. Yes, that's the Disk Snapshot Contributor role from question ten, which shows that snapshot rights are a separate role, not part of VM Contributor."
</Person1><Person2> "How does VM backup work?"
</Person2><Person1> "You enable backup for a VM with a policy, defining the schedule and retention. The backup extension takes a snapshot, which is kept locally for fast restore for one to five days, called instant restore, then data transfers to the vault. For Windows, backups are application consistent using VSS, and for Linux, file system consistent by default, or app consistent with pre and post scripts. Restore options: create a new VM, restore disks, replace the existing disks, restore individual files by mounting a recovery point, and cross region restore with geo redundant vaults. A standard policy takes one backup per day. An enhanced policy supports multiple backups per day for supported workloads."
</Person1><Person2> "Vault features."
</Person2><Person1> "Vault storage redundancy: locally redundant, zone redundant, or geo redundant, set before you protect items, with geo redundant as the default. Cross region restore needs geo redundant storage. Soft delete keeps deleted backup data for fourteen days by default, can be extended, and is a protection against ransomware. Immutable vaults and multi user authorization with Resource Guard protect against malicious changes. Backup Center and Backup reports provide monitoring."
</Person1><Person2> "Now backup frequencies. Questions forty seven and forty eight."
</Person2><Person1> "The case study requires Azure Backup configured so data1 and docs1 are backed up as often as Azure Backup allows. data1 is a blob container. For blobs, vaulted backup supports a daily or weekly schedule. So the most frequent is daily. You answered correctly. docs1 is an Azure file share. Azure Backup for Azure Files supports up to twenty four scheduled snapshots per day, so every hour is the most frequent of the options given. You said every four hours."
</Person1><Person2> "Explain the trap."
</Person2><Person1> "You probably assumed both resources shared the same limit, or that every four hours sounded like a typical high frequency. The question's key phrase was as often as Azure Backup allows. For Files, that's up to twenty four snapshots per day, thus hourly. For blobs, daily. The two resource types are intentionally paired so you have to know each service's capability."
</Person1><Person2> "Blob backup types."
</Person2><Person1> "Operational backup for blobs is continuous, stored in the same account, using point in time restore, with soft delete, versioning and change feed, and no vault data movement. Vaulted backup copies data to a Backup vault on a schedule, protecting against account deletion. File share backup uses share snapshots stored in the storage account, with the vault holding the policy and metadata, and restore of full shares or individual items."
</Person1><Person2> "Site Recovery."
</Person2><Person1> "Azure Site Recovery replicates VMs from one Azure region to another, or from on premises to Azure, for disaster recovery. You configure replication into a Recovery Services vault in the target region, and the Mobility service extension on the VM sends changes continuously. You define recovery plans, ordered failovers with scripts, test failovers in an isolated network, and failback after the outage. Key metrics: RPO, the amount of data loss you can tolerate, and RTO, the time to restore. Backup protects against data loss and corruption with restore points. Site Recovery provides continuity with a running copy elsewhere."
</Person1><Person2> "MARS and MABS."
</Person2><Person1> "The MARS agent backs up files, folders and system state from Windows machines directly to a Recovery Services vault. Microsoft Azure Backup Server backs up on premises workloads like Hyper-V, VMware, SQL, Exchange, SharePoint, with local disk and cloud tiers."
</Person1><Person2> "Log retention numbers to remember."
</Person2><Person1> "Metrics ninety three days. Activity log ninety days. Log Analytics workspace default thirty days interactive retention, configurable up to seven hundred thirty days, with long term archive. Backup soft delete fourteen days. Key Vault soft delete seven to ninety days."

</Person2><Person1> "AMA collects guest data using data collection rules, XPath filters at collection, KQL analyzes after ingestion.
