<Person1> "Welcome back to Study Deep Dive. Episode six: managed identities, Azure Key Vault, and disk encryption. This covers questions forty one, forty two, fifty two, fifty three, and links to eighty two. These are the security building blocks that appear in nearly every real world Azure design, so we'll go deeper than the questions."
</Person1><Person2> "Start with the problem. Why do we need managed identities?"
</Person2><Person1> "Applications need to authenticate to other Azure services, like Key Vault or Storage. Traditionally you store a secret, like a password or a client secret, in a config file. Secrets leak, expire, and need rotation. A managed identity removes the secret. Azure creates an identity in Entra ID for your resource, and the resource gets tokens from a local endpoint, with no credentials in code. You then grant that identity permission on the target through RBAC or an access policy."
</Person1><Person2> "Two types."
</Person2><Person1> "System assigned. It's enabled on a resource, like a VM, app, or container app. It's tied to the resource's lifecycle, deleted with it, and one to one. User assigned. It's created as a standalone Azure resource, and you attach it to one or more resources. It outlives them, and can be shared by many. Use system assigned for a single resource with a single purpose. Use user assigned when many resources share one identity, or you need to pre create the identity and permissions before deployment."
</Person1><Person2> "How does the app get the token?"
</Person2><Person1> "Through the Instance Metadata Service for VMs, at the link local address one six nine dot two five four dot one six nine dot two five four, or through environment variables for App Service and Functions. The SDK, with something like DefaultAzureCredential, handles it. Then the token is sent to Key Vault, which checks authorization."
</Person1><Person2> "Question forty one."
</Person2><Person1> "A container app named checkout app must retrieve a secret from Azure Key Vault. What should you create so it can authenticate? A managed identity. The wrong options. A shared access signature token: SAS is a storage mechanism, Key Vault doesn't use it. A private endpoint: network connectivity, not identity. A service principal: it can work, but then you manage a secret or certificate yourself, so a managed identity is simpler and more secure. A user account: a human identity, not appropriate for app to service."
</Person1><Person2> "How do container apps use it?"
</Person2><Person1> "You enable system assigned or attach a user assigned identity to the container app. You grant it the Key Vault Secrets User role, or an access policy with get on secrets. Container Apps can also reference Key Vault secrets directly through the identity, so the secret appears as an app secret without you handling the value."
</Person1><Person2> "Question forty two. Three vaults in different regions."
</Person2><Person1> "kv primary, kv secondary, kv archive, spread across two resource groups and regions. Which can supply the secret to the app? All three. Azure doesn't restrict an app to a vault in its own region or its own resource group. Cross region and cross resource group access is allowed, provided the identity is authorized and network rules allow it. Best practice is to keep the vault in the same region for latency and resilience. The question tested whether you invent a restriction that doesn't exist. Pattern: don't add rules the platform doesn't impose."
</Person1><Person2> "Explain Key Vault more fully."
</Person2><Person1> "Key Vault stores three kinds of objects. Secrets, like passwords or connection strings. Keys, cryptographic keys such as RSA or elliptic curve, used for encrypt, decrypt, sign, wrap. Certificates, which combine a key, a secret and metadata, and support automatic renewal with integrated authorities. Tiers: Standard, with software protected keys, and Premium, with HSM protected keys. There's also Managed HSM, a separate single tenant service."
</Person1><Person2> "Authorization models."
</Person2><Person1> "Two. The older vault access policy model, where you list principals and their permissions per object type, like get and list on secrets. And the Azure RBAC model, recommended, with roles like Key Vault Administrator, Key Vault Secrets User, Key Vault Secrets Officer, Key Vault Crypto Officer, Key Vault Crypto User, Key Vault Certificates Officer, and Key Vault Reader. In RBAC mode, access policies are ignored. And management plane access to the vault itself, like creating or deleting the vault, is always RBAC. Remember again control plane versus data plane: Contributor on a vault can manage the vault but, under the access policy model, can modify access policies and so grant itself data access, which is why RBAC mode is better."
</Person1><Person2> "Protection features."
</Person2><Person1> "Soft delete is on by default, keeping deleted vaults and objects for a retention period, from seven to ninety days. Purge protection prevents anyone from purging deleted items during the retention period, and once enabled can't be turned off. Firewalls and virtual network rules restrict access, with an option to let trusted Microsoft services through. Private endpoints give a private IP. Diagnostic settings log all access to Log Analytics, which is how you audit."
</Person1><Person2> "Connect to question eighty two."
</Person2><Person1> "The scenario: ten VMs in East US, a key vault Vault1, and NSG1 that denies all outbound internet. VMs must reach Vault1, least privilege, minimal ongoing administration. What destination in the outbound rule? A service tag. A service tag is a named set of IP prefixes for an Azure service, maintained by Microsoft, so you never update IP lists. The tag is AzureKeyVault. An application security group just groups your own VMs. An IP range works but needs manual maintenance as Microsoft changes addresses, which violates minimal administration."
</Person1><Person2> "Any deeper detail?"
</Person2><Person1> "Service tags can be regional, like AzureKeyVault dot EastUS, which is tighter and so better for least privilege when all VMs are in East US. And a practical note, to use a managed identity to get a token, the VM must also reach Entra ID, so you'd also allow the AzureActiveDirectory tag outbound. And the rule priority number must be lower than the deny rule so it's evaluated first."
</Person1><Person2> "Now disk encryption. Questions fifty two and fifty three."
</Person2><Person1> "First, understand all the encryption layers for Azure disks. Server side encryption is on by default. It encrypts managed disks at rest with platform managed keys, transparent to you. You can use customer managed keys in Key Vault through a disk encryption set. Encryption at host encrypts data on the VM host, including temporary disks and caches, before it flows to storage. Azure Disk Encryption, ADE, encrypts inside the guest operating system, using BitLocker on Windows and DM Crypt on Linux, with keys in Key Vault. And Confidential disk encryption for confidential VMs."
</Person1><Person2> "Concentrate on ADE."
</Person2><Person1> "ADE uses two keys. The BitLocker encryption key, called the BEK, is a secret that actually encrypts the volumes, stored in Key Vault. Optionally a key encryption key, the KEK, which is a Key Vault key that wraps, meaning encrypts, the BEK. That's what question fifty two was about, the technical requirement of using a KEK."
</Person1><Person2> "Question fifty two."
</Person2><Person1> "Which cmdlet, and which key? The answer: Set AzVMDiskEncryptionExtension and Key1. The cmdlet that enables ADE on a VM is Set AzVMDiskEncryptionExtension, with parameters for the Key Vault URL and ID, and for the KEK, KeyEncryptionKeyUrl and KeyEncryptionKeyVaultId. The other cmdlet names in the options don't exist. Key1 was RSA with size four thousand ninety six, and Key2 was an elliptic curve key. ADE requires an RSA key for the KEK. EC isn't supported."
</Person1><Person2> "Other ADE requirements?"
</Person2><Person1> "The Key Vault must be in the same region and the same subscription as the VM, and it must have the setting enabled for disk encryption access, which lets Azure retrieve secrets. The vault needs soft delete and purge protection for the KEK use in some scenarios. The VM needs outbound access to Key Vault and Entra ID."
</Person1><Person2> "Question fifty three. Which VMs qualify?"
</Person2><Person1> "Five nodes. Node1 uses an ephemeral OS disk. Node2 Windows Server twenty twenty two with a basic volume. Node3 Ubuntu twenty two oh four LTS with standard SSDs. Node4 uses Write Accelerator disks. Node5 uses a dynamic volume. The answer: Node2 and Node3. ADE doesn't support ephemeral OS disks, Write Accelerator enabled disks, and Windows dynamic volumes. Also unsupported in general: Basic tier VMs and A series, Generation two VMs on some Linux builds, and some distributions. The explanation says Ubuntu twenty two oh four is on the supported list."
</Person1><Person2> "Memory hook?"
</Person2><Person1> "Three blockers: Ephemeral, Write Accelerator, Dynamic. E, W, D. And the KEK must be RSA."
</Person1><Person2> "How would they twist it?"
</Person2><Person1> "Make Node3 use an unsupported Linux distribution. Make Node2 use a spanned or striped dynamic disk. Make a node use an Ultra Disk, which has its own limits. Or ask for the requirement to encrypt temporary disks, where encryption at host fits better."
</Person1><Person2> "ADE versus server side encryption with customer managed keys. Which is which?"
</Person2><Person1> "Server side encryption with a customer managed key encrypts at the storage layer, with a disk encryption set referencing a key in Key Vault. ADE encrypts at the OS level inside the VM. SSE is on by default for all managed disks, ADE is optional. If the question says BitLocker or DM Crypt, it's ADE. If it says disk encryption set, it's server side with CMK. If it says temp disk and cache, it's encryption at host."
</Person1><Person2> "Quick summary."
</Person2><Person1> "Authenticate an Azure resource to another service with a managed identity, system assigned or user assigned. SAS belongs to storage. Key Vault can be used across regions and groups. Use RBAC with Key Vault Secrets User. Service tag for outbound to Azure services, with AzureActiveDirectory too. ADE needs an RSA KEK, Key Vault in the same region and subscription, and no ephemeral OS disk, no Write Accelerator, no dynamic volumes. Next episode starts the storage section: accounts, redundancy, tiers, Data Lake, blobs and replication."
