Authorization methods, shared access signatures, stored access policies, immutable storage, encryption scopes, routing preference, network access, and AzCopy. This covers questions fifty four, fifty five, sixty one, seventy, seventy five, and the background to nineteen to twenty two and seventy three."
</Person1><Person2> "Start with how clients authorize to storage."
</Person2><Person1> "Four ways. Microsoft Entra ID with RBAC, the recommended way, using data roles like Storage Blob Data Reader. Shared Key, using the account access keys, which grants full access to everything and should be avoided or disabled. Shared access signatures, which delegate limited access. And anonymous public read access for blob containers, which should be disabled unless you really need it. You can turn off Shared Key authorization on the account, forcing Entra or SAS."
</Person1><Person2> "Why are account keys so dangerous?"
</Person2><Person1> "Each account has two keys, key one and key two, with two so you can rotate without downtime. Anyone with a key has full control over all data in the account, no audit identity, no condition. That is why the Key Operator role and the listKeys action are sensitive, and why the exam asked who can list and regenerate keys. Rotation process: switch apps to key two, regenerate key one, switch back, regenerate key two."
</Person1><Person2> "Shared access signatures."
</Person2><Person1> "A SAS is a signed URI that grants specific permissions to specific resources for a limited time. It has parameters: the resource, the permissions, like read, write, list, the start and expiry time, optionally an allowed IP range and protocol, and the signature. Three types. A user delegation SAS is signed with Entra credentials, through a user delegation key, valid for blob storage and Data Lake only, and is the most secure. A service SAS is signed with the account key and gives access to one service. An account SAS is signed with the account key and can span services. A SAS can't be revoked individually, unless it's tied to a stored access policy or you rotate the signing key."
</Person1><Person2> "Stored access policies. Question fifty four."
</Person2><Person1> "A stored access policy is a named server side definition of start time, expiry and permissions, attached to a container, queue, table or file share. A service SAS references the policy by name, instead of carrying those parameters. If you change or delete the policy, every SAS that references it changes or becomes invalid. That is how you revoke access. A user delegation SAS can't use a stored access policy. The limit: up to five stored access policies per container."
</Person1><Person2> "Question fifty four."
</Person2><Person1> "Container data2 already has three policies, Policy one, two and three. How many more can you create? Five minus three is two. You said one. It is pure arithmetic, but a very easy one to miss under time pressure. Make the habit: write the maximum, subtract the existing, write the answer."
</Person1><Person2> "Immutable storage and question fifty five."
</Person2><Person1> "Immutable storage, write once read many, WORM. It protects blob data from being modified or deleted for a defined time. Two kinds of policy at the container level: a time based retention policy, with a fixed retention interval in days, minimum one day, which can be unlocked for testing or locked, and once locked can't be removed and the retention can only be extended; and a legal hold, which is a tag based hold that stays until explicitly cleared. There is also version level immutability, which applies to individual blob versions. Immutability policies are not available on archive in some cases, and they require the account to be general purpose version two or premium block blob."
</Person1><Person2> "What was the question?"
</Person2><Person1> "For data2, which already had a legal hold, what's the maximum number of additional immutable blob stored policies you can create? The exam answered one. The logic: a container can have two types, one time based retention policy and one legal hold. The legal hold uses one, so one more, the time based policy, is possible. You said five. The mistake: mixing the five of stored access policies with the two kinds of immutability. In real Azure a container can hold multiple legal hold tags, but the exam counts the policy types, and I want you to answer it the exam's way."
</Person1><Person2> "Make a mnemonic."
</Person2><Person1> "Stored access policy, five. Immutability, two kinds. Say: five for SAS, two for WORM."
</Person1><Person2> "Encryption scopes. Question sixty one."
</Person2><Person1> "By default all data in a storage account is encrypted at rest with Microsoft managed keys, using AES two fifty six, with no configuration. Encryption scopes let you manage encryption at the container or blob level within one account, with different keys for different data. Each scope can use Microsoft managed keys or customer managed keys stored in Key Vault, and can also enable infrastructure encryption, a second layer. You can set a default scope for a container so all blobs written there use it, or specify a scope per blob upload. A scope can be disabled but not deleted."
</Person1><Person2> "And the question?"
</Person2><Person1> "Which resources can be encrypted using EncScope1, a scope in datastore2? Containers and blobs in datastore2 only. Encryption scopes are a blob service feature, so no file shares, queues or tables. And a scope belongs to one storage account, so it can't be used in datastore1. Wrong options included file shares and queues, and both accounts."
</Person1><Person2> "How can I remember the encryption options for storage?"
</Person2><Person1> "Account level: platform keys by default, or customer managed keys for the whole account. Container or blob level: encryption scope. Files, tables and queues: account level keys only, though queue and table can use account scoped encryption key types set at creation. Client side encryption is separate, done by the app before upload."
</Person1><Person2> "Question seventy five, routing preference."
</Person2><Person1> "Users reach website content in a storage account. The requirement: routed through the Microsoft point of presence closest to them. The answer: routing preference. Storage accounts have a networking setting called routing preference with two options. Microsoft network routing: the traffic enters the Microsoft global network at the edge POP nearest the user, and rides the Microsoft backbone to the storage account. Internet routing: traffic travels the public internet and enters the Microsoft network near the storage region. Microsoft routing gives better latency and reliability, internet routing costs less in egress. You publish routing specific endpoints, so users can choose which path to use."
</Person1><Person2> "Why not load balancing?"
</Person2><Person1> "Load balancers distribute traffic across backend servers like VMs, and they aren't a property of a storage account. Azure Firewall filters traffic. Private endpoints give a private path but don't choose a POP. You said load balancing. The pattern: if the feature is named in the question's own words, point of presence, find the setting that literally controls it."
</Person1><Person2> "Network security for storage."
</Person2><Person1> "Firewall and virtual networks settings: allow all networks, selected networks and IPs, or disable public access. With selected networks you add virtual network rules, via service endpoints on subnets, and IP rules for public IPs. Exceptions for trusted Azure services. Then private endpoints, which assign a private IP in your VNet to a storage sub resource, blob, file, queue, table, web or dfs, and you resolve the name through a private DNS zone like privatelink dot blob dot core dot windows dot net. When you create a private endpoint you can disable public network access entirely. We'll compare service endpoints and private endpoints in the networking episodes."
</Person1><Person2> "Question seventy, AzCopy."
</Person2><Person1> "AzCopy is a command line tool for moving data to and from Azure Storage. You must create a container named vmimages before uploading an on premises VM image. The right command: azcopy make with the blob endpoint, https colon slash slash the account dot blob dot core dot windows dot net slash vmimages. Why? The make command creates a container or file share. The blob endpoint is correct for a blob container. The wrong ones: sync and copy don't create containers. Queue, table and dfs endpoints are for other services. And an endpoint named images doesn't exist. Remember the endpoints: blob, file, queue, table, dfs."
</Person1><Person2> "Authentication for AzCopy?"
</Person2><Person1> "Either azcopy login for Entra, which needs a data role like Storage Blob Data Contributor to write, or a SAS token appended to the URL. AzCopy commands: copy for uploading, downloading and server to server copying, with a recursive flag for folders; sync to make a destination match a source, one directional; make to create; list; remove; jobs to manage resumable transfers. For VM images you'd normally upload a VHD as a page blob. For huge datasets use Azure Data Box, an offline appliance, or Azure Import Export."
</Person1><Person2> "Anything from questions nineteen to twenty two worth deepening?"
</Person2><Person1> "The role matrix for storage. Reader sees everything but no data except via keys with Reader and Data Access. Storage Account Contributor manages the account, including keys. Storage Account Key Operator Service Role lists and regenerates keys only. Storage Blob Data Reader, Contributor and Owner for blob data. Storage Queue Data roles for queues. Storage File Data SMB Share roles for Azure Files over SMB. Storage Table Data roles. Owner of data role gives POSIX style ownership with Data Lake."
</Person1><Person2> "Summarize."
</Person2><Person1> "Authorization: Entra ID first, SAS second, keys last. User delegation SAS is the most secure. Stored access policies: five per container, revoke SAS by editing them. Immutability: time based retention plus legal hold, two kinds. Encryption scopes: blobs and containers, one account. Routing preference: Microsoft network versus internet routing. AzCopy make creates containers, and the blob endpoint is blob dot core dot windows dot net. Next episode starts networking: virtual networks, DNS and private DNS."
