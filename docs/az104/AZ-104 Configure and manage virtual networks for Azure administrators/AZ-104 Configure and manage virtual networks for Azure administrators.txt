</Person1><Person1> "Episode eight: Azure DNS, part one. What DNS is, how name servers work, IPv4 and IPv6, record types, record sets, what Azure DNS is and is not, its security features, and the five steps to host a public domain."
</Person1><Person2> "Start from zero. What is DNS?"
</Person2><Person1> "DNS, the Domain Name System, is a protocol in the TCP/IP standard. Its essential role is translating human readable domain names, such as www dot wideworldimports dot com, into IP addresses. IP addresses let computers and network devices identify and route requests among themselves. DNS uses a global directory hosted on servers around the world, and Microsoft is part of that network through Azure DNS. A DNS server is also called a name server."
</Person1><Person2> "What does a DNS server do?"
</Person2><Person1> "Two primary functions. One: it maintains a local cache of recently used domain names and their IP addresses. This gives a faster response to a local lookup. If it cannot find the domain, it passes the request to another DNS server, and this repeats until a match is made or the search times out. Two: it maintains the key value database of IP addresses and any host or subdomain over which the server has authority. This is often associated with mail, web and other internet domain services."
</Person1><Person2> "How does a device know which DNS server to use?"
</Person2><Person1> "To access web based resources a device must reference a DNS server. On your on premises network the DNS settings come from your server. When you connect from an external location like a hotel, the settings come from the internet service provider."
</Person1><Person2> "The lookup process."
</Person2><Person1> "Simplified. If the domain is in the short term cache, the DNS server resolves it. If not, it contacts one or more DNS servers on the web, and when a match is found it updates the local cache and resolves the request. If the domain is not found after a reasonable number of checks, it replies with a domain cannot be found error."
</Person1><Person2> "IPv4 versus IPv6."
</Person2><Person1> "Every computer or network device has an IP address, unique within your domain. IPv4 is four numbers from zero to two hundred fifty five separated by dots, for example one twenty seven dot zero dot zero dot one. It is the most commonly used today, but with the growth of IoT devices it will eventually run out. IPv6 is newer and intended to replace it: eight groups of hexadecimal numbers separated by colons. Many devices have both. DNS can resolve names to both IPv4 and IPv6 addresses."
</Person1><Person2> "Is there a record type tied to each?"
</Person2><Person1> "Yes. An A record maps a name to an IPv4 address. An AAAA record, four A's, maps a name to an IPv6 address. Remember: IPv6 is four times as long as IPv4, so four A's."
</Person1><Person2> "Now the record types in the notes."
</Person2><Person1> "Configuration for your DNS server is stored in a zone, and each entry is called a record. The four most common. A: the host record. The most common type. </Person1><Person2> "What is the problem with the apex?"
</Person2><Person1> "The scenario: the first deployment improved resiliency by adding a load balancer to distribute inbound requests across servers. You know that A records and CNAME records do not support direct connection to Azure resources like load balancers. You need to link the apex domain to a load balancer. A normal A record needs a fixed IP. And a normal CNAME cannot be placed at the zone apex. The notes say CNAME records you might need for a Traffic Manager profile or Azure CDN endpoints are not supported at the zone apex level. However, other alias records are supported at the zone apex."

Alias records provide lifecycle tracking of target resources, so changes to a target are automatically applied to the DNS zone. </Person1><Person2> "Record types that support alias?"
</Person2><Person1> "A, AAAA and CNAME. A is the IPv4 mapping, AAAA the IPv6 mapping, CNAME the alias for your domain linking to the A record. Important: even when you create an alias, the base record type must still be A, AAAA or CNAME."
</Person1><Person2> "Benefits of alias records, listed in the notes."
</Person2><Person1> "Four. One: prevents dangling DNS records. A dangling record occurs when the zone records are not up to date with changes to IP addresses, so they point to something that no longer exists. Alias records prevent dangling references by tightly coupling the lifecycle of a DNS record with an Azure resource. Two: updates the record set automatically when IP addresses change. When the underlying IP of a resource changes, the alias ensures the associated records are refreshed. Three: hosts load balanced applications at the zone apex, by allowing apex routing to Traffic Manager. Four: points the zone apex to Azure CDN endpoints, directly."
</Person1><Person2> "Memory: no dangling, auto update, apex load balancing, apex CDN."
</Person2><Person1> "Yes. And one clarifying sentence from the notes: an alias record links the zone apex to the load balancer's resource, rather than a direct IP connection. So if the IP of your load balancer changes, the apex record continues to work."

</Person1><Person1> "Episode ten: Azure Load Balancer, part one. What it is, public versus internal, the seven components, how the five tuple hash works, rules, back end pools and health probes."
</Person1><Person2> "Set the scene."
</Person2><Person1> "The notes use Adatum, a new and expanding online commerce store. It has several three tier applications on virtual machines migrated from on premises datacenters, hosted across various virtual networks. Some applications are public, others should be accessible only to users at the main office in Sydney. On premises, hardware devices did layer four load balancing across the web tier and the middle tier VMs. They also stopped sending traffic to failed VMs, and kept a client's session on one VM in the back end pool. Now in Azure you want to replicate that with a native service: Azure Load Balancer."
</Person1><Person2> "What does it do?"
</Person2><Person1> "Azure Load Balancer distributes inbound traffic across a set of VMs in a back end pool. The pool can be Azure infrastructure as a service VMs or instances in a Virtual Machine Scale Set. You configure how traffic is distributed with load balancing rules. With the default probe controlled behaviour, health probes let the load balancer stop assigning new flows to instances whose probes report them unhealthy. The objectives: learn what it is and its functionality, and decide whether it meets your needs."
</Person1><Person2> "Why load balance at all?"
</Person2><Person1> "Some applications have so much traffic that a single server cannot respond in time. Instead of continuously adding processors, disks and RAM, you distribute incoming flows across multiple back end instances. A pool of smaller computers often responds better than one bigger server. An important accuracy note from the notes: Azure Load Balancer uses hash based distribution, so it does not guarantee equal request counts, data volumes or processing load on every instance."
</Person1><Person2> "Types of load balancer."
</Person2><Person1> "Public and internal. A public load balancer load balances internet traffic to your VMs. It maps the public IP address and port of incoming traffic to the private IP address and port of the back end VMs. Example: spread incoming web requests from the internet across multiple web servers. A public load balancer can also provide outbound connections for VMs in your virtual network. An internal, or private, load balancer directs traffic to resources inside a virtual network or reached through a VPN. Its front end IP address and virtual network are never directly exposed to an internet endpoint. It is used for internal line of business applications, accessed from within Azure or from on premises, and to balance traffic from a front end web tier across a set of secondary VMs that do calculations or data processing."
</Person1><Person2> "The internal load balancer scenarios."
</Person2><Person1> "Four. Within a virtual network: from VMs in the network to a set of VMs in the same network. Cross premises: from on premises computers to VMs in the virtual network. Multi tier applications: internet facing tier balancing to back end tiers that are not internet facing. Line of business applications: on premises computers reach an internal load balancer through VPN or ExpressRoute; these computers are clients, not members of the back end pool."
</Person1><Person2> "Scale and outbound?"
</Person2><Person1> "Both types scale to millions of TCP and UDP flows. A regional public Standard Load Balancer can also provide source network address translation, SNAT, for connections initiated by its back end instances. An internal load balancer does not itself provide public internet egress. Its back end VMs need a separate explicit outbound method when they must reach public endpoints. This module covers the Standard Load Balancer, with public front ends using Standard public IP addresses."
</Person1><Person2> "Where does it operate in the OSI model?"
</Person2><Person1> "Layer four, the transport layer. It manages traffic based on source and destination address, TCP or UDP protocol, and port number. It cannot apply different rules based on content, because it does not look inside traffic. For layer seven, application layer, you need something like Application Gateway."
</Person1><Person2> "The seven components."
</Person2><Person1> "Front end IP, load balancer rules, back end pool, health probes, inbound NAT rules, high availability ports, and outbound rules. Seven. We cover the first four now and the rest next time."
</Person1><Person2> "Front end IP."
</Person2><Person1> "The address clients use to connect. It can be public or private; that choice decides the type of load balancer. It can have multiple front end IPs. Public: maps the public IP and port to the private IP and port of the VM, and maps response traffic back. Private: internal load balancer, never exposed to the internet, accessed from Azure or from on premises through VPN or ExpressRoute."
</Person1><Person2> "IPv6?"
</Person2><Person1> "Regional Standard Load Balancer supports IPv4 and IPv6. A dual stack deployment uses separate IPv4 and IPv6 front end configurations, matching back end pools and rules, and VMs with both IPv4 and IPv6 NIC configurations in a dual stack network and subnet. Load Balancer does not translate IPv6 into IPv4. Adding an IPv6 front end does not make an IPv4 only application reachable over IPv6. Confirm the application listens on the required address family and that routing, NSGs and guest firewall allow it."
</Person1><Person2> "Rules."
</Person2><Person1> "A load balancer rule defines how traffic is distributed to the back end pool. It maps a front end IP and port combination to a set of back end IP and port combinations. A very important warning in the notes: a load balancing rule distributes traffic but does not grant network access. For a public Standard Load Balancer, configure NSGs on the back end subnet or NICs to permit the required client traffic to the back end service ports, and also permit it through the VM's guest firewall. Standard is closed by default."
</Person1><Person2> "Source IP preservation?"
</Person2><Person1> "Load Balancer preserves the source IP address and source port of incoming traffic. So back end NSGs evaluate the client source, not the load balancer's address. You allow the intended client ranges and client source ports, commonly ephemeral, while restricting destination ports to the required service ports. If an upstream NAT device or proxy changes the source, the back end sees the changed source."
</Person1><Person2> "The hash."
</Person2><Person1> "By default the load balancer picks a healthy back end instance for each flow using a hash of five values: source IP, source port, destination IP, destination port and protocol, TCP or UDP. Five tuple. Session affinity is not an extra field; it selects a different distribution mode, which we cover next episode."
</Person1><Person2> "Multiple front ends and floating IP."
</Person2><Person1> "Load Balancer can balance services on multiple ports, multiple IP addresses, or both, with different rules per front end IP. Multiple front end configurations are only supported with IaaS VMs. If rules for different front end IPs reuse the same back end IP configuration, port and protocol, enable Floating IP. Floating IP preserves the front end destination IP instead of translating it to the VM's private IP. Then you must configure each back end VM's loopback interface with the front end IP, set the guest OS to accept that traffic, and the guest firewall to permit the service. Enabling the setting alone is not enough. Rules using different back end ports do not need Floating IP just because they use multiple front ends. Applications that initiate outbound connections must use the NIC's primary IP configuration, not the loopback front end IP."
</Person1><Person2> "TLS?"
</Person2><Person1> "Load Balancer passes traffic through. It does not terminate TLS or inspect HTTP paths and cookies. For an HTTPS service behind it, the back end application terminates TLS, unless you add a separate proxy."
</Person1><Person2> "Back end pool."
</Person2><Person1> "A group of VMs or Virtual Machine Scale Set instances that respond to requests. To scale cost effectively, add more instances. The load balancer updates distribution automatically as you add or remove members. After you add two VMs, they become eligible for new flows when they pass the configured health probe. Adding VMs does not move established TCP connections. Distribution and compute scaling are separate: the load balancer does not create, resize or repair VMs. For automatic capacity, configure autoscale on a scale set and associate the instances with the back end pool."
</Person1><Person2> "Constraints."
</Person2><Person1> "For the regional load balancers described here, back end VMs belong to the same virtual network. Clients can connect from other networks if private connectivity, routing and access control permit it, but peering or an on premises connection does not make machines in those networks eligible for the pool. Also, do not rely on a back end VM reaching its own application through the internal load balancer's front end. If the flow maps back to the same VM and NIC that originated it, the connection can fail. A flow mapped to a different VM may succeed, which makes the problem look intermittent."
</Person1><Person2> "Health probes."
</Person2><Person1> "A health probe checks whether a back end instance can receive new flows. You configure protocol, port, interval and threshold, and associate it with the rule. Choose a check that reflects application readiness, since a listening TCP port alone does not prove every operation works. The behaviour assumes each instance's Admin State is None, so probes control eligibility, and the default NoHealthyBackendsBehavior value of AllProbedDown, which sends no new flows to the pool when every instance is probed down. AllProbedUp changes that and can send connections to instances whose probes failed, but does not make them healthy."
</Person1><Person2> "Probe protocols."
</Person2><Person1> "TCP: attempts to establish a TCP connection to the port. HTTP or HTTPS: sends an HTTP GET to the path; the endpoint must return HTTP two hundred within the response window. Redirects and other codes are not success. HTTP probes do not support hostname based configuration. HTTPS probes do not support client certificate authentication, and certificates throughout the chain must use SHA256 or stronger. If the client facing listener cannot meet those requirements, use a separate readiness listener on a different port, restricted to platform probe sources."
</Person1><Person2> "Interval and threshold."
</Person2><Person1> "The portal defaults to a five second interval. The service documentation lists fifteen seconds for ARM templates, REST API and Azure CLI. PowerShell's New AzLoadBalancerProbeConfig requires the interval parameter explicitly. HTTP and HTTPS probes wait for the shorter of the configured interval and thirty seconds when no response arrives. The threshold controls consecutive probe outcomes, but for HTTP probes an explicit two hundred or non two hundred response immediately determines status. The threshold applies when probes time out without response. The setting name is probeThreshold, and in PowerShell it is ProbeThreshold."
</Person1><Person2> "What happens when an instance is unhealthy?"
</Person2><Person1> "New flows stop going to it. Existing traffic depends on protocol. TCP: if one instance fails and others remain healthy, established connections to that instance can continue. If all probes are down, Standard Load Balancer can preserve established TCP flows when the pool has more than one instance. But preservation does not keep connections alive after the application closes them, an idle timeout, or the VM or network becomes unavailable. UDP: existing flows move to another healthy instance; if all are unhealthy, existing UDP flows terminate. A UDP application still needs a TCP, HTTP or HTTPS probe with a listener reflecting the UDP service's health; there is no UDP probe protocol."
</Person1><Person2> "Probe source."
</Person2><Person1> "IPv4 probes originate from one six eight dot six three dot one two nine dot sixteen, represented by the AzureLoadBalancer service tag in NSGs. The default NSG rule allowing it can be overridden by higher priority rules, and the guest firewall must permit the probe port. Allowing the probe source does not allow ordinary client traffic. IPv6 probes use the link local address fe eighty colon colon one two three four colon five six seven eight colon nine abc. A dual stack deployment needs NSG and guest firewall rules for the IPv6 probe too."
</Person1><Person2> "Admin state."
</Person2><Person1> "Standard Load Balancer lets you override probe driven eligibility. Set Admin State to Down to stop new connections to an instance during planned maintenance. Established TCP connections can continue, so let them finish before stopping the VM. Set it back to None to restore probe control. Setting it to Up makes the instance eligible even if its probe fails, so never use Up to hide an unhealthy application. The override applies to that instance in that pool and all probed rules using the pool; it does not affect other pools and does not control inbound NAT rules."
</Person1><Person2> "Recap."
</Person2><Person1> "Seven components: front end, rules, back end pool, probes, inbound NAT, HA ports, outbound rules. Layer four, pass through, five tuple hash. Rules distribute but do not grant access, so open NSGs. Probe source is one six eight dot six three dot one two nine dot sixteen, allow it with the AzureLoadBalancer tag. UDP needs a TCP or HTTP probe."
</Person1><Person1> "Episode eleven: Azure Load Balancer, part two. Session persistence, idle timeout and TCP reset, high availability ports, inbound NAT rules, outbound rules and SNAT, monitoring, when to use it and when not, global tier, DDoS, and SLA."
</Person1><Person2> "Session persistence first."
</Person2><Person1> "Load Balancer distributes flows, not individual application requests. With the default five tuple hash, traffic within a TCP connection stays on its chosen instance, but a new connection from the same client can go to another healthy instance. Session persistence, also called source IP affinity, changes the values used for selection. Three modes. None, the default: source IP, source port, destination IP, destination port and protocol. Client IP, a two tuple: source IP and destination IP. Client IP and protocol, a three tuple: source IP, destination IP and protocol."
</Person1><Person2> "What is the catch?"
</Person2><Person1> "Affinity directs connections with the same selected tuple to the same instance while back end membership and health stay unchanged. Clients behind a shared NAT address or proxy appear to have the same source IP, which can concentrate traffic on one instance. And it is not a guarantee: pool changes or an unhealthy instance can change where new connections go. Load Balancer does not store or replicate session data, so applications must handle reconnection and shared state."
</Person1><Person2> "Idle timeout."
</Person2><Person1> "Ordinary TCP load balancing rules and inbound NAT rules have a default idle timeout of four minutes, configurable from four to one hundred minutes. For inbound connections, a front end IP idle timeout setting takes precedence over the rule setting. Outbound rules have their own timeout: four minutes default, range four to one hundred twenty. Without TCP reset, Load Balancer silently drops a flow that reaches its idle timeout. Enabling TCP reset on a supported rule sends reset packets to both endpoints when the timeout expires, so they can close and reconnect. To keep an idle connection open use keepalives at an interval shorter than the timeout. Session persistence and successful health probes do not keep an idle connection alive. These settings do not apply to UDP rules."
</Person1><Person2> "High availability ports."
</Person2><Person1> "A rule with protocol all and port zero is a high availability port rule. A single rule balances all TCP and UDP flows on all ports of an internal Standard Load Balancer. The decision is per flow, on the five tuple. HA ports help with critical scenarios like high availability and scale for network virtual appliances inside virtual networks, and when a large number of ports must be balanced."
</Person1><Person2> "Flow symmetry."
</Person2><Person1> "Stateful NVAs may need both directions of a connection through the same appliance instance, called flow symmetry. HA ports support it in supported designs with a single internal load balancer and single back end pool, with the right NIC and IP configuration. They do not guarantee symmetry across separate load balancers, multiple front ends or multiple pools. Confirm with the vendor. For NVAs on traffic arriving at or leaving a public endpoint, consider Gateway Load Balancer, which can chain to a Standard public load balancer and keep both directions on the same appliance path. It complements the application load balancer. It is not a general purpose next hop for user defined routes and does not combine with the Global tier. Internal HA ports remain appropriate for internal NVA scenarios."
</Person1><Person2> "Inbound NAT rules."
</Person2><Person1> "An inbound NAT rule forwards a front end IP and port to a specific VM and back end port. For example a dedicated front end port mapped to TCP three three eight nine, RDP, on one VM. It is port forwarding, not distribution across the pool. For multiple VMs or scale set instances, inbound NAT rules version two target a back end pool and allocate per instance front end port mappings from a configured range. Use a NIC based back end pool. Size the port range for the number of instances, because insufficient mappings can block scale out. Inbound NAT rules do not need a health probe and do not configure outbound SNAT. The pool can identify instances by network interface configurations or IP addresses; the notes' example uses NIC based membership and should not be generalised."
</Person1><Person2> "Security warning."
</Person2><Person1> "Prefer Azure Bastion or private RDP and SSH instead of exposing management ports publicly. If you use public inbound NAT for management, restrict source addresses and back end management ports through NSGs and guest firewalls. The NAT mapping provides no authentication or authorization."
</Person1><Person2> "Outbound rules."
</Person2><Person1> "An outbound rule on a regional public Standard Load Balancer configures SNAT for connections initiated by back end instances, using the front end public IPs so they can reach the internet. Choose an explicit outbound method. Azure NAT Gateway is recommended for most scenarios and can provide subnet level egress while Load Balancer handles inbound. Outbound rules remain an option when you want outbound connections to use the load balancer's front end IPs. Plan SNAT port allocation because exhausted ports prevent new outbound connections."
</Person1><Person2> "Port allocation."
</Person2><Person1> "An explicit outbound rule can still use default port allocation. For production, choose manual SNAT port allocation. For a scale set, size it for the maximum planned instances, not the current count, or scale out can be blocked or new instances lack ports. Review front end public IP capacity and monitor Used SNAT Ports, Allocated SNAT Ports and failed SNAT connections. Manual allocation still needs capacity planning."
</Person1><Person2> "Default outbound access."
</Person2><Person1> "Important and current: private subnets do not provide default outbound access. For API versions released after March thirty first, twenty twenty six, subnets in new virtual networks default to private, and the portal already uses this default. Existing virtual networks are not automatically converted. Configure an explicit outbound method rather than relying on an implicit outbound IP."
</Person1><Person2> "Details of the outbound example."
</Person2><Person1> "It assumes NIC based pool members with primary IPv4 configurations and no instance level public IPs. If an outbound rule shares a front end with a load balancing rule, disable automatic outbound SNAT on that load balancing rule. A NAT gateway on the subnet takes precedence for new outbound connections. Custom routes to an NVA or virtual network gateway can send traffic through another egress path. IP based pools have different default outbound behaviour."
</Person1><Person2> "NAT gateway SKUs."
</Person2><Person1> "Choose egress separately from the load balancer's front end zone configuration. Standard NAT Gateway provides IPv4 egress from one availability zone. StandardV2 NAT Gateway is zone redundant and supports IPv4 and IPv6, but needs StandardV2 public IPs or prefixes, separate from the Standard public IPs used by Standard Load Balancer. As of November twenty twenty six, Microsoft documents that associating a StandardV2 NAT gateway with a subnet disrupts IPv6 outbound connections that use Load Balancer outbound rules. For that dual stack combination use Load Balancer outbound rules for both families, or Standard NAT Gateway for IPv4 with Load Balancer outbound rules for IPv6. Adding StandardV2 NAT Gateway can also interrupt existing outbound connections, so plan the change."
</Person1><Person2> "Monitoring."
</Person2><Person1> "Use Azure Monitor. Health Probe Status reflects the load balancer's view of instance eligibility and includes administrative state overrides. It is not independent proof the application answered. In the portal open Load balancing rules and inspect Health status details to distinguish probe success from an administrative override or an all back ends down policy. Data Path Availability measures the load balancer data path, not application health. For SNAT, compare Used and Allocated SNAT Ports and review SNAT Connection Count for failures."
</Person1><Person2> "Logs."
</Person2><Person1> "Configure a diagnostic setting to collect the LoadBalancerHealthEvent log category into a Log Analytics workspace. Events identify no healthy back ends, high SNAT port usage, SNAT exhaustion and data path problems. Query the ALBHealthEvent table and configure log alerts. These are not HTTP access logs or records of every connection, delivery can be delayed, an empty log is not proof of health, and ingestion and retention cost money."
</Person1><Person2> "Testing."
</Person2><Person1> "Test the application's protocol and front end port from an allowed client that is not a member of the back end pool. For an internal load balancer that client needs private connectivity and a route. A healthy probe does not prove the client's traffic passes its own NSG, firewall and routing. Public front end ping tests reachability of the load balancer itself, not an end to end exchange, because Load Balancer answers the ICMP rather than forwarding it. That is separate from ICMP forwarding in an internal Standard Load Balancer with an HA ports rule."
</Person1><Person2> "When should I use it?"
</Person2><Person1> "Best for applications needing ultra low latency and high performance, and when you replace hardware layer four load balancers. It replicates health probes that stop new flows to unhealthy nodes, and source IP affinity. A caution: matching the OSI layer does not mean identical packet support. Load balancing rules do not forward fragmented IP packets, including fragmented TCP and UDP; HA ports have the same limitation. Check packet size and path MTU needs before migrating. Use public load balancers for web tier front ends and internal ones between web tier and processing tier. Prefer Bastion or private connectivity for administration."
</Person1><Person2> "When not?"
</Person2><Person1> "For a low traffic web app on a single IaaS VM, it is usually unnecessary unless you need a port mapping or outbound rules. It does not make a single VM redundant. For outbound only needs prefer NAT Gateway. Alternatives: Front Door Standard or Premium, global HTTP and HTTPS delivery with acceleration, caching, TLS termination and application layer routing, WAF depending on tier. Traffic Manager, DNS based, does not proxy traffic, failover depends partly on DNS caching and client behaviour. Application Gateway Standard v2 or WAF v2, regional HTTP aware routing and TLS termination, also TCP and TLS proxying. Unlike pass through Load Balancer it terminates the client connection and opens a separate one to the back end. Choose WAF v2 for WAF; WAF does not inspect TCP or TLS listeners, and the TCP and TLS proxy does not support UDP."
</Person1><Person2> "Zones."
</Person2><Person1> "Load Balancer supports zone redundant front ends in regions with availability zones. Distribute back end instances across zones with enough capacity after a failure. It does not provide a WAF. A public load balancer inherits the zone configuration of its front end public IP. An internal one has zone configuration on its private front end. Zonal is possible too. A zone redundant front end does not keep the app available if all back end instances in the failed zone are down."
</Person1><Person2> "DDoS."
</Person2><Person1> "Azure gives infrastructure level DDoS protection for public IPs at no extra cost. For internet facing workloads evaluate DDoS Network Protection or DDoS IP Protection for enhanced protection of eligible public IPs, including a public load balancer's front end. They add workload tuned mitigation and monitoring at extra cost, complementing NSGs and WAF. Load balancing and zone redundancy do not replace a DDoS strategy."
</Person1><Person2> "SLA and cost."
</Person2><Person1> "The Load Balancer SLA requires at least two healthy VMs as back end instances. It does not guarantee application availability, and the documented SLA excludes downtime from SNAT port exhaustion or NSGs that block traffic. Pricing depends on configured rules and processed data; public IP charges are separate."
</Person1><Person2> "Global tier."
</Person2><Person1> "Use a regional Standard Load Balancer to distribute to VMs or scale set instances in a virtual network. For global layer four distribution, Standard Load Balancer has a Global tier. Its public front end distributes traffic to regional public Standard load balancers. The Global tier has no internal front end, and its back end pool does not accept internal load balancers. It does not replace Front Door or Application Gateway features. A Global tier load balancer and its global public IP must be created in a supported home region. The home region is only the deployment location. Regional back ends can be in any public region; participating regions advertise the global front end address. As of November twenty twenty six, Australia East and Southeast are participating but not home regions, so confirm the current home region list."

</Person2><Person1> "Persistence uses two or three tuple hashes but is not a guarantee; idle timeout four minutes, TCP reset helps; HA ports equals protocol all port zero for NVAs; inbound NAT is port forwarding; outbound needs explicit method, NAT Gateway preferred; Load Balancer is layer four pass through, no WAF, no TLS termination."

</Person2><Person1> "Adatum again, selling industrial drones. Web applications hosted in the on premises datacenter. An aging hardware device on the perimeter network manages traffic to them. You want to retire it and have an Azure service mediate traffic, with a private network connection between Azure and the datacenter. The replacement must do four things: detect when an on premises server is unavailable so traffic is not sent to it; TLS termination to offload back end encryption and decryption when forwarding over unencrypted HTTP, noting that with end to end TLS back end servers still do TLS processing; cookie based session affinity; and security filtering of malicious requests like SQL injection and cross site scripting, using WAF v2 with an enabled policy in Prevention mode."
</Person1><Person2> "So what is Application Gateway?"
</Person2><Person1> "A service that manages requests from client applications to web apps hosted on a pool of web servers. The pool can be Azure VMs, Virtual Machine Scale Sets, Azure App Service and even on premises servers. It load balances HTTP traffic and provides WAF protection when configured with WAF v2 and an enabled WAF policy. A listener using HTTPS encrypts traffic between users and the gateway. HTTPS in the back end HTTP settings encrypts traffic between the gateway and application servers."
</Person1><Person2> "Version warning."
</Person2><Person1> "The module covers Standard v2 and WAF v2. Application Gateway v1, Standard and WAF SKUs, retired on April twenty eighth, twenty twenty six and is no longer supported. Migrate remaining v1. The separate Basic SKU is a preview offering with a different feature set."
</Person1><Person2> "Features."
</Person2><Person1> "Requests are normally distributed among healthy servers in the selected pool using round robin. With cookie based affinity enabled, later requests returning the gateway's cookie can go to the same healthy server. That helps apps keeping local session state but does not replicate state or guarantee a transaction survives a back end failure. Features: HTTP and HTTPS, client facing HTTP two over HTTPS, and WebSocket. WAF with WAF v2 and an enabled policy; Detection mode logs rule matches without blocking, Prevention mode blocks according to rules and anomaly scoring; Standard v2 does not inspect. End to end TLS. Autoscaling. Connection draining, supporting planned removal of back end servers by stopping new requests and allowing existing connections to finish within a timeout, with an exception for requests bound by gateway managed affinity. And a TCP and TLS proxy for other workloads, though this module focuses on layer seven."
</Person1><Person2> "Components."
</Person2><Person1> "Front end IP addresses: clients connect through them. v2 supports public only, private only or combined. The limit is one public and one private address per IP family. IPv4 only can have two; dual stack up to four: public and private IPv4, public and private IPv6. IPv6 requires a dual stack gateway and virtual network; IPv6 only gateways and IPv6 back end targets are not supported; an existing IPv4 gateway cannot be converted in place. Private only v2 deployment has network isolation registration and subnet delegation requirements."
</Person1><Person2> "Listeners."
</Person2><Person1> "A listener accepts connections that match its front end IP, port and protocol. A Basic listener accepts requests without filtering by hostname. A Multi site listener also matches one or more hostnames. An HTTPS listener uses a TLS certificate to secure the client connection."
</Person1><Person2> "Routing rules."
</Person2><Person1> "A request routing rule connects a listener to back end targets and back end HTTP settings. A basic rule sends requests to one pool. A path based rule selects a pool by URL path, with a default target when no path matches. Back end HTTP settings control the back end protocol, port, cookie affinity, connection draining, request timeout and probe association."
</Person1><Person2> "How does it differ from Load Balancer?"
</Person2><Person1> "For HTTP, Application Gateway picks a pool using layer seven information such as hostname and URL path, then distributes with round robin across healthy servers. Load Balancer is layer four, using the five tuple hash by default. So: Application Gateway understands web requests; Load Balancer understands connections."
</Person1><Person2> "WAF in detail."
</Person2><Person1> "WAF inspects HTTP requests before forwarding. The listener accepts the connection first; for HTTPS the gateway terminates TLS so WAF can inspect the decrypted request. Rules detect threats such as SQL injection and cross site scripting. For a new deployment use WAF v2 with an enabled policy associated with the gateway, listener or path. Managed rule sets are updated as threats evolve. Microsoft Default Rule Sets combine OWASP Core Rule Set protections with additional Microsoft protections. Microsoft currently recommends DRS two point two, based on OWASP CRS three point three point four. You can configure exclusions and rule overrides to reduce false positives, and body inspection and size limits. Recommended rule sets and creation defaults are not necessarily the same, so explicitly select and verify type and version, and review rules before upgrading."
</Person1><Person2> "Back end pools."
</Person2><Person1> "A collection of web servers: a fixed set of VMs, a scale set, an App Service app, or on premises servers. The gateway itself distributes among healthy servers, and a pool does not need a separate Azure Load Balancer. Configure targets as IP addresses or fully qualified domain names that can serve requests under the associated HTTP settings. To encrypt to the back end, choose HTTPS in the back end HTTP settings. The back end presents its server certificate in the handshake. v2 normally validates publicly trusted certificates with its built in trusted root store. For private CA or self signed, configure the trusted root certificate in the HTTP settings."
</Person1><Person2> "App Service back ends."
</Person2><Person1> "Configure HTTPS in the HTTP settings, normally port four four three. A normal publicly trusted App Service certificate needs no extra trusted root. Azure management of the app does not automatically enable back end HTTPS. Configure the back end hostname and TLS server name to match the app's domain and certificate. With the default azurewebsites dot net domain, use the back end target's hostname. With a custom domain, configure the domain and certificate on the back end and preserve the original hostname where possible. Do not apply hostname override indiscriminately. For HTTPS back ends configure: the protocol and port, the hostname and TLS server name, and any trusted root for private chains. Keep chain, expiry and server name validation enabled in production."
</Person1><Person2> "Routing types."
</Person2><Person1> "Hostname based listener selection and URL path routing can work together. Example: a Multi site listener selects shop dot contoso dot com, and its path rule sends images and video paths to different pools. On v2 request routing rule priority determines listener evaluation order, so give site specific rules a higher priority, meaning a lower number, than overlapping wildcard or Basic listener rules. Paths within a path rule are evaluated in listed order, so put specific paths before broad wildcards."
</Person1><Person2> "Path based."
</Person2><Person1> "Sends requests with different URL paths to different pools. For example video paths to servers optimised for streaming, image paths to servers handling image retrieval."
</Person1><Person2> "Multi site."
</Person2><Person1> "Lets more than one web application share one gateway. Configure DNS so each hostname resolves to the gateway front end: an A record for IPv4, an AAAA for IPv6 when supported, or a CNAME from a subdomain to the gateway's DNS name. A CNAME does not point to an IP and cannot be an ordinary zone apex record. Link to the DNS episodes: that is the apex problem again. Example: A records for contoso dot com and fabrikam dot com to the same public IPv4 front end, Multi site listeners for those names, rules selecting pools, and for HTTPS a certificate valid for each hostname. Useful for multitenant applications."
</Person1><Person2> "Other routing features."
</Person2><Person1> "Redirection, to another site or from HTTP to HTTPS. Rewrite HTTP headers, which carry parameters between client and server. Custom error pages with your own branding."
</Person1><Person2> "Recap."
</Person2><Person1> "Components: front end IPs, listeners, routing rules, back end HTTP settings, back end pools. Basic versus Multi site listeners. Basic versus path based rules. WAF needs WAF v2 plus an enabled policy; Detection logs, Prevention blocks. Round robin by default. Path based looks at the URL, multi site looks at the hostname."
</Person1><Person1> "Episode thirteen: Azure Application Gateway, part two. TLS termination and end to end TLS, blocking direct access, health probes, autoscaling, WebSocket and HTTP two, when to use it, when not to, and how it compares with Front Door, Traffic Manager and Load Balancer."
</Person1><Person2> "TLS termination first."
</Person2><Person1> "TLS termination at Application Gateway centralises management of the client facing certificate. If the gateway forwards to the back end over HTTP, it also removes the TLS workload from the back end, but that hop is unencrypted. For end to end TLS, use HTTPS on both the listener and the back end HTTP settings. The gateway terminates the client TLS connection, processes the decrypted request, and establishes a separate TLS connection to the back end. The back end still needs a valid server certificate and does TLS processing. Certificates authenticate the endpoints; the TLS connections use negotiated keys to protect application data."
</Person1><Person2> "Why terminate at all instead of passing through?"
</Person2><Person1> "Because the gateway must see the request to route by path or hostname and to run the WAF. A pass through device like Load Balancer cannot read an encrypted URL. Terminate, inspect, then optionally re encrypt."
</Person1><Person2> "TLS versions."
</Person2><Person1> "Application Gateway requires TLS one point two or higher. Support for TLS one point zero and one point one ended on August thirty first, twenty twenty five. Confirm clients and back ends support the required versions. Some Azure settings and API identifiers still use the legacy term SSL."
</Person1><Person2> "The request flow."
</Person2><Person1> "Client traffic arrives on a configured front end IP and port. The matching listener accepts the connection and, for HTTPS, terminates TLS. A Multi site listener also matches the requested hostname. The associated routing rule decides whether to forward to a back end target or redirect. Front end listeners commonly use ports eighty and four four three but can use other supported ports. The back end protocol and port are configured separately."
</Person1><Person2> "Bypass risk."
</Person2><Person1> "Important warning. Application Gateway can be the public entry point, but adding it does not automatically stop clients reaching a back end directly. Configure back end network access so application traffic can arrive only through the gateway path. For private VM back ends avoid public ingress and use NSG or firewall rules. For App Service use private endpoints with suitable public access restrictions, or service endpoints with app access restrictions. Preserve access for health probes and authorised administration. Otherwise attackers bypass the gateway and the WAF."
</Person1><Person2> "Health probes."
</Person2><Person1> "They decide which back end servers can receive requests. If you do not associate a custom probe, a default probe is used: interval thirty seconds, response timeout thirty seconds, unhealthy threshold three consecutive failures. On v2 probes continue at the configured interval, so a back end is not necessarily declared unhealthy exactly thirty seconds after a failure. By default an HTTP status code from two hundred through three ninety nine is healthy. Compare with Load Balancer, which wants exactly two hundred for HTTP probes. Custom probes let you configure hostname, path, timing, unhealthy threshold and response matching. Use one when the app requires a specific hostname or health endpoint."
</Person1><Person2> "Autoscaling."
</Person2><Person1> "Standard v2 and WAF v2 adjust instance count as demand changes. Instead of a fixed instance count, configure a minimum and optionally a maximum. Choose bounds for expected demand and cost, and allow time for new instances to be provisioned."
</Person1><Person2> "WebSocket and HTTP two."
</Person2><Person1> "WebSocket is natively supported through HTTP and HTTPS listeners. A connection starts with an HTTP upgrade handshake and then carries bidirectional messages. No separate enable setting. HTTP two multiplexes streams over one connection. The gateway supports it on the client facing HTTPS connection but uses HTTP one point one to the back end. Check the gateway's HTTP two setting for client support; enabling it does not disable one point one. HTTP three over QUIC is in public preview for client connections on Basic listeners, with HTTP one point one to the back end, no SLA, not for production. Basic there refers to the listener type, not the Basic SKU."
</Person1><Person2> "When should I use it, for Adatum?"
</Person2><Person1> "Routing: traffic goes from an Azure endpoint to a back end pool of Adatum's on premises servers, provided private connectivity is configured, and probes stop sending new requests to unhealthy servers. TLS termination: offloads back end CPU work when forwarding over HTTP; with end to end TLS the back end still needs a certificate and does TLS work. WAF v2 with an enabled policy in Prevention mode: blocks SQL injection and cross site scripting before they reach back ends, but tune and test against legitimate traffic before enforcing. Cookie affinity: routes clients returning the cookie to the same healthy server, but apps with local session state still need a recovery design."
</Person1><Person2> "The on premises connectivity warning."
</Person2><Person1> "To use private on premises servers as targets, establish IP connectivity from the gateway's virtual network, for example site to site VPN or ExpressRoute. Configure routing, name resolution and firewall rules so the gateway can reach the application and its probe endpoint. Adding a private IP to a pool does not create the connection. That links to episode three on gateway transit and to the VPN and DNS episodes."
</Person1><Person2> "When not?"
</Person2><Person1> "It may be unnecessary when the hosting platform already meets traffic management and security needs and the cost and complexity are not justified. But low traffic or a single back end does not by itself rule it out: WAF, TLS termination, redirection and request rewriting are still useful without multiple servers. A gateway does not make a single back end highly available."
</Person1><Person2> "The comparison."
</Person2><Person1> "Front Door: an application delivery network offering global load balancing and site acceleration for web apps, with layer seven features such as TLS offload, path based routing, fast failover, WAF and caching. Choose it, for example, for a web app deployed across multiple Azure regions. Traffic Manager: DNS based traffic load balancer distributing traffic across global regions with high availability. Because it is DNS based it works at the domain level and cannot fail over as quickly as Front Door, due to DNS caching and systems not honouring TTLs. Standard Load Balancer: layer four for TCP and UDP. Regional deployments balance within a region; the Global tier balances across public regional load balancers. Zone redundancy depends on the front end configuration and region; back ends must also be distributed if the app must survive a zone failure."
</Person1><Person2> "A decision shortcut."
</Person2><Person1> "HTTP aware, regional, WAF, path or host routing: Application Gateway. HTTP aware, global, acceleration: Front Door. DNS based, any protocol, global, slower failover: Traffic Manager. TCP or UDP, regional, ultra low latency, pass through: Load Balancer. Global layer four: Load Balancer Global tier."
</Person1><Person2> "Another memory aid?"
</Person2><Person1> "Layers and scope. Two questions: which layer, and how wide? Layer seven regional, Application Gateway. Layer seven global, Front Door. DNS global, Traffic Manager. Layer four regional, Load Balancer. Layer four global, the Global tier."
</Person1><Person2> "Quick drill. Which Application Gateway SKU for WAF?"
</Person2><Person1> "WAF v2 with an enabled policy. Another: which mode blocks?"
</Person1><Person2> "Prevention."
</Person2><Person1> "Another: how does the gateway reach on premises back ends?"
</Person1><Person2> "Through a site to site VPN or ExpressRoute, with routing, DNS and firewall rules."
</Person2><Person1> "Another: client side HTTP two, back end?"
</Person1><Person2> "HTTP one point one."
</Person2><Person1> "Another: default probe healthy codes?"
</Person1><Person2> "Two hundred through three ninety nine."
</Person2><Person1> "Perfect. Summary: Application Gateway is layer seven, regional; routes by hostname and path; terminates TLS; supports end to end TLS; WAF v2 inspects; probes and autoscaling keep it resilient; and you must block direct access to the back ends."
</Person1><Person1> "Episode fourteen: Azure Network Watcher. The monitoring, diagnostic and traffic tools, how each one works, what it returns, and which tool to use for which problem."
</Person1><Person2> "What is it?"
</Person2><Person1> "Network Watcher lets organisations detect and monitor network performance issues for infrastructure as a service resources. The scenario is Adatum again: three tier applications migrated to VMs across multiple virtual networks, plus hybrid apps with compute tiers on premises and in the cloud. Network Watcher provides tools to monitor, diagnose, view metrics and enable or disable logs for IaaS resources such as VMs, virtual networks, application gateways and load balancers. It is not designed for PaaS monitoring or web analytics."
</Person1><Person2> "Prerequisites and objectives?"
</Person2><Person1> "Know IP addressing, subnetting, routing and NSGs, plus VPNs, ExpressRoute and peering. Objectives: learn what it is and what it provides, and determine whether it meets your needs."
</Person1><Person2> "Structure."
</Person2><Person1> "Three major sets of tools. Monitoring: topology and connection monitor. Network diagnostic: IP flow verify, NSG diagnostics, next hop, effective security rules, connection troubleshoot, packet capture, VPN troubleshoot. Traffic: flow logs and traffic analytics. So two, seven, two. Eleven tools."
</Person1><Person2> "How do I turn it on?"
</Person2><Person1> "Network Watcher becomes automatically available when you create a virtual network in an Azure region in your subscription. Search for it in the portal."
</Person1><Person2> "Topology."
</Person2><Person1> "It visualises the whole network: an interactive view of resources and their relationships across multiple subscriptions, resource groups and locations. At the start of troubleshooting it shows all the elements involved and may reveal something not apparent from resource group contents. It shows subnets, network interfaces, NSGs, load balancers, load balancer health probes, public IPs, virtual network peering, virtual network gateways, VPN gateway connections, virtual machines and scale sets. Every returned resource has Name, Id, Location and Associations. Each association has AssociationType, with valid values Contains and Associated, plus Name and ResourceId."
</Person1><Person2> "Connection monitor."
</Person2><Person1> "Unified end to end connection monitoring for Azure and hybrid. It measures latency between resources, detects changes affecting connectivity such as network configuration changes or NSG modifications, probes VMs at regular intervals to find failures, and can diagnose problems and explain why and how to fix. To use it you install monitoring agents on the monitored hosts. It uses lightweight executables to run connectivity checks in Azure or on premises. On Azure VMs install the Network Watcher Agent VM extension."
</Person1><Person2> "IP flow verify."
</Person2><Person1> "Detects traffic filtering issues at the VM level. It checks if a packet is allowed or denied to or from an IP address, IPv4 or IPv6, and tells you which security rule allowed or denied it. It uses a five tuple check: local and remote port, protocol TCP or UDP, local IP, remote IP, plus the VM and its network adapter and the direction, inbound or outbound. It runs a logical test on the rules in place. Evaluates NSG rules and any security admin rules."
</Person1><Person2> "NSG diagnostics."
</Person2><Person1> "Detects filtering issues at VM, scale set or application gateway level. It checks if a packet is allowed or denied to or from an IP address, IP prefix or service tag, tells you which rule, and lets you add a new higher priority rule to allow or deny that traffic."
</Person1><Person2> "Next hop."
</Person2><Person1> "Detects routing issues. For a VM and NIC it returns the next hop type, IP address and route table ID for a destination IP. Traffic from an IaaS VM is sent according to the effective routes of the NIC. Knowing the next hop shows whether traffic goes to the intended destination or nowhere. A bad route directing traffic to on premises or an appliance can cause connectivity problems. If the route is a user defined route, that route is returned; otherwise it returns System Route. Use next hop after you create a UDR to an NVA to confirm it takes effect."
</Person1><Person2> "Effective security rules."
</Person2><Person1> "Shows all rules applied to a network interface, the subnet it is in, and the aggregate. Since more than one NSG can apply to a resource, this tool considers all of them to explain why traffic is denied or allowed."
</Person1><Person2> "Connection troubleshoot."
</Person2><Person1> "Tests a connection from a VM, scale set, application gateway or Bastion host to a VM, FQDN, URI or IPv4 address. It gives results similar to connection monitor but at a point in time rather than over time. It checks TCP connectivity. On success it shows latency in milliseconds, the number of probe packets sent and the number of hops. On failure it shows the fault type. Six types: CPU, high CPU utilisation; Memory, high memory utilisation; GuestFirewall, a firewall outside Azure blocked it; DNSResolution, the destination could not be resolved; NetworkSecurityRule, an NSG blocked it; UserDefinedRoute, an incorrect user route in a routing table."
</Person1><Person2> "Packet capture."
</Person2><Person1> "A VM extension started remotely through Network Watcher. It records all traffic to and from a VM or scale set, saving you from running captures manually with OS or third party tools. Trigger it from the portal, PowerShell, CLI or REST. Filters use the five tuple: protocol, local IP, remote IP, local port, remote port. Data is stored on the local disk or in a storage blob."
</Person1><Person2> "VPN troubleshoot."
</Person2><Person1> "Troubleshoots virtual network gateways and connections, via portal, PowerShell, CLI or REST. It diagnoses health and returns results; it is a long running transaction, with preliminary results giving overall health. Returned values: startTime, endTime, code which is UnHealthy if there is a single diagnosis failure, results containing id as fault type, summary, detailed, and recommendedActions with actionText, actionUri and actionUriText."
</Person1><Person2> "Traffic tools."
</Person2><Person1> "Flow logs log information about your Azure IP traffic and store it in Azure storage. You can log traffic flowing through an NSG or an Azure virtual network. Traffic analytics provides rich visualisations of flow log data."
</Person1><Person2> "Scenarios."
</Person2><Person1> "Three. First, IaaS VM connectivity. Developers cannot open a remote PowerShell session to a new Windows VM from another VM on the same network. Use IP flow verify, specify the VM's IP and TCP port five nine eight six, which PowerShell uses over HTTPS, the remote IP and port, choose TCP and Check. If an NSG rule blocks, it names the rule.
