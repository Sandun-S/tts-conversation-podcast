<Person1> "Episode one of series five, the storage series. Today: what Azure Storage is, the data categories, the four data services, and storage account types. This is the foundation for every other storage topic on the AZ one oh four."
</Person1><Person2> "Start simple. What is Azure Storage?"
</Person2><Person1> "Microsoft's cloud storage solution for modern data scenarios. It offers a massively scalable object store, a file system service for the cloud, a messaging store for reliable messaging, and a NoSQL store. The notes call it an AI ready service. It is used for file shares, for working data such as websites, mobile apps and desktop apps, and by infrastructure as a service virtual machines and platform as a service cloud services."
</Person1><Person2> "How do I categorize the data?"
</Person2><Person1> "Three categories. Virtual machine data: disks and files. Disks are persistent block storage for IaaS VMs, delivered through Azure managed disks, used for database files, static website content or application code; how many data disks you can attach depends on the VM size. Files are fully managed file shares. Unstructured data: the least organized, called nonrelational, stored in Azure Blob Storage and Azure Data Lake Storage; Blob Storage is a highly scalable REST based object store, and Data Lake Storage is the Hadoop Distributed File System as a service. Structured data: relational format with a shared schema, rows, columns and keys; stored in Azure Table Storage, Azure Cosmos DB and Azure SQL Database. Tables are an autoscaling NoSQL store, Cosmos DB is a globally distributed database service, and SQL Database is a fully managed database as a service."
</Person1><Person2> "Prominent features to remember."
</Person2><Person1> "Durability and availability: redundancy protects against transient hardware failures, and replication across datacenters or regions protects against local catastrophe. Secure access: all data is encrypted, with fine grained control over who has access. Scalability: massively scalable. Manageability: Microsoft handles hardware maintenance, updates and critical issues. Accessibility: data is reachable worldwide over HTTP or HTTPS, with SDKs for dot NET, Java, Node, Python, PHP, Ruby, Go and the REST API; scripting with PowerShell or the Azure CLI; and visual tools, the Azure portal and Azure Storage Explorer."
</Person1><Person2> "The newer features in the notes."
</Person2><Person1> "Three. First, SFTP support: Blob Storage can use the SSH File Transfer Protocol so existing SFTP tools move files directly to and from blobs. It requires hierarchical namespace, which you can enable when you create the account on the Advanced tab, or later under Settings, Configuration. Second, NFS version three support for Blob Storage, so Linux clients mount a container like an NFS share, simplifying migration of Linux file workloads. Third, a portal setting called Default to Microsoft Entra authorization, which makes role based access control the default instead of shared access keys."
</Person1><Person2> "Now the four services."
</Person2><Person1> "Blob Storage: object storage for massive unstructured data. Ideal for serving images or documents to a browser, files for distributed access, streaming video and audio, backup and restore, disaster recovery and archiving, and data for analysis. Reachable by URL, REST API, PowerShell, CLI or client libraries."
</Person1><Person1> "Azure Files: highly available network file shares using SMB and NFS, readable also by REST or client libraries. Multiple VMs share the same files with read and write access. Scenarios: migrating on premises apps that use file shares, especially if you mount the share to the same drive letter; configuration files shared across VMs; shared developer tools so everybody uses the same version; diagnostic logs, metrics and crash dumps. Authentication in the basic scenario uses the storage account credentials."
</Person1><Person1> "Queue Storage: stores and retrieves messages, up to sixty four kilobytes each, with millions of messages in a queue, for asynchronous processing. Notes example: customers upload pictures; instead of making them wait for thumbnails, write a message to the queue and an Azure Function creates the thumbnails; each part scales separately."
</Person1><Person1> "Table Storage: nonrelational structured data, a key and attribute store with a schemaless design, fast and cost effective, typically cheaper than traditional SQL for similar volume. There is also the Cosmos DB Table API, which adds throughput optimized tables, global distribution and automatic secondary indexes."
</Person1><Person2> "Choosing quickly."
</Person2><Person1> "Massive unstructured data, browser serving, streaming, backup: Blob. Highly available file shares, lift and shift: Files. Backlog of messages: Queue. Structured nonrelational data: Table."
</Person1><Person2> "Now account types."
</Person2><Person1> "General purpose accounts have two basic performance levels: Standard and Premium. Standard is backed by magnetic hard disk drives, lowest cost per gigabyte, good for bulk or infrequently accessed data. Premium is backed by solid state drives with consistent low latency, good for I O intensive workloads such as databases. A critical note: you cannot convert Standard to Premium or the other way. You must create a new account and copy the data. All account types are encrypted at rest with Storage Service Encryption."
</Person1><Person2> "The table."
</Person2><Person1> "Memorize four rows. Standard general purpose version two: Blob including Data Lake, Queue, Table and Files; redundancy LRS, GRS, RA GRS, ZRS, GZRS, RA GZRS; recommended for most scenarios, including page blobs for disks. Premium block blobs: Blob only, including Data Lake; LRS and ZRS; block blobs and append blobs; high transaction rates, smaller objects, consistently low latency. Premium file shares: Azure Files only; LRS and ZRS; enterprise or high performance; the one that supports both SMB and NFS shares. Premium page blobs: page blobs only; LRS only; for operating systems, VM data disks and databases, index based and sparse structures."
</Person1><Person2> "Legacy accounts."
</Person2><Person1> "You may meet General purpose version one and legacy BlobStorage accounts. Microsoft recommends upgrading them to General purpose version two, in place, using the portal, CLI or PowerShell. Upgrading to version two is the supported direction; version two is the one that gets all the current features."
</Person1><Person2> "Trap list."
</Person2><Person1> "One: Standard and Premium are not interchangeable; create new and copy. Two: Premium file shares support SMB and NFS; the notes say it is the choice if you need both protocols across shares. Three: Premium page blobs are LRS only in the notes. Four: SFTP needs hierarchical namespace. Five: Queue messages are up to sixty four kilobytes. Six: Version two is the default recommendation. Next episode, replication."
</Person1><Person1> "Episode two. Storage replication: locally redundant, zone redundant, geo redundant, read access, and geo zone redundant. Redundancy is one of the most tested storage topics, so we go slowly."
</Person1><Person2> "Why replicate?"
</Person2><Person1> "Data in a storage account is always replicated for durability and high availability. Replication protects from planned and unplanned events: transient hardware failures, network or power outages, and massive natural disasters. You can replicate within one datacenter, across zones in a region, or across regions. Replication is what lets the account meet the Azure Storage service level agreement even through failures."
</Person1><Person2> "Locally redundant storage first."
</Person2><Person1> "LRS is the lowest cost option and the least durable. It copies the data within a single datacenter in the primary region. If a datacenter level disaster hits, such as fire or flooding, all replicas might be lost or unrecoverable. When is it fine? One: data that is easily reconstructed if lost. Two: data that constantly changes, like a live feed, where storing it is not essential. Three: when governance requires data to stay within a location."
</Person1><Person2> "Zone redundant."
</Person2><Person1> "ZRS synchronously replicates data across three storage clusters in a single region. Each cluster is physically separate and lives in its own availability zone, with separate utilities and networking. If a zone becomes unavailable you can still access and manage your data. Excellent performance and low latency. Two cautions from the notes: ZRS isn't available in all regions, and changing to ZRS from another option requires physical data movement from a single storage stamp to multiple stamps in the region."
</Person1><Person2> "Geo redundant."
</Person2><Person1> "GRS replicates data to a secondary region hundreds of miles from the primary. Designed for at least sixteen nines of durability, that is ninety nine point nine nine nine nine nine nine nine nine nine nine nine nine nine nine percent. Durable even if the primary region is completely lost. With plain GRS, the secondary data is available to read only if Microsoft initiates a failover from the primary to the secondary. With read access GRS, RA GRS, you can read from the secondary at any time, regardless of failover."
</Person1><Person2> "How does the copy actually happen?"
</Person2><Person1> "With GRS or RA GRS, an update is first committed to the primary location and replicated with LRS there, three copies. Then it is replicated asynchronously to the secondary region, where the data again uses LRS. Both regions spread replicas across separate fault domains and upgrade domains within a storage scale unit, the basic replication unit within a datacenter. Because the geo copy is asynchronous, there can be a delay, so a failover may lose very recent writes. That last sentence is from my knowledge, not the notes."
</Person1><Person2> "Geo zone redundant."
</Person2><Person1> "GZRS combines ZRS in the primary with geo replication. Data is replicated across three availability zones in the primary region and also to a secondary geographic region. Each Azure region is paired with another region in the same geography, forming a regional pair. You can keep reading and writing if a zone fails, and your data survives a full regional outage. Also sixteen nines durability, same scalability targets as the others. RA GZRS adds optional read access to the secondary. Microsoft recommends GZRS for consistency, durability, high availability, excellent performance and disaster recovery resilience, and RA GZRS when you want read access to the secondary during a regional disaster."
</Person1><Person2> "The comparison table in the notes."
</Person2><Person1> "Four failure scenarios. Node in a datacenter unavailable: every option survives it. Entire datacenter unavailable: ZRS, GRS, RA GRS, GZRS and RA GZRS survive; LRS does not. Region wide outage: GRS, RA GRS, GZRS and RA GZRS survive. Read access during a region wide outage: only RA GRS and RA GZRS. Memory trick: Z for zones, G for geo, R A for read access."
</Person1><Person2> "Quick decision guide."
</Person2><Person1> "Cheapest, nonessential data: LRS. Survive a datacenter or zone loss but stay in the region for governance: ZRS. Survive a region loss: GRS. Survive a region loss and read the secondary: RA GRS. Best overall resilience: GZRS. Best overall plus secondary reads: RA GZRS. Premium accounts only offer LRS and ZRS, as we saw last episode."
</Person1><Person2> "Exam style traps."
</Person2><Person1> "One: a requirement says data must remain readable during a regional outage; GRS is not enough, you need RA GRS or RA GZRS. Two: a requirement says survive a zone failure and a region failure; GZRS. Three: a requirement says data cannot leave the region; LRS or ZRS. Four: GRS secondary is LRS. Five: ZRS not in all regions. Six: replication is controlled by the account setting, which Azure Files also inherits. Next, endpoints, custom domains and network security."
</Person1><Person1> "Episode three. Accessing storage: endpoints, custom domains, and securing network access with firewalls, service endpoints and private endpoints."
</Person1><Person2> "How is a storage object addressed?"
</Person2><Person1> "Every object has a unique URL. The storage account name forms the subdomain, and the service specific domain completes the endpoint. For an account named mystorageaccount: blob service at mystorageaccount dot blob dot core dot windows dot net; table service at dot table dot core dot windows dot net; queue service at dot queue dot core dot windows dot net; file service at dot file dot core dot windows dot net. Append the object location to reach it: mystorageaccount dot blob dot core dot windows dot net slash mycontainer slash myblob. That implies storage account names must be globally unique, from my knowledge: three to twenty four characters, lowercase letters and numbers."
</Person1><Person2> "Custom domains."
</Person2><Person1> "You can map a custom domain such as www dot contoso dot com to the blob or web endpoint so users reach blob data through your brand. The notes cover direct mapping: you create a CNAME record from your subdomain to the storage account endpoint. Example: subdomain blobs dot contoso dot com points through a CNAME to contosoblobs dot blob dot core dot windows dot net. Note the pattern: CNAME, subdomain, not the root domain."
</Person1><Person2> "Is there anything else from my knowledge on custom domains?"
</Person2><Person1> "Yes, labelled as outside the notes. The notes only describe direct mapping. Microsoft's documentation also describes an indirect method with an asverify subdomain to avoid downtime when migrating a live domain, and a custom domain with HTTPS usually needs a content delivery network or Front Door in front. The exam leans on the CNAME direct mapping."
</Person1><Person2> "Securing endpoints: the firewall."
</Person2><Person1> "In the portal use Networking, Firewalls and virtual networks. By default a storage account accepts connections from any network. You can restrict access to selected virtual networks and subnets, and to specific public IP address ranges. Rules from the notes: you can allow one or more public IP ranges. Subnets and virtual networks must be in the same Azure region or region pair as the storage account. And test your configuration to be sure the endpoint limits access as expected."
</Person1><Person2> "Service endpoints versus private endpoints."
</Person2><Person1> "Service endpoint: the storage account remains on its public endpoint, but access is limited to specific VNets and subnets, with traffic taking the optimized Azure backbone route. Simpler configuration. The notes say use it for development scenarios or when some public internet access is acceptable. Private endpoint: gives the storage account a private IP address from your VNet, bringing the service into your network. All traffic between the VNet and storage goes over the Microsoft backbone, eliminating public internet exposure. Recommended for production workloads that need full network isolation and compliance."
</Person1><Person2> "Which for which service?"
</Person2><Person1> "A private endpoint is created per storage service, so blob, file, queue and table each need their own private endpoint, and DNS must resolve the account name to the private IP, typically with a private DNS zone. That is from my knowledge, and it ties to your networking series on Azure DNS."
</Person1><Person2> "Decision table."
</Person2><Person1> "Need public access only from certain subnets and IPs, simplest: service endpoint plus firewall. Need no public exposure, on premises access via VPN or ExpressRoute, compliance: private endpoint, and disable public network access. Both can exist, but with a private endpoint you normally block the public path."
</Person1><Person2> "Trap list."
</Person2><Person1> "One: endpoint format is account dot service dot core dot windows dot net. Two: custom domain uses CNAME. Three: subnets must be in the same region or region pair. Four: private endpoint equals private IP; service endpoint equals public endpoint with restricted access. Five: firewall rules apply to all services of the account. Six: test the endpoint after configuring. Next: blob containers, blob types and access tiers."
</Person1><Person1> "Episode four. Blob Storage fundamentals: the three resources, containers and naming, public access levels, blob types, and tools to upload."
</Person1><Person2> "Start with the hierarchy."
</Person2><Person1> "Blob stands for binary large object. Blob Storage is object storage. Three resources: the storage account, containers inside the account, and blobs inside containers. A blob cannot exist alone; it must be in a container. A container holds unlimited blobs, and an account holds unlimited containers. You must create a container before uploading. Configurable pieces: container options, blob types and upload options, access tiers, lifecycle rules, and object replication."
</Person1><Person2> "Container naming rules."
</Person2><Person1> "Unique within the storage account. Only lowercase letters, numbers and hyphens. Must begin with a letter or a number. Minimum three characters, maximum sixty three."
</Person1><Person2> "Public access level."
</Person2><Person1> "Default is private, visible only to the account owner. Three choices. Private: no anonymous access. Blob: anonymous read access for the blobs only, meaning someone must know the blob URL, and cannot list the container. Container: anonymous read and list access across the entire container including blobs. The important note: Blob and Container levels have no effect unless the storage account setting Allow Blob anonymous access is enabled. If disabled, every container stays private regardless of its own setting. Microsoft recommends leaving it disabled unless you serve public content. The exercise in the notes, a public website, requires enabling it on the account first."
</Person1><Person2> "Blob types."
</Person2><Person1> "Three. Block blobs: made of blocks assembled into a blob; the default type; for text and binary data like files, images and videos; most scenarios. Append blobs: also blocks, optimized for append operations; for logging where data keeps growing. Page blobs: up to eight terabytes, efficient for frequent random read and write; used by Azure virtual machines for operating system and data disks. After creation you cannot change a blob's type."
</Person1><Person2> "Uploading."
</Person2><Person1> "Portal for a few files: you pick the blob type, block size, the container folder, the access tier and the encryption scope. For lots of files use tools. Azure Storage Explorer: standalone app for blobs, files, queues, tables, Data Lake entities and managed disks. AzCopy: command line for Windows and Linux, copies to and from Blob Storage, across containers and across accounts. Azure Data Box Disk: Microsoft ships you solid state disks, you copy data and send them back for upload, for large datasets or network limits."
</Person1><Person2> "Pricing factors."
</Person2><Person1> "Block blob cost depends on data volume per month, number and type of operations plus data transfer, and the redundancy option. Use the Azure pricing calculator. Billing details: cooler tiers lower the per gigabyte storage price but raise access and transaction charges. Cool, Cold and Archive bill a per gigabyte data access charge on reads. Every tier has a per transaction charge that rises as the tier gets cooler. Geo replication data transfer is charged per gigabyte on geo replicated accounts. Outbound data transfer is billed per gigabyte of bandwidth. Changing the account default tier from Cool to Hot costs the equivalent of reading all the data; Hot to Cool costs the equivalent of writing all the data to Cool, on General purpose version two accounts."
</Person1><Person2> "The website exercise."
</Person2><Person1> "Scenario: public company website with images, videos, marketing literature and customer stories, global customers, low latency, document versions tracked, deleted documents quickly restorable. Skills: create a highly available storage account, allow anonymous public access, create a container for website documents, enable soft delete, and enable blob versioning. Soft delete and versioning are covered next episode."
</Person1><Person2> "Traps."
</Person2><Person1> "One: container names lowercase, three to sixty three. Two: public levels only work if the account allows anonymous access. Three: Blob level does not allow listing, Container level does. Four: block is default; page for VM disks; append for logs. Five: type is immutable. Six: AzCopy for command line bulk; Data Box Disk for offline bulk. Next: access tiers, lifecycle management and object replication."
</Person1><Person1> "Episode five. Access tiers, rehydration, lifecycle management rules, and object replication. This is where cost optimization questions come from."
</Person1><Person2> "The four tiers."
</Person2><Person1> "Hot, Cool, Cold, Archive. Hot: optimized for frequent reads and writes, actively processed data; highest storage cost, lowest access cost. Cool: infrequently accessed data kept at least thirty days; short term backup, disaster recovery sets, older media; immediately available; lower storage cost, higher access cost than Hot. Cold: infrequent access kept at least ninety days; lower storage cost and higher access cost than Cool. Archive: offline tier for data that tolerates several hours of retrieval latency; must remain at least one hundred eighty days or you pay an early deletion charge; secondary backups, raw original data, compliance records; cheapest storage, most expensive access."
</Person1><Person2> "The comparison table."
</Person2><Person1> "Availability: Hot ninety nine point nine percent, Cool ninety nine percent, Cold ninety nine percent, Archive ninety nine percent. With RA GRS reads: Hot ninety nine point nine nine, the others ninety nine point nine. Latency to first byte: milliseconds for Hot, Cool and Cold; hours for Archive. Minimum duration: none, thirty, ninety, one hundred eighty days."
</Person1><Person2> "Rehydration."
</Person2><Person1> "Archive blobs are offline; you cannot read them. To read, rehydrate to Hot, Cool or Cold. Two methods: Copy Blob, recommended, which creates a new blob in an online tier and leaves the archived one; or Set Blob Tier, which changes the tier in place. Priority: Standard, up to fifteen hours; High, within one hour for objects under ten gigabytes, at higher cost. Use High for urgent disaster recovery."
</Person1><Person2> "Account default tier versus blob tier."
</Person2><Person1> "From my knowledge, labelled as outside the notes: an account has a default access tier, Hot or Cool, that new blobs inherit. You can override per blob. Archive can only be set at the blob level, never as the account default."
</Person1><Person2> "Lifecycle management."
</Person2><Person1> "A rule based policy for General purpose version two and Premium block blob accounts; legacy Blob accounts are supported but version two is recommended. Policies transition data to cooler tiers and delete it at end of life. Capabilities: transition Hot to Cool, Hot to Cold, Hot to Archive, Cool to Cold, Cool to Archive, Cold to Archive; delete current versions, previous versions or snapshots; automatically move blobs from Cool back to Hot when accessed, which suits unpredictable access with no early deletion charges; scope the rules to the entire account, selected containers, or subsets using name prefixes or blob index tags."
</Person1><Person2> "How is a rule written?"
</Person2><Person1> "If then blocks. The If clause: more than N days ago since modification or access; the system checks whether data was accessed or modified. The Then clause: move to Cool, move to Cold, move to Archive, or delete the blob. Business scenario from the notes: active early, occasional after two weeks, rarely after a month. So Hot first, Cool after fourteen days, Archive after about thirty days. Costs fall as age rises."
</Person1><Person2> "Object replication."
</Person2><Person1> "Asynchronously copies blobs between containers per policy rules; includes blob content, metadata and versions. Requirements: versioning must be enabled on both source and destination accounts; snapshots are not replicated; supported when source and destination are in Hot, Cool or Cold, and they can differ. You create a replication policy naming the source account and destination account, containing one or more rules, each pairing a source container with a destination container and identifying which blobs to replicate. From my knowledge, labelled: change feed must be enabled on the source account as well."
</Person1><Person2> "Why use it?"
</Person2><Person1> "Lower latency: clients read from a nearby region. Compute efficiency: workloads process the same blobs in different regions. Data distribution: process in one place, replicate only results. Cost: after replication, move the copy to Archive with lifecycle rules."
</Person1><Person2> "Object replication versus geo redundancy?"
</Person2><Person1> "Geo redundancy is account wide, replica not directly writable, and secondary location is fixed to the pair. Object replication is container level, selective, the destination is a normal writable account in any region you choose, and can be a different tier. Mostly from my knowledge, but it is the exam distinction."
</Person1><Person2> "Traps."
</Person2><Person1> "One: Archive minimum one hundred eighty days; Cold ninety; Cool thirty. Two: rehydration up to fifteen hours standard, one hour high. Three: object replication needs versioning on both. Four: snapshots not replicated. Five: lifecycle filters by prefix or index tags. Six: Cool to Hot on access is a lifecycle option. Seven: Archive is offline. Next, blob data protection and Azure Files."
</Person1><Person1> "Episode six. Azure Storage security part one: strategies, authorization methods, shared access signatures and stored access policies."
</Person1><Person2> "The big picture."
</Person2><Person1> "Think defense in depth. Encryption at rest: Storage Service Encryption with two hundred fifty six bit AES encrypts everything written; decrypts on read; no extra cost, no performance hit. It includes disks encrypted with Azure Disk Encryption: BitLocker for Windows, dm crypt for Linux. Encryption in transit: set Secure transfer required so only secure connections are accepted; existing accounts should explicitly disallow T L S one point zero and one point one. Encryption models: server side with service managed keys, customer managed keys in Key Vault, customer managed keys on customer controlled hardware; or client side encryption with keys stored on premises. Authorization: Microsoft recommends Entra ID with managed identities for blob, queue and table. Role based access control scoped to the storage account. Storage Analytics logging for tracing requests, usage trends and diagnosing issues."
</Person1><Person2> "Four authorization strategies."
</Person2><Person1> "Microsoft Entra ID: fine grained RBAC for users, groups or applications; the recommended method. Shared Key: access with the account access key, primary or secondary; to force Entra authorization, disable Shared Key at the account level. Shared access signatures: delegate access to a particular resource with specific permissions for a specific time. Anonymous access: disabled by default on new accounts; keep it off for sensitive data."
</Person1><Person2> "What is a SAS?"
</Person2><Person1> "A uniform resource identifier granting restricted access rights to storage resources without exposing your account keys. Hand the URI to clients for a defined period. Typical use: services where users read and write their own data."
</Person1><Person2> "Three SAS types."
</Person2><Person1> "User delegation SAS: secured with Entra credentials plus the permissions in the SAS; supported for Blob Storage and Data Lake Storage; this is the most secure SAS. Service SAS: access to a specific resource in one storage service, for example list files or download one file. Account SAS: everything a service SAS can do plus more, across services and account level abilities, such as creating file systems. Service and account SAS are signed with the account key."
</Person1><Person2> "Stored access policy."
</Person2><Person1> "Adds control to a service SAS on the server side. You define a policy on a container, queue, table or share with start time, expiry and permissions, and SAS tokens reference it. Key benefit: you can revoke or change permissions by modifying or deleting the policy, without regenerating account keys. User delegation and account SAS do not use stored access policies; from my knowledge, only service SAS does."
</Person1><Person2> "Risk recommendations."
</Person2><Person1> "Use HTTPS always, because a SAS intercepted over HTTP can be reused. Reference stored access policies where possible. Use short expiry for ad hoc SAS. Have clients renew early so retries work if the issuing service is down. Plan start time: clock skew can cause failures for the first minutes, so set the start at least fifteen minutes in the past or omit it so it's valid immediately; skew up to fifteen minutes either way. Minimum permissions on the narrowest resource. Validate data written through a SAS before using it. Don't assume a SAS is always correct: use a middle tier service for sensitive operations, or make a container public if all blobs should be public."
</Person1><Person2> "Decode a SAS URI."
</Person2><Person1> "Parameters. Resource URI with restype service and comp properties: service level operations, get or set properties. sv: storage version. ss: services, b f means Blob and Files. st: start time in UTC, optional. se: expiry time in UTC. sr: resource, b for blob. sp: permissions, r w for read and write. sip: IP range allowed, example one sixty eight dot one dot five dot sixty to seventy. spr: protocol, https only. sig: the signature, an HMAC using SHA two fifty six, Base sixty four encoded."
</Person1><Person2> "Exam style traps."
</Person2><Person1> "One: revoke a SAS without changing keys: stored access policy. Two: most secure SAS: user delegation. Three: restrict a SAS to a client IP and HTTPS: sip and spr. Four: Shared Key disabled forces Entra. Five: SAS expiry compromised: regenerate the account key that signed it if no policy. Six: start time buffer fifteen minutes. Next: encryption keys, customer managed keys, Defender and Insights."
</Person1><Person1> "Episode seven. Security part two: encryption at rest in depth, access keys, customer managed keys, Storage Insights and Microsoft Defender for Storage."
</Person1><Person2> "Encryption basics."
</Person2><Person1> "Data is encrypted before it is written and decrypted when read, transparently. Two hundred fifty six bit AES, one of the strongest block ciphers. Enabled for all new and existing accounts and cannot be disabled. No code changes needed."
</Person1><Person2> "Access keys."
</Person2><Person1> "Creating an account generates two five hundred twelve bit access keys. They authorize via Shared Key or SAS tokens signed with the key. Two keys exist so you can rotate: switch applications to key two, regenerate key one, and so on, without interruption. Microsoft recommends storing them in Azure Key Vault and rotating regularly. Key Vault supports automatic rotation policies, for example every ninety days, or you rotate manually. After regenerating, update every app using the old key; this does not interrupt VM disk access."
</Person1><Person2> "Three key options."
</Person2><Person1> "Infrastructure encryption: double encryption, once at the service level and once at the infrastructure level, with two different algorithms and keys; can be enabled for the whole account or an encryption scope; must be chosen at creation, from my knowledge. Platform managed keys: generated, stored and managed entirely by Azure; the default; customers do not interact. Customer managed keys: keys you create, read, delete, update or administer; stored in your own key vault or hardware security module. Bring your own key means you import a key from elsewhere."
</Person1><Person2> "Customer managed key requirements."
</Person2><Person1> "Gives flexibility and control: you can create, disable, audit, rotate and define access controls. Use a new or existing vault and key. The storage account and key vault must be in the same region but may be in different subscriptions. Keys live in a customer owned Key Vault or Key Vault Managed HSM. Managed HSM provides FIPS one forty dash two Level three validation for the highest compliance. In the portal, under Encryption: choose the encryption type, Microsoft managed or customer managed, then specify the key by entering a key URI or selecting from a vault."
</Person1><Person2> "Practical needs, from my knowledge."
</Person2><Person1> "The storage account needs an identity, system assigned or user assigned managed identity, with permission to the vault, for example the Key Vault Crypto Service Encryption User role. The vault should have soft delete and purge protection on. If access to the key is lost, the storage data becomes inaccessible. Labelled as my knowledge."
</Person1><Person2> "Storage Insights."
</Person2><Person1> "A monitoring view over Azure Storage: performance, capacity and availability in one place. Detailed metrics and logs: latency, throughput, capacity use and transactions. Integrates with RBAC, Entra ID, connection strings and ACL permissions. Use it for real time monitoring and trends, alerts on anomalies, security auditing through logs, and health analysis. It is passive monitoring and history."
</Person1><Person2> "Defender for Storage."
</Person2><Person1> "Proactive threat detection. Malware scanning of blob uploads. Sensitive data threat detection: PII or credentials stored inappropriately. Activity based detection: unusual access patterns, suspicious download volume, hash reputation analysis. Complements Insights, which is reactive."
</Person1><Person2> "The lab."
</Person2><Person1> "Manage Azure Storage, about fifty minutes: create and configure a storage account, create and secure blob storage, create and secure Azure file storage using Storage Browser."
</Person1><Person2> "Traps."

</Person1><Person2> "What is Azure Files?"
</Person2><Person1> "Fully managed cloud file shares accessible over SMB, NFS and HTTP, from Windows, Linux and macOS. Characteristics: serverless, no VMs to manage; a share holds up to one hundred tebibytes and a file up to four tebibytes, with real hierarchical folders; encrypted at rest and in transit; reachable from anywhere with internet by default; identity integration with Entra identities or AD DS identities synced to Entra; snapshots integrate with Previous Versions in File Explorer, and Azure Backup is supported; redundancy follows the storage account replication setting."
</Person1><Person2> "Files versus Blob."
</Person2><Person1> "Files: SMB and NFS plus REST; true directory objects; shared across multiple VMs; lift and shift for apps using native file system APIs; dev and debugging tools shared by many VMs. Blob: REST and client libraries; flat namespace; accessed through containers; streaming and random access; application data accessed from anywhere at massive scale in block blobs."
</Person1><Person2> "Protocol rule."
</Person2><Person1> "A single share can't do both SMB and NFS, but one storage account can hold both kinds of shares. SMB uses port four hundred forty five, which many ISPs block outbound; that's the most common mount problem from on premises."
</Person1><Person2> "Tiers."
</Person2><Person1> "Premium: SSD, low latency, FileStorage account type, LRS and ZRS, provisioned billing. Transaction optimized, Hot and Cool: HDD standard, in General purpose version two accounts, all six redundancy options, pay as you go. Transaction optimized for heavy transactions, Hot for general team shares, Cool for online archive and backup. The note says SSD file shares reach single digit milliseconds. File shares without a storage account are now generally available, per the notes, for simpler management."
</Person1><Person2> "Authentication."
</Person2><Person1> "Identity based over SMB: three Active Directory sources, on premises AD DS, Microsoft Entra Domain Services, and Microsoft Entra Kerberos; then assign Azure RBAC roles. Access key: static, full control, bypasses access control, avoid sharing. SAS: dynamically generated URI based on the key, with permissions, times, IP and protocol; with Azure Files used only for REST API access from code."
</Person1><Person2> "Snapshots."
</Person2><Person1> "Incremental, read only, point in time copies at the share level, capturing only changes since the last snapshot. Same for SMB and NFS in public regions. A unique timestamp is added to the share URI. They use the share's redundancy. Up to two hundred snapshots per share. They persist until deleted, and deleting the share deletes all its snapshots. Azure Backup can lease snapshots to prevent accidental deletion. Restore a file, a folder or the whole share; full restore needs only the latest snapshot. Uses: protect against application errors and corruption, such as before a code release; accidental deletions; scheduled backup history. Automate with PowerShell or CLI, Azure Automation or GitHub Actions."
</Person1><Person2> "Soft delete."
</Person2><Person1> "Enabled at the storage account level; deleted shares go to a soft deleted state instead of being erased; retention one to three hundred sixty five days; can be enabled on new or existing shares. Uses: accidental loss, failed upgrades, ransomware recovery without paying, long term retention, business continuity."
</Person1><Person2> "Storage Explorer."
</Person2><Person1> "Standalone app for Windows, macOS and Linux managing multiple accounts and subscriptions. Needs both management layer and data layer permissions through Entra ID. Scenarios: connect to subscription; local emulator storage; attach external storage with account name and key, where the portal calls the key key one, and for national clouds choose Other and enter the endpoint domain; attach an account with a SAS; attach a single service with a SAS. Regenerate access keys regularly; two keys let you rotate with no downtime."
</Person1><Person2> "Azure File Sync."
</Person2><Person1> "Caches several Azure file shares on a Windows Server on premises or in a cloud VM, centralizing shares in Azure while keeping local performance. Five components. Storage Sync Service: top level resource, one region, up to one hundred sync groups and ninety nine registered servers. Sync group: one cloud endpoint and up to fifty server endpoints. Cloud endpoint: the Azure file share, only one per sync group. Server endpoint: an NTFS path on a registered server, not on the system volume. Azure File Sync agent: installed on each Windows Server, a background service. Access locally via SMB, NFS or FTPS. Cloud tiering keeps recently used data local and moves older data to Azure. Uses: lift and shift, branch offices, backup and disaster recovery, archiving."
