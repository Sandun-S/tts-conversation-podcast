</Person2><Person1> "A VM is not one thing. </Person2><Person1> "The network, the VM name, the location, the VM size, the disks, and the operating system. Let's go through them."
</Person1><Person2> "The network first, which is surprising."
</Person2><Person1> "The notes say the first thing to think about is not the VM at all, it is the network. Ask what the server communicates with and which ports are open. Virtual networks give private connectivity between VMs and other Azure services. VMs in the same VNet can access one another, while services outside the VNet cannot connect in by default. You can allow external access, including your on premises servers. The warning: network addresses and subnets are not trivial to change once set up, so plan topology before placing VMs, especially if you will connect to your private company network. When you set up a VNet you specify address spaces, subnets and security; connected VNets must use non overlapping ranges. You can use private ranges such as ten dot zero dot zero dot zero slash eight, one seven two dot sixteen slash twelve, or one nine two dot one six eight slash sixteen. Azure treats any range as private if it is reachable only within the VNet, interconnected VNets and your on premises location."
</Person1><Person2> "Segregation and security."
</Person2><Person1> "Break the VNet into subnets, for example ten dot one for VMs, ten dot two for back end services, ten dot three for SQL servers. And remember: Azure reserves the first four addresses and the last address of every subnet. By default there is no security boundary between subnets, so everything can talk to everything inside the VNet. Use network security groups, which act as software firewalls applying rules to each inbound or outbound request at the network interface and subnet level."
</Person1><Person2> "Now, planning each VM."

</Person1><Person2> "VM name."
</Person2><Person1> "The VM name becomes the computer name in the operating system, and it also defines an Azure resource, and it is not trivial to change later. </Person1><Person2> "Location."
</Person2><Person1> "You choose a region at creation. Place the VM near your users for performance and to meet legal, compliance or tax requirements. Two more points: the location can limit your options, since each region has different hardware and some configurations are not available everywhere; and prices differ between regions, so a flexible workload can be cheaper in another region."
</Person1><Person2> "VM size."
</Person2><Person1> "You do not choose CPU, memory and storage separately; you choose a VM size, a package. Sizes are grouped by workload. General purpose: balanced CPU to memory, for testing and development, small to medium databases, low to medium traffic web servers. Compute optimized: high CPU to memory ratio, for medium traffic web servers, network appliances, batch processes, application servers. Memory optimized: high memory to CPU, for relational databases, medium to large caches, in memory analytics. Storage optimized: high disk throughput and I O, ideal for databases. GPU: heavy graphics rendering, video editing, deep learning model training and inference. High performance compute: the fastest and most powerful CPUs, with optional high throughput network interfaces. Memory trick: balanced, CPU heavy, memory heavy, disk heavy, graphics, fastest."
</Person1><Person2> "Resizing."
</Person2><Person1> "You can change size when needs change, provided the current hardware configuration is allowed in the new size. Rules: you can resize while running, but only to sizes available in the current hardware cluster the VM runs on; the portal shows only available sizes, the command line returns an error if you pick an unavailable one. A running resize automatically reboots the machine. If you stop and deallocate the VM first, you can pick any size available in the region, because deallocation removes the VM from its cluster. The warning: resizing production VMs reboots them, which causes a temporary outage and can change settings like the IP address, for a dynamic address."
</Person1><Person2> "Billing: what do I pay for?"
</Person2><Person1> "The supporting resources have their own costs. Virtual network: per virtual network pricing. Network interface: no separate cost, but the number of NICs is limited by VM size. IP addresses: per IP pricing. NSG: no charge. Disks: the OS disk, usually one hundred twenty seven gibibytes, though smaller for some images, is charged at regular disk rates; the local temporary disk is not charged. OS license: cost varies with core count and can be reduced with the Azure Hybrid Benefit for Windows and Linux. Best practice: keep data on a separate disk, so if a VM fails you can detach the data disk and attach it to another VM."
</Person1><Person2> "Pricing model."
</Person2><Person1> "Two separate costs: compute and storage, scaled independently. Compute is priced per hour but billed per minute; a VM running for fifty five minutes is charged fifty five minutes. A stopped and deallocated VM is not charged for compute because the hardware is released. Linux is cheaper because there is no license charge; Windows includes the OS license. The notes say two payment options for compute: pay as you go, billed with no commitment, ideal for short term or unpredictable workloads, and Reserved Virtual Machine Instances, an advance purchase for one or three years in a specified region, with up to seventy two percent savings compared to pay as you go. Always use the Stop button in Azure, which deallocates."

</Person1><Person1> "Episode three. Virtual machine availability: planned and unplanned maintenance, availability sets, update domains, fault domains, availability zones, and the supporting services in the notes: load balancer, storage redundancy, Site Recovery and Azure Backup."
</Person1><Person2> "Define availability."
</Person2><Person1> "The percentage of time a service is available for use. If you expect your website to be always accessible, that is one hundred percent availability, which no one can fully guarantee, so you design for a high target, backed by service level agreements."
</Person1><Person2> "Why do VMs have availability issues?"
</Person2><Person1> "Azure VMs run on physical servers in datacenters. Physical servers fail. If the host fails, the VMs on it fail. Azure moves them automatically to a healthy host, but that self healing takes several minutes. Also, Azure itself updates the platform, from software updates to hardware upgrades. Usually the guest VMs are not impacted, but sometimes a reboot is needed."
</Person1><Person2> "Three kinds of events."
</Person2><Person1> "One: unplanned hardware maintenance. The platform predicts that hardware is about to fail and migrates your VM using Live Migration, which pauses the VM only for a short time, though performance may be reduced before or after. Two: unexpected downtime. The hardware or infrastructure fails unexpectedly, such as local network failure, local disk failure, or other rack level failures. The platform automatically heals the VM to a healthy machine in the same datacenter. During healing the VM reboots, and in some cases the temporary drive is lost. Three: planned maintenance. Periodic updates by Microsoft to the platform. The key note: Microsoft does not automatically update your VM's operating system or software; you are responsible for that; only the underlying host and hardware are patched."
</Person1><Person2> "Availability sets."
</Person2><Person1> "A logical feature to ensure a group of related VMs are deployed together so that a single point of failure does not affect all, and not all VMs are updated at the same time during host upgrades. Characteristics: VMs in a set should perform identical functions and have the same software. Azure ensures the VMs run across multiple physical servers, compute racks, storage units and network switches. If a failure occurs, only a subset is affected and the application stays up. You can create the VM and availability set together. Crucial: a VM can be added to an availability set only when the VM is created. To change it later you must delete and recreate the VM. Availability sets can be created via portal, ARM templates, scripting or API."
</Person1><Person2> "What do they not protect against?"
</Person2><Person1> "Operating system failures or application specific failures. You still need backup and disaster recovery for application level protection."
</Person1><Person2> "Design principles."
</Person2><Person1> "Redundancy: put multiple VMs in the set. Tier separation: each application tier in its own availability set, so web and SQL tiers are separate. Load balancing: use Azure Load Balancer in front, creating a load balanced availability set. Managed disks: use managed disks with VMs in availability sets."
</Person1><Person2> "Update and fault domains."
</Person2><Person1> "Every VM in an availability set is placed in one update domain and one fault domain. An update domain is a group of nodes upgraded together during a rollout. During planned maintenance, only one update domain is rebooted at a time. You can specify between one and twenty update domains when creating the set; the default is five. The update domain count cannot be changed after creation; you must delete and recreate the set. A fault domain is a group of nodes that share a physical unit of failure, think of the same physical rack sharing power and network switches. The notes' scenario: two fault domains with two VMs each; the web availability set has one VM from each fault domain; the SQL set has two other VMs, one from each. So a rack failure takes down one web VM and one SQL VM but not both of either. Typical numbers: two or three fault domains depending on the region; update domains up to twenty."
</Person1><Person2> "The memory line."
</Person2><Person1> "Update domain is for planned maintenance and reboots one at a time. Fault domain is for unplanned hardware failure, shared rack."
</Person1><Person2> "Availability zones."
</Person2><Person1> "A high availability offering that protects from datacenter failure. Zones are unique physical locations in a region, each with one or more datacenters with independent power, cooling and networking. A minimum of three separate zones in all enabled regions. Colocate compute, storage, networking and data within a zone and replicate to other zones. If you create three or more VMs across three zones, they are effectively distributed across three fault domains and three update domains, and the platform makes sure VMs in different zones are not updated at the same time."
</Person1><Person2> "Zonal versus zone redundant services."
</Person2><Person1> "From the notes: zonal services pin each resource to a specific zone, examples: Azure virtual machines and managed disks. Zone redundant services replicate automatically across all zones, examples: zone redundant Azure Storage and Azure SQL Database. Standard public IP addresses can be zone redundant, which is recommended, zonal, or non zonal. The tip: for comprehensive business continuity, combine availability zones with Azure regional pairs."
</Person1><Person2> "Quick comparison."
</Person2><Person1> "Availability set: within one datacenter, protects against rack and update issues, free to use, VMs only. Availability zone: protects against whole datacenter failure, higher SLA, VM pinned to a zone. Region pair: protects against region disaster. SLA ladder in general: single VM with premium disk, about ninety nine point nine percent; availability set, ninety nine point nine five percent; availability zones, ninety nine point nine nine percent. These figures are from my knowledge of the Azure SLA, not the notes."
</Person1><Person2> "Related services in the notes."
</Person2><Person1> "First, Scale sets, next episode. Second, load balancer: combine Azure Load Balancer with an availability zone or set for the best resiliency; it distributes traffic across multiple VMs. Third, storage redundancy: Azure Storage always keeps multiple copies. Choose based on how data is replicated in the primary region, whether replicated to a second distant region, and whether you need read access to the secondary. The options are LRS, ZRS, GRS, GZRS and read access variants; we covered them in series two."
</Person1><Person2> "Site Recovery."
</Person2><Person1> "Azure Site Recovery replicates workloads from a primary site to a secondary location, so if the primary fails you fail over, and later fail back. Business advantages: Azure as the recovery destination removes the cost of a secondary datacenter, and it is simple to test failovers without impacting production, because untested plans are not plans. Recovery plans can include custom PowerShell scripts, Automation runbooks or manual steps. It works with Azure VMs, Hyper-V, VMware and physical servers, orchestrating replication, failover and recovery for BCDR."
</Person1><Person2> "Azure Backup."
</Person2><Person1> "Backup as a service for physical or virtual machines anywhere, on premises or cloud. Scenarios: files and folders on Windows, application aware snapshots using VSS, SQL Server, SharePoint and Exchange, native Azure VMs Windows and Linux, and Linux and Windows ten client machines. Advantages: automatic storage management, pay as you use; unlimited scaling; multiple storage options, LRS or GRS; unlimited data transfer with no charge for it; encryption; application consistent backups; long term retention without limit. Components: the Azure Backup agent, System Center Data Protection Manager, Azure Backup Server, and the Azure Backup VM extension. Backups are stored in a Recovery Services vault, backed by Azure Storage blobs, and you define a backup policy: when snapshots are taken and how long they are kept."
</Person1><Person2> "The difference between Site Recovery and Backup, which is a common exam trap."
</Person2><Person1> "Site Recovery is about availability: replicating running workloads to another location so you can fail over. Backup is about data protection: restore points to recover from deletion or corruption. Disaster recovery versus point in time restore."
</Person1><Person2> "Recap."
</Person2><Person1> "Three event types: unplanned hardware maintenance with live migration, unexpected downtime with healing, planned maintenance. Availability set: set at creation only, update domains one to twenty default five, fault domains for racks. Zones: three minimum, zonal for VMs, zone redundant for storage and SQL. Site Recovery for failover, Backup for restore. Next: scaling and scale sets."
</Person1><Person1> "Episode four. Scaling virtual machines: vertical versus horizontal scaling, Virtual Machine Scale Sets, orchestration modes, spreading, and autoscale in detail."
</Person1><Person2> "Why scale at all?"
</Person2><Person1> "Usage patterns change. A robust configuration keeps throughput and responsiveness while minimizing the cost of running too many machines. The module's story: a company website that must dynamically adjust to workload and have a business continuity plan, solved with scale sets and autoscale."
</Person1><Person2> "Vertical scaling."
</Person2><Person1> "Also called scale up and scale down: change the size of the VM, making it more or less powerful. Use it when a service is under utilized, such as at weekends, to reduce monthly cost, or to support larger demand without adding VMs. Limitations: it depends on larger hardware being available, it hits an upper limit and varies by region, and it usually requires the VM to stop and restart, so there is temporary loss of access."
</Person1><Person2> "Horizontal."
</Person2><Person1> "Scale out and scale in: change the number of VM instances. More flexible; you can run potentially thousands of VMs. Generally fewer limitations than vertical scaling. Consider reprovisioning too: removing an existing VM and replacing it with a new one; a good plan accepts interruptions and decides what data must be kept and migrated to the new machine."
</Person1><Person2> "Memory trick."
</Person2><Person1> "Vertical is up and down, one bigger or smaller machine. Horizontal is out and in, more or fewer machines."
</Person1><Person2> "What is a scale set?"
</Person2><Person1> "An Azure compute resource for deploying and managing a set of identical VMs. Configure all the VMs the same way and you gain true autoscaling: instances are added as demand rises and removed as demand falls. You do not pre provision VMs. It is easier to build large scale services for compute, big data and container workloads. Adding and removing can be manual, automated or both. There is no cost for the scale set itself; you pay for each VM instance."
</Person1><Person2> "Traffic distribution."
</Person2><Person1> "Scale sets work with Azure Load Balancer for basic layer four traffic distribution and with Azure Application Gateway for advanced layer seven distribution and TLS termination. Instances can be spread across multiple availability zones, a single zone, or regionally, and zone options may differ by orchestration mode."
</Person1><Person2> "Orchestration modes."
</Person2><Person1> "Two. Uniform: all instances are created from the same base image and configuration. Flexible: VMs can use different images, sizes or configurations in the same set. The mode must be chosen when the scale set is created. In the notes, Flexible is the default and recommended for new deployments; accept it unless you specifically need identical instances. Older material said Uniform was default, so note the change."
</Person1><Person2> "Portal settings."
</Person2><Person1> "Orchestration mode, image, VM architecture, size, and on the Advanced tab the spreading algorithm. Architecture: x sixty four or Arm sixty four. Arm sixty four VMs can give up to fifty percent better price performance than comparable x sixty four, but x sixty four has the most software compatibility. You also choose options like Azure Spot instances, managed disks and allocation policies."
</Person1><Person2> "Spreading algorithm."
</Person2><Person1> "It determines how VMs are balanced across fault domains. Max spreading: VMs spread across as many fault domains as possible in each zone. Fixed spreading: always exactly five fault domains. If fewer than five fault domains are available, a scale set with max spreading completes, while one with fixed spreading fails. So Microsoft recommends max spreading."
</Person1><Person2> "Scaling modes."
</Person2><Person1> "When creating a scale set, choose manual or autoscaling. Manual: you maintain a fixed instance count, set from zero to one thousand, and configure the scale in policy, which is the order instances are selected for deletion, for example balance across zones then delete the VM with the highest instance ID. Autoscaling: based on a CPU metric or a schedule."
</Person1><Person2> "Autoscale configuration."
</Person2><Person1> "Autoscale is based on a scaling condition. Settings: default instance count, the initial number of VMs, zero to one thousand; instance limits, the minimum to scale down to and the maximum to scale up to; scale out, the CPU threshold percentage that triggers it and the number of instances to add; scale in, the CPU threshold that triggers removal and the number to remove; query duration, the time the engine looks back for the average of the metric, to let the metric stabilize; and schedule, with start and end dates, optionally repeated on certain days. The notes' illustration: minimum two, maximum five."
</Person1><Person2> "Why define both scale out and scale in?"
</Person2><Person1> "Without a scale out rule, performance degrades under load. Without a scale in rule, you pay for idle instances. Always create a pair. Also the default instance count is used when metrics are unavailable, so choose a safe default. Keep minimum and maximum different with an adequate margin."
</Person1><Person2> "Benefits of autoscale."
</Person2><Person1> "Automatic adjusted capacity based on defined performance thresholds; scale out if load is consistent, not a brief spike; scale in when demand is consistently low, saving cost; scheduled events at fixed times, like business hours; reduced management overhead."
</Person1><Person2> "Compare with App Service autoscale."
</Person2><Person1> "Same principles: rules and schedules, minimum, maximum, default, scale out and in pair. The difference: scale sets scale VM instances; App Service plans scale the plan's instances, which we cover in the next episodes."
</Person1><Person2> "Typical exam trap."
</Person2><Person1> "A question says: a scale set must automatically add instances when average CPU exceeds seventy five percent for ten minutes, and remove when below twenty five percent. Answer: autoscale with a CPU metric rule for scale out and one for scale in, with a ten minute duration. Another: VMs with different sizes in the same scale set. Answer: Flexible orchestration mode. Another: Which spreading algorithm tolerates regions with fewer than five fault domains? Max spreading."
</Person1><Person2> "Recap."
</Person2><Person1> "Vertical equals resize, may stop and restart. Horizontal equals instance count. Scale set: identical VMs, Flexible default, no charge for the set. Autoscale: default, minimum, maximum, scale out and in rules, query duration, schedule. Max spreading recommended. Next: App Service plans."
</Person1><Person1> "Episode five. Azure App Service plans: what a plan is, pricing tiers, how apps run and scale, scale up versus scale out, rule based autoscale, and automatic scaling. This links directly to a question you saw in series two, so pay attention."
</Person1><Person2> "What is an App Service plan?"
</Person2><Person1> "A set of compute resources for web apps to run on. Analogy: a server farm in traditional hosting. One or more apps can run on the same plan. Creating a plan in a region creates compute resources there, and every app in the plan runs on them. Each plan defines: operating system, Linux or Windows; region; pricing tier, which determines features and price, with available tiers depending on the OS chosen at creation; number of VM instances; and size of VM instances, defined by CPU, memory and remote storage."
</Person1><Person2> "Considerations."
</Person2><Person1> "Cost saving: multiple apps in one plan share compute, so you pay once. But the apps share the same instances, so manage capacity carefully; before adding an app, check the app's needs and the remaining capacity. The warning: overloading a plan can cause downtime for new and existing apps. Isolate an app in its own plan when it is resource intensive, when you want to scale it independently, or when it needs a different region. Note: a plan lives in one region, so an app in another region needs a plan in that region."
</Person1><Person2> "Pricing tiers."
</Person2><Person1> "Free, Shared, Basic, Standard, Premium, Premium V two, Premium V three, Isolated, Isolated V two. Three categories. Shared compute: Free and Shared run on the same VM as other customers' apps, with CPU quotas per app, cannot scale out, for development and testing only, and no SLA. They are metered per application. Dedicated compute: Basic, Standard, Premium, Premium V two, Premium V three run on dedicated VMs; only apps in the same plan share the compute; higher tiers allow more instances. Isolated: Isolated V two and Isolated run dedicated VMs on dedicated virtual networks, giving network isolation on top of compute isolation, with maximum scale out."

Time based: scale on schedule patterns, such as a profile for business hours, or a webhook at eight in the morning on Saturday in a time zone. </Person2><Person1> "By default the app is name dot azurewebsites dot net, with a virtual IP. A custom domain is one you own, pointed at the app: branded, trusted, manageable. </Person1><Person1> "Episode seven. Containers on Azure: containers versus virtual machines, Azure Container Instances, container groups, Azure Container Apps, and how they compare with Azure Kubernetes Service."
</Person1><Person2> "Start with containers versus VMs."
</Person2><Person1> "A VM virtualizes the hardware, each with a full operating system. A container virtualizes the operating system, so several applications share one OS instance while staying isolated. The comparison table. Isolation: a container gives lightweight isolation, not as strong a security boundary as a VM; a VM gives complete isolation, useful when hosting competing companies' apps on the same server. Operating system: containers run the user mode part of the OS and can be tailored to need only required services, using fewer resources; VMs run a full OS including the kernel. Deployment: individual containers with Docker on the command line, multiple with an orchestrator like Azure Kubernetes Service; VMs with Windows Admin Center, Hyper-V Manager, PowerShell or System Center Virtual Machine Manager. Persistent storage: containers use Azure Disks for a single node or Azure Files for shared storage; VMs use a virtual hard disk or SMB share. Fault tolerance: if a cluster node fails, the orchestrator recreates containers on another node quickly; VMs fail over to another server where the OS restarts."
</Person1><Person2> "Benefits of containers."
</Person2><Person1> "Flexibility and speed when developing and sharing code; simplified testing; streamlined, accelerated deployment; higher workload density and better resource utilization."
</Person1><Person2> "What is a container image?"
</Person2><Person1> "A lightweight, standalone, executable package that includes code, runtime, system tools, system libraries and settings. It is portable and runs consistently across environments. A container is a running instance of an image. Images are stored in registries such as Azure Container Registry, which we covered in series two with its tiers."
</Person1><Person2> "Azure Container Instances."
</Person2><Person1> "The fastest and simplest way to run a container in Azure, with no VMs to manage and no higher level service to adopt. Good for any scenario that works in isolated containers. Features: fast startup in seconds; public IP and DNS name, with FQDN; custom sizes: CPU cores from zero point one to four vCPU and memory from zero point one to sixteen gigabytes per container, fixed for the life of the container group; persistent storage by mounting Azure Files shares; Linux and Windows containers, with the OS type specified at group creation; co scheduled multi container groups sharing host resources; virtual network deployment for Linux container groups, which receive no public IP and communicate only within the VNet or peered networks."
</Person1><Person2> "Container groups."
</Person2><Person1> "The top level resource in ACI: a collection of containers scheduled on the same host that share lifecycle, resources, local network and storage volumes. Similar to a Kubernetes pod. Resource allocation for a multi container group is the sum of the containers' requests: CPU, memory, GPUs. Deployment methods for multi container groups: an Azure Resource Manager template, JSON, good alongside other resources; Bicep, Microsoft's recommended infrastructure as code language, more concise with IntelliSense; or a YAML file, a container focused format, ideal when deploying only container instances. Note the portal and CLI can create only single container groups; YAML or templates are needed for multi container."
</Person1><Person2> "Networking details."
</Person2><Person1> "Containers in a group can share one external IP address, one or more ports on it, and a DNS label with an FQDN. To let external clients reach a container, you must expose the port on the IP address and from the container. Port mapping is not supported because containers in a group share a port namespace; two containers cannot listen on the same port. When the group is deleted, its IP and FQDN are released. Example in the notes: a group on a single host with a DNS label, one public IP with one exposed port, one container on port eighty and another on port one four three three, and two Azure Files shares mounted, one per container."
</Person1><Person2> "Use cases for multi container."
</Person2><Person1> "Web app updates: one container serves the app and another pulls the latest content from source control. Log collection: the application writes logs and a logging container stores them long term. Monitoring: a monitoring container requests the app periodically and raises alerts. Front end and back end: one container serves the web app, another retrieves data. This is the sidecar pattern."
</Person1><Person2> "Restart policies, mentioned in the Copilot prompt."
</Person2><Person1> "ACI has three restart policies: Always, the default, which restarts a container if it stops; OnFailure, restart only on a nonzero exit code; and Never. For task based workloads such as batch jobs, use OnFailure or Never so the container does not loop forever. That is from my knowledge; the notes only reference it as a prompt."
</Person1><Person2> "Azure Container Apps."
</Person2><Person1> "A serverless platform to run containerized applications with less infrastructure and lower cost. You do not manage servers, orchestration or deployment details. Uses: API endpoints, background processing jobs, event driven processing, microservices. It scales dynamically on HTTP traffic, event driven processing, CPU or memory load, or any KEDA supported scaler, including scale to zero. Features: optimized for general purpose containers especially many microservices; powered by Kubernetes and open source technologies Dapr, KEDA and Envoy; Kubernetes style features like service discovery and traffic splitting; supports on demand, scheduled and event driven jobs. It does not give direct access to the Kubernetes APIs, which is the main difference from AKS."
</Person1><Person2> "Compare the three container services."
</Person2><Person1> "ACI: best for isolated, short lived tasks, simplest, per second billing, no orchestration. Container Apps: serverless microservices, built on AKS but as platform as a service, HTTP and event driven autoscaling including scale to zero, quick deployment. AKS: managed Kubernetes cluster where Azure handles the control plane, you get granular control and customization, horizontal pod autoscaling and cluster autoscaling, best for complex long running applications needing full Kubernetes features. Choosing: simple single container or task: ACI. Microservices with serverless and no Kubernetes expertise: Container Apps. Full Kubernetes control and ecosystem: AKS. And a plain web app in a container: App Service, Web App for Containers on Basic or Standard with Linux."
