<Person1> "Welcome back. Episode eight: governance, part one. Azure Policy, resource locks, and moving resources. This covers questions seventy one, seventy two and seventy three. Governance was where you were weakest, so I'll start from the idea, not the questions. We cover management groups, tags, quotas and Advisor in part two."
</Person1><Person2> "What does governance actually mean in Azure?"
</Person2><Person1> "Governance is the set of rules and controls that keep an organization's cloud estate consistent, secure and affordable. Imagine a city. Azure RBAC is the question who is allowed to do things: who holds keys to which buildings. Azure Policy is the building code: what may be built, and how. Resource locks are padlocks on specific buildings so nobody demolishes or modifies them by accident. Management groups, tags and subscriptions are the city districts, address labels and billing accounts. Cost management and Advisor are the accountant and the inspector."
</Person1><Person2> "Start with Azure Policy then."
</Person2><Person1> "Azure Policy evaluates resources against rules and either reports or enforces. The pieces. A policy definition is a rule: an if condition and a then effect. For example, if the resource type is virtual machines, then deny. A policy assignment applies a definition to a scope: management group, subscription, resource group, with parameters. An initiative, also called a policy set, groups many definitions so you assign them together, for example a regulatory compliance initiative. An exclusion removes a child scope from an assignment. An exemption is a formal, optionally time limited, waiver for a specific resource. Policy is inherited downward like RBAC: assign at the subscription, applies to all resource groups inside."
</Person1><Person2> "What are the effects?"
</Person2><Person1> "Deny: blocks the request that violates the rule, the resource isn't created or updated. Audit: allows it but records non compliance. Append: adds fields to the resource during creation, for example adding a tag. Modify: adds, updates or removes properties or tags, for existing resources through remediation. DeployIfNotExists: deploys a related resource if missing, such as installing a monitoring extension. AuditIfNotExists: audits when a related resource doesn't exist. Disabled: turns the rule off. Key facts: Policy is evaluated when resources are created or updated, and in periodic compliance scans, roughly every twenty four hours, or on demand. Policy doesn't delete existing resources. Non compliant existing resources are flagged, and you can run remediation tasks for modify and deployIfNotExists effects, which use a managed identity assigned to the policy."
</Person1><Person2> "How is Policy different from RBAC? I mix them up."
</Person2><Person1> "Memorize this pair. RBAC controls what a user can do, based on who the user is. Policy controls what can be deployed, based on the properties of the resource, regardless of who the user is. Even an Owner is blocked by a deny policy. If someone has a role but the deployment fails with a policy violation, the answer is Policy. If the error is authorization failed, it's RBAC. Test for exam: a question about restricting regions, sizes, resource types, or requiring tags, that's Policy. A question about who can create or read, that's RBAC."
</Person1><Person2> "Question seventy one."
</Person2><Person1> "The setup: VNET one and VM one exist in RG one. A Not allowed resource types policy is assigned to RG one with enforcement enabled. It blocks Microsoft dot Network slash virtualNetworks and Microsoft dot Compute slash virtualMachines. You must deploy a new VM named VM two in RG one and connect it to VNET one. What first? Answer: remove Microsoft dot Compute slash virtualMachines from the policy. You got this right. Let me explain why the others are wrong, because a twist can flip them. VNET one already exists. The policy doesn't remove existing resources, and connecting a new network interface to an existing virtual network is a write on the network interface resource and a join action on the subnet, not the creation of a virtual network. So you don't need to unblock virtual networks. Adding a subnet is irrelevant to the block. An ARM template doesn't bypass Policy, because the policy engine sits in Azure Resource Manager and evaluates every request, whether from the portal, CLI or template."
</Person1><Person2> "What if the question had been, deploy VM two and a new VNET in RG one?"
</Person2><Person1> "Then you'd remove both types, or you could deploy into another resource group. Another valid approach in practice: instead of editing the policy, create a policy exemption for RG one, or exclude the resource group in the assignment, or set enforcement mode to Do not enforce, which keeps evaluating and reporting but doesn't block. In a multiple choice question, the offered option decides. Note also that creating a VM involves other resource types such as network interfaces and disks, which aren't on the list, so only the VM type needs unblocking."
</Person1><Person2> "Now locks. What exactly is a lock?"
</Person2><Person1> "A resource lock prevents accidental deletion or modification of a resource, no matter what RBAC role the user has. Two lock levels. CanNotDelete, shown as Delete in the portal: authorized users can read and modify, but not delete. ReadOnly: authorized users can only read. It behaves as if everyone only had the Reader role. Locks apply at subscription, resource group or resource scope, and are inherited by child resources. Locks apply to control plane operations, the management ones sent to Azure Resource Manager, not to data plane operations. Example: a delete lock on a storage account stops deleting the account but doesn't stop deleting blobs in it. A read only lock on a storage account can break things in surprising ways: listing the account keys is a POST operation, which is blocked, so tools that need keys fail. A read only lock on a resource group prevents creating new resources in it. To create or delete locks, you need Microsoft dot Authorization slash locks permissions, which only Owner and User Access Administrator have among built in roles. Even an Owner must remove the lock before deleting the resource."
</Person1><Person2> "Which lock would I use to protect a production database from deletion, and also allow changes?"
</Person2><Person1> "CanNotDelete. ReadOnly would also stop changes, like scaling it up. Lock precedence: if multiple locks exist on the same scope chain, the most restrictive applies."
</Person1><Person2> "Now questions seventy two and seventy three, and moving resources."
</Person2><Person1> "The setup: two resource groups. RG one has no lock. RG two has a lock named Lock of type Delete. In RG one: Storage one with a Delete lock named Lock one. VNET one with a Read only lock named Lock two. IP one, a public IP, no lock. In RG two: Storage two with a Delete lock, VNET two with a read only lock, IP two with none. Question seventy two: which resources can be moved from RG one to RG two? Answer: IP one, VNET one and storage one, all three. You said IP one and storage one only, so you excluded VNET one, because of the read only lock. Question seventy three, the mirror: which can be moved from RG two to RG one? All three, IP two, VNET two and storage two. You answered correctly."
</Person1><Person2> "Why doesn't the read only lock stop the move?"
</Person2><Person1> "According to the exam's explanation, locks are designed to prevent update or removal of the resource, and a move changes only the resource's location in the hierarchy, the resource group it belongs to, not the resource itself. The exam's walkthrough screenshots show the move succeeded with the locks in place, including a Delete lock on the target resource group. So for this exam: locks do not block moving resources between resource groups. Rule to memorize for the exam: move is not delete and not modify, so locks don't block it."
</Person1><Person2> "Is that really how Azure works? It feels wrong that a lock on the source group doesn't matter."
</Person2><Person1> "Honest answer: Azure documentation on moving resources says a move operation locks both the source and target groups during the move, and requires write permissions. The lock documentation lists what locks block, writes and deletes, and a move is technically a write on the resource ID path, so in practice behavior has varied by resource type and over time. I'd treat the exam's answer as the one to choose, and real world, test in a lab or check the move support table before relying on it. Never assume a locked resource moves smoothly in production."
</Person1><Person2> "What are the real rules for moving?"
</Person2><Person1> "Rules, from the documentation. One: you need the right to move: Microsoft dot Resources slash subscriptions slash resourceGroups slash moveResources slash action on the source group, and write access on the target group. Two: not all resource types can be moved, check the move support list. Three: the resource's ID changes, because the resource group name is part of the ID, so scripts and policies that referenced the old ID must be updated. Four: moving between resource groups doesn't change the region. Moving to another region is a different operation, with Azure Resource Mover or redeployment. Five: the resource group policy of the destination applies afterward, not the source's. Tags and RBAC role assignments set on the old resource group no longer apply, while role assignments made directly on the resource move with it. Six: you can move between subscriptions in the same tenant, with limits, for example dependent resources must move together, such as a virtual network with its peerings. Seven: during the move, both groups are locked for write and delete, but the resources keep running, except for operations on the moved resources."
</Person1><Person2> "Twist examples?"
</Person2><Person1> "They might ask what happens to the region: unchanged. They might ask which resource can't be moved, such as a classic resource in some conditions, or a resource with a dependency in another group, like a VNET with a gateway that must go together. They might ask what role is needed on the target: write on the target resource group, such as Contributor. They might give a delete lock on a resource and ask whether you can delete: no, remove the lock first. Or ask who can create locks: Owner or User Access Administrator."
