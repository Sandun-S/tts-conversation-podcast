<Person1> "Welcome back. Episode thirteen: virtual networking, part two. Network security groups, how to read them, load balancing options, and the Ironclad network design. Questions covered: thirty one, thirty two, thirty three, thirty five, thirty six, sixty nine, eighty, eighty two and eighty three."
</Person1><Person2> "Let's start with NSGs, since three questions use them."
</Person2><Person1> "A network security group is a stateful packet filter with a list of allow and deny rules. Each rule has a priority between one hundred and four thousand ninety six, lower number evaluated first, a name, a direction inbound or outbound, a protocol, source, destination, port ranges, and an action allow or deny. Processing stops at the first match. Stateful means that if you allow a flow in one direction, the return traffic is allowed automatically. You can associate an NSG with a subnet, or with a network interface, or both. Every NSG ships with default rules you can't delete but can override with higher priority rules. Inbound defaults: priority sixty five thousand, AllowVnetInBound, allowing traffic from the virtual network address space. Priority sixty five thousand one, AllowAzureLoadBalancerInBound. Priority sixty five thousand five hundred, DenyAllInBound. Outbound defaults: sixty five thousand AllowVnetOutBound, sixty five thousand one AllowInternetOutBound, sixty five thousand five hundred DenyAllOutBound."
</Person1><Person2> "And when both subnet and NIC have NSGs?"
</Person2><Person1> "Both apply, in sequence. Inbound traffic is evaluated by the subnet NSG first, then by the NIC NSG. Outbound traffic is evaluated by the NIC NSG first, then by the subnet NSG. A packet must be allowed at every layer it crosses. If either denies, it's dropped. Traffic inside the same subnet is also filtered by the subnet NSG."
</Person1><Person2> "The three RDP questions. Explain the setup."
</Person2><Person1> "Two VMs, both Windows Server twenty nineteen, with public IPs and RDP enabled. VM one is in Subnet one and VM two in Subnet two, both in VNet one. NSG one has only default rules, associated to Subnet one. NSG two has the default rules plus Rule one: priority one hundred, TCP, port three three eight nine, source any, destination any, allow, associated to VM two's network interface. Question thirty one: you can connect to VM one from the internet using RDP. False, you got it right. Inbound from the internet to VM one is checked at Subnet one's NSG: the default rules allow only VNet and load balancer sources, and then DenyAllInBound. Internet source doesn't match AllowVnetInBound, so it hits the deny. No explicit allow for three three eight nine. Dropped."
</Person1><Person2> "Question thirty two, VM two from the internet."
</Person2><Person1> "True. Inbound to VM two: Subnet two has no NSG, so nothing there. Then the NIC NSG, NSG two: Rule one at priority one hundred allows TCP three three eight nine from any. Match, allow. The VM has a public IP, so the path exists. Question thirty three: from VM one you can RDP to VM two. True. Outbound from VM one: the NIC has no NSG; then Subnet one's NSG one, outbound default rules include AllowVnetOutBound, so traffic to another address in the VNet is allowed. Between subnets, Azure's default system routes connect them. Inbound at VM two: Subnet two nothing, NIC NSG two has Rule one allowing three three eight nine from any source, including VM one. Allowed. You got all three correct, but note the method: trace the packet through each hop and check which NSG applies in each direction."
</Person1><Person2> "A trick: what if the rule were on Subnet two as a deny with higher priority?"
</Person2><Person1> "Then VM two would be unreachable regardless of the NIC allow, because the inbound path crosses the subnet first. The principle: an allow at one layer doesn't override a deny at another layer. A real world tip: opening three three eight nine to any is bad practice. Use Azure Bastion, just in time VM access, or restrict the source to your IP."
</Person1><Person2> "Question eighty, the Ironclad NSG."
</Person2><Person1> "After creating an NSG, recommend a solution that allows users to access ProductionPortal. Answer: create an incoming security rule for port four four three from the Internet, and associate the NSG to the subnet that contains the web servers. You got this right. Why exactly? The case study says users access the web front end exclusively by using HTTPS, so inbound TCP four four three. Inbound, since users initiate. Associate with the web subnet, not all subnets, because processing and database tiers shouldn't accept traffic from the internet, which is least exposure and fits the requirement to minimize open ports between tiers."
</Person1><Person2> "Questions eighty two and eighty three, the design. I got them right but explain."
</Person2><Person1> "Recommend a solution that satisfies the technical requirements. Number of virtual networks: one. Number of subnets per virtual network: three. Reasoning: three tiers, SQL, web and processing, each with seven VMs. Requirement: minimize the number of open ports between application tiers. You get that by putting each tier in its own subnet, then using NSGs to allow only the necessary ports between subnets: web to processing on the app port, processing to SQL on one four three three, and deny everything else. One virtual network is enough, since VMs in the same VNet can talk by default, so no peering or gateways. Multiple VNets would add peering cost and complexity, and the requirement to minimize administrative effort pushes to one VNet."
</Person1><Person2> "What about application security groups?"
</Person2><Person1> "Application security groups, ASGs, let you group NICs of VMs by role, such as WebServers, AppServers, DbServers, and write NSG rules in terms of groups instead of IP addresses: allow from AppServers to DbServers on one four three three. With seven VMs per tier, ASGs simplify rules, as you add or remove VMs from the group without editing rules. An ASG and its NICs must be in the same virtual network. Service tags are another shorthand: names for groups of Azure IP prefixes, such as Internet, VirtualNetwork, AzureLoadBalancer, Storage, AzureKeyVault, Sql. Memory: ASG groups your own VMs, service tags name Azure services."
</Person1><Person2> "Now load balancing. Questions thirty five, thirty six and sixty nine."
</Person2><Person1> "Four services. Azure Load Balancer: layer four, TCP and UDP, very fast, zone redundant, public or internal. A public load balancer has a public frontend IP, internet facing. An internal load balancer has a private frontend IP inside a VNet, for traffic from inside the VNet or from on premises over VPN. Application Gateway: layer seven, HTTP and HTTPS, with URL path routing, multi site hosting, SSL termination, cookie affinity, and an optional Web Application Firewall, WAF, to block SQL injection and cross site scripting. Can be public or private. Traffic Manager: DNS based routing across regions or endpoints, with methods like priority, weighted, performance, geographic. It doesn't proxy traffic. Azure Front Door: global layer seven entry point with CDN like acceleration and WAF. And Azure CDN, caching static content close to users. Rule: balancing inside a region at layer four, Load Balancer; at layer seven with web features, Application Gateway; across regions by DNS, Traffic Manager; global web acceleration, Front Door."
</Person1><Person2> "Explain thirty five and thirty six."
</Person2><Person1> "The setup: a multi tier application. Web tier: internet facing, ten VMs. Application tier: not internet facing, one hundred VMs. Database tier: five SQL Server VMs, not internet facing. Question thirty five: evenly distribute traffic from the web tier to the application tier across all VMs. Answer: an internal load balancer. Traffic is internal, between tiers, no internet exposure. A public load balancer would expose the app tier, Application Gateway is for web traffic and layer seven features, an NSG filters, doesn't balance. Question thirty six: protect the web tier from SQL injection attacks coming from the internet. Answer: an Application Gateway with the WAF tier. Standard tier gateway does not inspect for attacks, only WAF does. The load balancers work at layer four, they can't see SQL in an HTTP request. You got both right."
</Person1><Person2> "And sixty nine, the two services for even distribution to App one."
</Person2><Person1> "The setup: users connect from home by point to site VPN and from customer locations through site to site VPNs, so they all arrive through private connections, not the internet. App one runs on several Windows Server VMs. Requirement: incoming connections distributed evenly across the VMs. Which two services? Answer: an internal load balancer and an Application Gateway. You got it right. Because users come in via VPN, the app is reached on private IPs. An internal load balancer works at layer four, and an Application Gateway with a private frontend works at layer seven. A public load balancer would need a public front end, and Traffic Manager and CDN are DNS and caching solutions that don't balance across VMs inside a network."
</Person1><Person2> "Do any of these relate to availability for the Ironclad design?"
</Person2><Person1> "Yes, each tier has seven VMs. For high availability across failures within a region, you place VMs in an availability set, which spreads them across fault domains and update domains, or in availability zones, spreading across datacenters. A Standard load balancer supports zones. Typical Ironclad design: web tier behind an Application Gateway with WAF over HTTPS, processing tier behind an internal load balancer, SQL tier with its own internal load balancer for Always On availability groups, three subnets, NSGs per subnet, VMs in an availability set per tier, backed up with Recovery Services vault."
</Person1><Person2> "Diagnostic tools for NSGs?"
</Person2><Person1> "In Network Watcher. IP flow verify tests whether a packet to or from a VM is allowed or denied and tells you which rule decided. Effective security rules on a NIC show the combined result of NSGs at subnet and NIC. Next hop shows which route a packet will take. NSG flow logs record traffic data, though they're being retired in favor of virtual network flow logs. Connection troubleshoot tests connectivity end to end. Packet capture captures traffic on a VM."
