<Person1> "Welcome back. Episode two: the hybrid identity picture. We build everything from zero, because this is the foundation under about a fifth of the exam. No question numbers yet, only the picture. Then at the end I connect it to the questions you missed."
</Person1><Person2> "Start at the very beginning. What is Active Directory?"
</Person2><Person1> "Imagine a company with an office building. In the building there are computers, file servers and employees. Someone has to keep the master list of who is allowed to do what: this person is Anna in finance, her password is this, she may open that share, she may log in to those computers. In the nineties Microsoft built a product for that master list, called Active Directory Domain Services, usually shortened to AD DS. It runs on Windows Server machines called domain controllers. A domain controller holds the directory, the database of accounts, and answers every login on the local network."
</Person1><Person2> "So AD DS is a server role, an on premises database of identities."
</Person2><Person1> "Exactly. And it has a particular structure. Learn four words. A domain is a boundary containing accounts and computers, for example ironclad dot com. A forest is the top level container, one or more domains that share a schema and trust each other. In the Ironclad case study the company has an Active Directory forest named ironclad dot com. An organizational unit, an OU, is a folder inside a domain, used to organize accounts and apply policies, for example OU Finance, OU Engineering. And objects are the things in the folders: users, groups, computers."
</Person1><Person2> "Why do the OUs matter for Azure?"
</Person2><Person1> "Because later, when you synchronize to the cloud, you choose which folders to synchronize. In your Azure Files question the setup was: User one in OU two, User two in OU one, Group one in OU one, and the synchronization only covers OU one. That wording is not decoration, it decides who exists in the cloud. Keep that in mind. Also, how does AD DS prove who you are? With a protocol called Kerberos, plus an older one called NTLM. Kerberos works with tickets: you log in once, the domain controller hands you a ticket granting ticket, and you use it to request tickets for each service, like a file server. The ticket contains your identity and your group memberships, as security identifiers, SIDs. Remember that detail, we use it in the Azure Files episode."
</Person1><Person2> "Fine. Now what is Microsoft Entra ID, and how is it different?"
</Person2><Person1> "Microsoft Entra ID, formerly Azure Active Directory, is a completely different product that unfortunately shares the old name. It is a cloud identity service for the internet. It does not use Kerberos or OUs or domain controllers. It uses web protocols: OAuth two, OpenID Connect and SAML. Tokens instead of tickets. Its structure is flat: one tenant, one directory, no OUs. A tenant is your organization's dedicated instance, like ironclad dot onmicrosoft dot com, and it holds users, groups, applications and devices. Every Azure subscription trusts exactly one tenant, and RBAC role assignments use identities from that tenant."
</Person1><Person2> "If someone says Azure AD is Active Directory in the cloud, is that wrong?"
</Person2><Person1> "It's the most common misunderstanding. Entra ID is not a domain controller in the cloud. It cannot do Kerberos for file servers, it cannot apply Group Policy, it has no domain join in the old sense. It is an identity provider for modern cloud and web applications. If you need the old style, managed in the cloud, there is a third product, Microsoft Entra Domain Services, which gives you managed domain controllers in a virtual network, so legacy apps can use Kerberos, LDAP and domain join without you running servers. Three things: AD DS on premises, Entra ID in the cloud, Entra Domain Services as managed AD DS in Azure."
</Person1><Person2> "Okay. So how does a company with AD DS get into the cloud?"
</Person2><Person1> "Hybrid identity. The idea is that the same human has one identity, with one username and password, in both worlds. You don't want Anna to have two accounts. So you keep AD DS as the place where accounts are created and managed, and you copy those accounts into Entra ID using a synchronization tool. The classic tool is Microsoft Entra Connect, the Sync version. You install it on an on premises server. It reads from AD DS, and it writes to Entra ID. By default it runs a delta sync about every thirty minutes. The copies in Entra are called synchronized or hybrid users. The newer lighter option is Microsoft Entra Cloud Sync, which uses a small agent, supports multiple disconnected forests, and is managed from the cloud. Both do the same job conceptually."
</Person1><Person2> "What exactly is copied?"
</Person2><Person1> "Objects and their attributes. Users, groups, contacts, and attributes like display name, department, job title, city, proxy addresses, and the user principal name. And you choose the scope: all domains, selected domains, selected OUs, or a filter by group or attribute. That's why OUs matter. If only OU one is synchronized, then users in OU two don't exist in Entra ID at all, as synced objects."
</Person1><Person2> "Now, the source of authority. I keep hearing that."
</Person2><Person1> "Source of authority means: where is this object mastered, where do edits happen? For a synced user, the source of authority is on premises. The cloud copy is read mostly, and attributes that are mastered on premises can't be edited in the Entra portal. If you try to change the job title of a synced user in the portal, it's greyed out or rejected, because the next sync would overwrite it anyway. You change it in Active Directory, wait for sync. For a cloud only user, created directly in Entra, the source of authority is Entra, so you edit in the portal. Guests invited from other tenants are also cloud objects. Memorize this: synced equals edit on premises, cloud only or guest equals edit in Entra. There is one famous exception, which is the usage location attribute, which we'll do in episode three."
</Person1><Person2> "Next, authentication. How do hybrid users sign in to Azure?"
</Person2><Person1> "Three methods, and this is high value. Method one, password hash synchronization, PHS. Entra Connect takes a hash of the on premises password hash, and stores that derived hash in Entra ID. When you sign in to the cloud, Entra checks your password against its own copy. It's the simplest, it keeps working if your on premises network is down, and it enables leaked credential detection. Method two, pass through authentication, PTA. Entra ID does not store passwords or hashes. Instead, when you sign in, the password is passed securely to a small agent on premises, which validates it against a domain controller and answers yes or no. Method three, federation, usually with Active Directory Federation Services, AD FS. Entra ID redirects the sign in to your own federation servers, which authenticate and issue a token back. Most complex, most infrastructure."
</Person1><Person2> "And which one do I choose when the requirement says passwords must not be stored in Azure?"
</Person2><Person1> "That's exactly the Ironclad requirement. User passwords and password hashes from the on premises directory must not be stored in Azure. That rules out password hash sync. The answer is pass through authentication, or federation. In an exam where only one is offered, and the requirement also says minimize administrative effort, pass through authentication is the likely pick, because federation needs more servers. Note also that Entra Connect with PTA still synchronizes identities, the accounts and attributes. It just doesn't synchronize any password material."
</Person1><Person2> "And seamless single sign on?"
</Person2><Person1> "Seamless single sign on is an add on, used with PHS or PTA. When a domain joined computer inside the corporate network opens a cloud app, the user is signed in automatically, using a Kerberos ticket, without typing the password again. Think of it as a convenience layer, not a method itself."
</Person1><Person2> "What about writeback?"
</Person2><Person1> "Writeback sends some changes from the cloud back to on premises. Password writeback is the famous one: when a user resets a forgotten password using self service password reset in the cloud, writeback sends the new password to Active Directory. Without it, SSPR for synced users can't work, because the password lives on premises. There is also device writeback and group writeback in some configurations. Hold that thought, we meet SSPR in episode six."
</Person1><Person2> "What about custom domains, like ironclad dot com versus onmicrosoft dot com?"
</Person2><Person1> "Every tenant starts with a domain like ironclad dot onmicrosoft dot com. If your users sign in on premises as anna at ironclad dot com, the same suffix must exist and be verified in Entra, otherwise synced users end up with the onmicrosoft suffix. To add a custom domain: add the domain in Entra, receive a TXT record or MX record, add that record at the public registrar's DNS, then verify. We'll walk through that exact sequence in question eighty four next episode."
</Person1><Person2> "How do devices fit in this?"
</Person2><Person1> "Three states, worth separating now. Entra registered, for personal devices, bring your own, the user signs in with a personal account. Entra joined, the device is owned by the organization, cloud only, users sign in with their work account, there's no domain controller needed, best for cloud first companies. Hybrid joined, the device is joined to on premises AD DS and is also registered in Entra, used by companies with existing domains. And joining a virtual machine to a classic domain is a separate thing again, handled by a domain join extension in an ARM template, like in question sixty seven."
</Person1><Person2> "Okay, give me a mental picture to keep."
</Person2><Person1> "Picture two cities. On the left, the old city called Ironclad dot com, with a town hall, the domain controller, a map of districts, the OUs, and ticket booths issuing Kerberos tickets. On the right, a modern city in the cloud, Entra ID, with no districts, only a big flat register, and everything runs on tokens and web passes. A bridge between the cities, the sync tool, carries copies of residents across, but only from districts you chose. Residents who exist only on the right side, cloud only users and guests, have no home on the left. And for logging in, you decide whether the right city holds a copy of the password fingerprints, or asks the left city each time, or hands the whole decision to a separate security office, federation."
</Person1><Person2> "Now link it to my missed questions."
</Person2><Person1> "Four links. One, question eighty five: for which users can you edit job title in Entra? The cloud only member and the guest. The synced user, no. Two, question eight: User three, a cloud only user, cannot access an Azure Files share that uses AD DS authentication, because Kerberos needs the account in AD DS. Three, question six: User one lives in OU two, not synchronized, yet gets access through group membership, because of how Azure Files and Kerberos work with default share permissions. We do it fully in episode five. Four, the Ironclad password requirement, pass through authentication."
</Person1><Person2> "Quick recap?"
</Person2><Person1> "AD DS is on premises, Kerberos, forests, domains and OUs. Entra ID is cloud, tokens, flat tenant. Entra Domain Services is managed AD DS. Entra Connect or Cloud Sync copies chosen objects up. Source of authority decides where you edit. PHS stores a derived hash in the cloud, PTA stores nothing and validates on premises, federation delegates to AD FS. Seamless SSO is convenience. Writeback sends changes back, notably passwords for SSPR. Next episode: users, attributes, custom domains, bulk operations and deletion."
