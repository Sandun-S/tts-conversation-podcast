</Person1><Person2> "Now question eighteen, keys."
</Person2><Person1> "You want to ensure that the access keys for storage one are rotated automatically. Which configuration? Answer: configure an Azure Key Vault. You got it right. Each storage account has two access keys, key one and key two, which provide complete control over the account, so they're sensitive. Best practice: avoid using keys, use Entra authorization, and where keys are needed, rotate them regularly. A key rotation reminder can be set on the storage account itself, a key expiration policy that flags keys older than a number of days. </Person1><Person2> "Question twenty two, SAS."
</Person2><Person1> "Let me first explain shared access signatures, since the Ironclad requirement uses them. A SAS is a signed token that gives limited, time limited access to storage resources without sharing the account key. It's a URI query string with parameters: which resource, which permissions like read or write, start and expiry time, allowed IP range, allowed protocol, and a signature. Three types. User delegation SAS: signed with Entra credentials through a user delegation key, available for blobs and Data Lake, the most secure and recommended. Service SAS: signed with the account key, for one storage service such as blob. Account SAS: signed with the account key, covers multiple services. A service SAS can be linked to a stored access policy, which lets you control expiry or revoke the SAS without changing the key. A container can have up to five stored access policies. If an account key is regenerated, SAS tokens signed with that key are invalidated."
</Person1><Person2> "And the Ironclad external partners requirement?"
</Person2><Person1> "External partners must be provided with secure temporary access to the engineering design documents. That sentence calls for a SAS: it's temporary by design, it requires no account in your tenant, and it can be restricted to read only, specific blobs, and specific IP addresses. A user delegation SAS is best, as it's backed by Entra identity, with a maximum validity of seven days. Alternatives like inviting partners as guests and assigning Storage Blob Data Reader could also work for ongoing access, but temporary access with no identity, a SAS is the exam's pick. A stored access policy makes it revocable."
</Person1><Person2> "Question twenty two now."
</Person2><Person1> "You have blob images, clients access via SAS, and you want users to see a warning whenever they create a SAS with an expiration longer than seven days. What configuration? Answer: set Allow recommended upper limit for shared access signature expiry interval to Enabled, which is the SAS expiration policy on the storage account. You chose create an alert rule. The expiration policy lets you set a recommended maximum interval, in days, hours, minutes. When a user creates a SAS that exceeds it, the portal warns them, and the violation is logged in diagnostic logs. It doesn't block, it's a recommendation, hence the word recommended. Alert rules notify on metrics or logs, they don't warn at creation time. Lifecycle management handles tiers and deletion. A read only lock prevents changes to the account, but isn't a SAS policy."

</Person1><Person2> "Question fifty four, immutability."
</Person2><Person1> "You must ensure that any new blobs uploaded to archivecontainer cannot be altered or deleted for one year after creation. What do you configure? Answer: an access policy. You got it right. In the portal, a container has an Access policy blade, which holds two things: stored access policies for SAS, and immutable blob storage policies. The immutable one has two kinds. Time based retention: blobs can't be modified or deleted for a set number of days after creation, here three hundred sixty five days. And legal hold: blobs can't be modified or deleted until the hold tags are cleared, with no expiry date. Immutability is called WORM, write once read many. Distractors: IAM doesn't stop owners from deleting, access level controls anonymous read, and access tier controls cost."
