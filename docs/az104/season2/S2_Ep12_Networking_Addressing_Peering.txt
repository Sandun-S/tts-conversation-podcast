</Person1><Person2> "Start with what a virtual network is."
</Person2><Person1> "An Azure virtual network, VNet, is your private network in the cloud. You choose one or more address spaces, in CIDR notation, such as ten dot two dot zero dot zero slash sixteen. Then you carve out subnets from the address space, such as ten dot two dot zero dot zero slash twenty four. VMs and other resources get private IPs from subnets. By default, everything in a VNet can talk to everything else, across subnets, because Azure creates system routes between them. A VNet is scoped to one region and one subscription. Resources in one VNet can't see another VNet unless you connect them with peering or a gateway."
</Person1><Person2> "Question five. The subnet math."
</Person2><Person1> "VNet one has the address space one seven two dot sixteen dot ten dot zero slash twenty four. Subnet one uses one seven two dot sixteen dot ten dot zero slash twenty five. What is the maximum number of VMs that can be connected to Subnet one? Options: twenty four, twenty five, one twenty three, one twenty eight, two fifty one. Answer: one hundred twenty three. You chose two hundred fifty one."
</Person1><Person2> "Show me why."
</Person2><Person1> "The subnet is slash twenty five, not slash twenty four. A slash twenty five has thirty two minus twenty five, seven host bits, two to the seventh, one hundred twenty eight addresses. Azure reserves five addresses in every subnet: the first is the network address, the second is used for the default gateway, the third and fourth map Azure DNS addresses, and the last is the broadcast address. So one hundred twenty eight minus five equals one hundred twenty three usable. Two hundred fifty one is what you'd get if you used the whole VNet slash twenty four: two hundred fifty six minus five. That's the trap: the VNet address space is bigger than the subnet. Always use the subnet's prefix. Formula: two to the power of thirty two minus prefix, minus five. Examples: slash twenty four gives two fifty one. Slash twenty six gives fifty nine. Slash twenty eight gives eleven. Slash twenty nine gives three, which is the smallest subnet Azure allows."
</Person1><Person2> "And the explanation about what's reserved, did the exam get it right?"
</Person2><Person1> "The exam says first four and last. Real Azure: network address, default gateway, two Azure DNS mappings, and the broadcast address. Same count of five. Good enough. Also, some subnets have minimum sizes: the GatewaySubnet recommends at least slash twenty seven, Azure Firewall subnet needs slash twenty six, Azure Bastion subnet needs slash twenty six."

</Person1><Person2> "Explain the difference."
</Person2><Person1> "Two layers. The address space is the big pool of private addresses that the VNet is allowed to use. Subnets are slices taken from that pool. A VM's NIC gets an IP from a subnet. For ten dot two dot one dot zero slash twenty four, it's inside the existing slash sixteen pool, ten dot two dot anything. You only need a new slice, a subnet. For one nine two dot one six eight dot one dot zero, that's outside the pool. A subnet must be within the VNet's address space, so you must first add the new address space, then create the subnet, then deploy the VM. Delete a subnet or delete an address space moves in the wrong direction. Adding a network interface doesn't create IP ranges."
</Person1><Person2> "Question thirty four, peering and overlap."
</Person2><Person1> "VNet one has address space ten dot two dot zero dot zero slash sixteen, with no devices. VNet two has the same address space. You need to peer them. What first? Answer: modify the address space of VNet one. You got it right. Peered virtual networks must have non overlapping address spaces, because routing needs to tell which network an address belongs to. Here both are identical. So you must change one of them. If VNet one has no resources, changing it is easy. If a VNet is already peered or has a subnet in use, you can still modify the address space but must resync the peering, in some cases removing and recreating. A gateway subnet isn't required for basic peering, and a service endpoint is unrelated."
</Person1><Person2> "Now question nine, which VNets can peer."

</Person1><Person2> "Why can you peer across tenants?"
</Person2><Person1> "Virtual network peering supports same region peering, called regional, and cross region peering, called global peering. It supports virtual networks in the same subscription or different subscriptions, and even different Microsoft Entra tenants, as long as the person doing it has the needed permissions on both sides, in particular Network Contributor on each VNet, or a custom role with the peering write and join actions. Peering is created in both directions: a link from A to B and a link from B to A, each with its own settings. The thinking error was assuming subscription or tenant boundaries stop connectivity. They don't. What can block peering: overlapping address spaces, and a few special cases like peering with a classic VNet needing extra care."
</Person1><Person2> "What do peering settings do?"
</Person2><Person1> "Per link, you set: allow virtual network access, which is on by default and lets traffic flow; allow forwarded traffic, which lets a link carry traffic that didn't originate in the peer, needed for network virtual appliances; allow gateway transit, set on the VNet that owns the VPN gateway, so peers can use it; and use remote gateways, set on the spoke, to use the hub's gateway. Peering is non transitive. If A is peered with B and B is peered with C, A can't reach C through B automatically, unless you use a hub appliance with user defined routes, or gateway transit for gateways, or Azure Virtual WAN, or a mesh in a hub and spoke."
</Person1><Person2> "Question seventeen, the cost effective link from on premises to VNet two."
</Person2><Person1> "The setup: two peered VNets, VNet one and VNet two. VNet one has a VPN gateway using static routing, and the on premises network connects through it. You need users on premises to access a VM in VNet two, cost effectively. Answer: use service chaining together with user defined routes. You chose Application Gateway. Service chaining means directing traffic from one virtual network through a service, here a gateway, in another peered network, using user defined routes. The mechanism is gateway transit: in the peering link from VNet one to VNet two, you enable Allow gateway transit. In the link from VNet two to VNet one, you enable Use remote gateways. Then VNet two uses the VPN gateway in VNet one. With static routing you also need to add the VNet two address space to the on premises VPN device, since static routes don't learn automatically, which is why the exam mentions static routing. Alternatively, user defined routes in VNet two's subnets point to a virtual appliance."
</Person1><Person2> "Why not the other options?"
</Person2><Person1> "Azure Firewall costs a lot and isn't required just for routing. Application Gateway is a layer seven load balancer for web traffic, not for routing network traffic between VNets and on premises. ExpressRoute is a separate private circuit, expensive, and not needed because a VPN is already in place. The question's key phrase: cost effective, using what you already have. Use the existing VPN gateway and peering. Know also the limits: the remote gateway setting can't be used when the spoke has its own gateway, and gateway transit doesn't work with a Basic SKU gateway."
</Person1><Person2> "Question sixteen, public IPs."
</Person2><Person1> "You have VM one, VNet one, NIC one, load balancer LB one and a virtual network gateway VPN one. You create a new public IP named IP one. Which two can be linked to IP one? Answer: LB one and NIC one. You chose VM one and LB one. A VM does not directly reference a public IP. The VM has a network interface, and the NIC's IP configuration has the association to the public IP. Public IPs can also be associated with a load balancer frontend, a NAT gateway, Azure Firewall, Application Gateway frontend, Bastion, and a virtual network gateway. A VNet doesn't take a public IP at all. The exam answer says the VPN gateway isn't linked to manually created public IPs, which is outdated. Real Azure: you do create a public IP resource and associate it with the VPN gateway's IP configuration when you create the gateway. For this question, the intended answer is LB and NIC."
</Person1><Person2> "Basic versus Standard public IP?"
</Person2><Person1> "Standard SKU public IPs: static allocation, secure by default, closed to inbound traffic until an NSG allows it, zone redundant by default in zonal regions, work with Standard load balancers. Basic SKU public IPs: can be dynamic, open by default, and are being retired. In September twenty twenty five, Basic public IP addresses retire, so Standard is the future. Also note that you can't mix SKUs between a load balancer and its public IP: both Standard or both Basic."
