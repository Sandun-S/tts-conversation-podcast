</Person1><Person2> "Start with virtual machines in general, so I have the picture."
</Person2><Person1> "A virtual machine is IaaS compute. To get one you need a size, which defines vCPUs, memory, and disk and network limits, an image, an operating system disk, a network interface in a subnet, and optionally data disks and a public IP. Sizes come in families: B series burstable, D series general purpose, E series memory optimized, F series compute optimized, N series with GPUs, and so on. VM states matter for billing: Running, Stopped, and Stopped deallocated. If you stop a VM inside the operating system, it's stopped but still allocated, so you keep paying for compute. If you stop it from the portal, it becomes deallocated, releasing the compute hardware, so compute charges stop, though you still pay for disks, and dynamic public IPs may change."
</Person1><Person2> "Question fifteen. Resizing."
</Person2><Person1> "Three VMs in an availability set AVSet one. You want to resize VM one to a larger size, but the target size is not available. What first? Answer: deallocate VM one. You chose create a proximity placement group. Why does the size not appear? Each physical cluster of hardware in a datacenter supports a particular set of VM sizes. A running VM is on one cluster. The resize options list only shows sizes available on that cluster. If you want a size that's not on the current cluster, Azure must move the VM to another cluster. That's only possible when the VM is deallocated, so the platform can allocate it freshly somewhere else. Deallocating VM one, then looking again at sizes, often shows the larger sizes."
</Person1><Person2> "And availability sets? Do they complicate it?"
</Person2><Person1> "For VMs in an availability set, all VMs are placed on the same cluster so they share fault and update domain structure. If the target size isn't available on that cluster, the Microsoft documentation says you need to stop all the VMs in the availability set, then resize one of them, then start them all, since all must be moved together to a cluster that supports the new size. The exam's answer to the first step is deallocate VM one. In a longer sequence question, you'd see deallocate all VMs in the set, resize, then start. Also, resizing a running VM causes a restart. Also, any data on the temporary disk is lost on a deallocation and resize across clusters, and the dynamic public IP can change."
</Person1><Person2> "Why are the other options wrong?"
</Person2><Person1> "A proximity placement group is about placing VMs physically close for low latency, which actually restricts placement further, and might make it harder to get certain sizes. Convert to a managed availability set, the set is already managed if VMs use managed disks, and doing it isn't about sizes. Powering off VM two and three: powering off without deallocating doesn't release hardware, and the question concerns VM one."
</Person1><Person2> "Availability concepts, quickly?"
</Person2><Person1> "Availability set: VMs spread over fault domains, which share power and network, usually up to three, and update domains, up to twenty, so planned maintenance doesn't take every VM down. Protects against rack and host failures, SLA of ninety nine point nine five percent. Availability zones: physically separate datacenters in a region, each with independent power, cooling and network, SLA ninety nine point nine nine percent for two or more VMs in different zones. Virtual machine scale sets: groups of identical VMs, autoscaling by metrics or schedules, across zones and fault domains. You can't combine an availability set with a zone for the same VM. Proximity placement group: low latency between VMs."
</Person1><Person2> "Now ARM templates. What are they?"
</Person2><Person1> "Azure Resource Manager templates are JSON files that declare the infrastructure you want. Declarative: you describe the end state, Azure Resource Manager works out how to create it. Idempotent: deploying again changes only what's different. Structure: a schema, a content version, parameters for inputs, variables for reusable values, resources, which is the main section, and outputs. Each resource has a type, an API version, a name, a location, properties, and optionally dependsOn, tags and so on. Deployment modes: incremental, the default, adds or updates resources and leaves others alone; complete, which deletes resources in the resource group that aren't in the template. Bicep is a friendlier language that compiles to ARM JSON. Template functions appear in square brackets, like concat, resourceId, parameters, variables, copyIndex."
</Person1><Person2> "Questions fifty and fifty one, the data disks loop."
</Person2><Person1> "You deploy a VM with an ARM template and it must be created with multiple data disks, controlled by a parameter, the number of data disks. A template snippet is shown with two blanks, Code Segment A and Code Segment B. Question fifty: Segment A, options: copy, copyIndex, dependsOn. Answer: the word copy, that is, quote copy colon open bracket. You chose dependsOn. Question fifty one: Segment B. Options: bracket copy, bracket copyIndex, bracket dependsOn. Answer: bracket copyIndex. You got that right."
</Person1><Person2> "Explain the template mechanics."
</Person2><Person1> "To create several of something in ARM, you use the copy element. There are two forms. At the resource level, a copy block with a name and a count creates that many copies of the whole resource, like several network interfaces. At the property level, inside a resource, a copy array defines an array property, like dataDisks, built by iterating. In the VM resource, under storageProfile, you write: copy, an array with one object having a name, dataDisks, a count of parameters numberOfDataDisks, and an input object describing each disk: lun equals copyIndex of dataDisks, createOption Empty, diskSizeGB one thousand twenty three. So Segment A is the copy keyword that creates the loop. Segment B, the lun value, uses the function copyIndex, which returns the current zero based iteration number, giving a unique LUN for each disk: zero, one, two. A logical unit number must be unique per disk on a VM."
</Person1><Person2> "What would dependsOn do?"
</Person2><Person1> "dependsOn expresses an ordering dependency between resources: create the NIC before the VM that uses it. It doesn't create repetitions. A classic trap: dependsOn sounds like it relates to the disks and the VM. But the thinking should be: what keyword repeats things? copy. What function gives the loop counter? copyIndex. Remember copy is a property or element, and copyIndex is a function, written inside square brackets."
</Person1><Person2> "Twists for templates?"
</Person2><Person1> "They could ask what makes a template run the loop serially instead of in parallel: mode serial with batchSize inside the copy. They could ask what you'd use to deploy a resource only if a condition is true: the condition property. They could ask how to reference an existing resource: resourceId. They could ask what deployment mode removes resources not in the template: complete. They could ask where to put secrets: use secure string parameters, or reference Key Vault secrets in the parameter file, never plain text."
</Person1><Person2> "Questions sixty seven and sixty eight, the domain join."
</Person2><Person1> "You have an Azure subscription with a VM running Windows ten. You need to join it to an Active Directory domain using an ARM template. Question sixty seven: Segment A, the resource type. Options: Extensions; Microsoft dot Compute slash VirtualMachines; Microsoft dot Compute slash virtualMachines slash extensions. Answer: the third, Microsoft dot Compute slash virtualMachines slash extensions. You chose the second. Question sixty eight: Segment B, where does the domain password go? </Person1><Person2> "Why extensions?"
</Person2><Person1> "A VM extension is a small package of software that Azure installs on a VM to do post deployment configuration or automation. Examples: custom script extension, DSC, antimalware, monitoring agents, and the JsonADDomainExtension, which joins a Windows VM to an Active Directory domain. In a template, extensions are child resources of the virtual machine, with the type Microsoft dot Compute slash virtualMachines slash extensions, and a name made of the VM name, a slash, and the extension name. The second option, VirtualMachines without extensions, is the VM resource itself, not the extension. The first is not a valid resource type."
</Person1><Person2> "What does the extension body look like?"
</Person2><Person1> "Properties include publisher Microsoft dot Compute, type JsonADDomainExtension, typeHandlerVersion one dot three, autoUpgradeMinorVersion true. Then settings: Name, the domain, such as ironclad dot com; OUPath, the organizational unit path where to put the computer account; User, the domain account with rights to join; Restart true; and Options three, which means join domain and create the computer account. Then protectedSettings: Password, the password for that domain user. Protected settings are encrypted using a key from the VM, not shown in plain text in the deployment history or the portal. Settings are visible. So passwords always go to protectedSettings, which answers question sixty eight."
</Person1><Person2> "What does the VM need to join a domain?"
</Person2><Person1> "Network line of sight to a domain controller, so a VNet connected through VPN or ExpressRoute to on premises, or domain controllers running in Azure. And DNS: the VNet's DNS servers must point to the domain controllers so the domain name resolves. Plus a domain account allowed to join computers. Alternatively, use Microsoft Entra Domain Services as the domain. Or skip all that: use Entra join for Windows ten and eleven, with the AADLoginForWindows extension, and use RBAC roles Virtual Machine Administrator Login or Virtual Machine User Login. That's the cloud native way."
</Person1><Person2> "And the case study? Ironclad has an AD forest named ironclad dot com."
</Person2><Person1> "A plausible Ironclad question: after migrating the portal VMs, they must join the domain ironclad dot com. Answer pattern: deploy domain join extensions via template, VNet DNS pointing at domain controllers, VPN to on premises. Another potential: virtual machine hard disks must use unmanaged standard storage, per the technical requirements. Unmanaged disks are VHD files stored as page blobs in a standard storage account that you manage, rather than managed disks. In a template, the VM's osDisk has a vhd uri pointing into the storage account. Unmanaged disks are being retired, with a retirement date, and have limits like storage account throughput, but the exam's case study mandates them. Also unmanaged disks can still be backed up with Azure Backup."
