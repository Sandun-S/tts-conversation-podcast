<Person1> "Welcome back. Episode five: Azure Files and identity based access. This is the family of questions where AD DS, hybrid identities and storage meet, and it cost you four marks. It covers questions six, seven, eight, twenty three, twenty four and twenty five. If you only replay one identity episode, replay this."
</Person1><Person2> "Start simple. What is Azure Files?"
</Person2><Person1> "Azure Files gives you fully managed file shares in the cloud, reachable by the SMB protocol, which Windows uses for mapped network drives, and also by NFS for Linux in some tiers. A file share lives inside a storage account. You mount it with a path like backslash backslash storage account name dot file dot core dot windows dot net backslash share name. The problem: who is allowed to open it? By default, the storage account key gives complete access to every share, like a master password. That's not good for ordinary users. So Azure Files supports identity based authentication, where users authenticate with a directory identity and get permissions per user."
</Person1><Person2> "Which directories can it use?"
</Person2><Person1> "Three identity sources over SMB. One: on premises Active Directory Domain Services, AD DS. Two: Microsoft Entra Domain Services, the managed domain. Three: Microsoft Entra Kerberos, which supports hybrid identities, meaning users that exist in both on premises AD and Entra, without needing line of sight to a domain controller. Critical rule: a storage account can use only one identity source for SMB authentication at a time. And for the on premises AD DS option, the identities that get access have to be hybrid identities, meaning they exist in AD DS and are synchronized to Entra ID. Cloud only identities, created only in Entra, can't be used with the AD DS source."
</Person1><Person2> "Why? Why can't a cloud only user connect?"
</Person2><Person1> "Because AD DS authentication uses Kerberos. For a Kerberos ticket, the user must have an account in the domain controller that issues tickets. A cloud only user has no account in Active Directory. Nobody on premises knows them. Picture the old city and the new city from episode two. A resident who only exists in the new city can't get a ticket from the old city's ticket booth. Therefore question eight, User three, a cloud only user, cannot access share one. False."
</Person1><Person2> "So what actually happens when I open a share with AD DS authentication?"
</Person2><Person1> "Step by step. First, the storage account was joined to Active Directory. That's done once by an administrator, with the AzFilesHybrid module or the setup script, creating a computer account or service logon account for the storage account in the domain, with a service principal name for the file endpoint. Second, a user logs in to a domain joined machine, gets a ticket granting ticket. Third, the user maps the share. Their machine requests a service ticket for the storage account's service principal name. The domain controller issues it, containing the user's identity and group SIDs. Fourth, the machine presents the ticket to Azure Files over SMB. Azure Files validates it, then checks permissions in two layers."
</Person1><Person2> "Two layers?"
</Person2><Person1> "Layer one is the share level permission, which is Azure RBAC. Layer two is the file and directory level permission, the NTFS ACL, set with Windows tools like File Explorer security tab or icacls. The effective permission is the more restrictive of the two. Think of a building: share level is the front door, NTFS is the door of each office."
</Person1><Person2> "Share level permissions. Which roles?"
</Person2><Person1> "Three data plane roles. Storage File Data SMB Share Reader: read access. Storage File Data SMB Share Contributor: read, write and delete. Storage File Data SMB Share Elevated Contributor: also modify NTFS permissions, which administrators need. There's also a Storage File Data Privileged Contributor for special backup scenarios. You assign them like any role in Azure RBAC, to a user or group, at storage account, share, or resource group level. And there's a shortcut: the default share level permission."
</Person1><Person2> "Explain the default share level permission."
</Person2><Person1> "It's a setting on the storage account: for any identity that authenticates successfully but has no specific role assignment, apply this default role. The options are none, which means access denied unless a role is assigned, or one of the SMB share roles to all authenticated users and groups. In your scenario, it's set to allow access for all authenticated users and groups. That means that anyone who can authenticate with Kerberos through the associated Active Directory is allowed at share level, even without a specific assignment."
</Person1><Person2> "And now, question six, the tough one. User one in OU two, not synchronized, but a member of Group one in OU one."
</Person2><Person1> "Let me restate it. AD DS: User one is a user in OU two. User two is in OU one. Group one is a global security group in OU one, and its member is User one. Storage one uses AD DS, default share permission allows all authenticated users and groups. share one assignments: User two gets SMB Share Reader, Group one gets SMB Share Contributor. Entra Connect synchronizes OU one only. Also User three, a cloud only user in Entra. Question six: can User one access share one? Answer: True."
</Person1><Person2> "But User one isn't synchronized."
</Person2><Person1> "Right, and this is the part to understand. Two reasons it still works. First, User one has an account in AD DS, so they can get a Kerberos ticket, and therefore can authenticate against the AD DS associated with the storage account. The synchronization only matters for assigning explicit Azure roles, because the Azure RBAC role assignment has to point to an identity that exists in Entra. User one doesn't exist in Entra as an object, but the group Group one does, because it's in OU one. Second, the default share level permission allows all authenticated users anyway. And third, when User one gets a Kerberos ticket, it contains the SIDs of their groups, including Group one. Azure Files reads the group SIDs and maps them to the role assignments on the synchronized Group one, which has Contributor. Microsoft's documentation says explicitly that non synchronized users can get access through membership in a synchronized group."
</Person1><Person2> "Then User two, question seven."
</Person2><Person1> "User two is in OU one, synchronized, hybrid, and explicitly assigned SMB Share Reader. Question seven: can User two access content in share one? True. You said False, perhaps because you thought read only meant no access, or because you doubted hybrid sync. The statement is about accessing content. Reader means they can read the content. The qualifier at the end of the explanation: actual file access also depends on NTFS ACLs, and since the question mentions no restrictive ACL, we assume none. Careful, the word access is not the same as edit."
</Person1><Person2> "And User three, I said True."
</Person2><Person1> "User three is cloud only, no AD DS account, so no Kerberos ticket from the associated AD DS. False. Mnemonic, for AD DS authentication: no on premises account, no Kerberos, no access."
</Person1><Person2> "Now the second family, questions twenty three to twenty five. The tenant is hybrid, with User one not enabled for on premises synchronization, User two enabled. Three shares: share one and share two in contoso twenty twenty five, share three in contoso twenty twenty six. Identity based access, AD DS, is enabled only on contoso twenty twenty five, with default share permission for all authenticated users."
</Person2><Person1> "Question twenty three: User one can access share one? You said True. Correct: False. User one is described as not synchronized from on premises, in a hybrid tenant, which in this question means a cloud only account. No AD DS account, so no Kerberos. Question twenty four: User two can access share two? True. Synchronized, hybrid, storage account configured, default permission allows authenticated users. Question twenty five: User two can access share three? You said True. Correct: False. Share three is in contoso twenty twenty six, a different storage account, which has no identity based access configured. Authentication is configured per storage account, not per tenant or per user. User two is fine, but the second account isn't set up."
</Person1><Person2> "But question six said an unsynchronized user can access and question twenty three said an unsynchronized user can't. That seems contradictory."
</Person2><Person1> "Excellent catch, so let me resolve it. In question six, unsynchronized means a person who has an account in AD DS, but their OU isn't in the sync scope. They can still authenticate with Kerberos, because they have the on premises account. In question twenty three, not enabled for on premises synchronization describes a cloud only user, in a tenant, with no on premises account. The word not synchronized hides two different situations: has an AD DS account that isn't synced, or has no AD DS account at all. Always ask: does this person have an account in the on premises directory associated with the storage account? That's the real test. If the question doesn't say, then the exam intends cloud only, and the answer is False, as the explanation for twenty three says."
</Person1><Person2> "That's confusing wording for an exam."
</Person2><Person1> "It is, so treat it as a scenario type and recognize the three variants. Variant one: user with AD DS account in synced OU, hybrid. Access allowed, subject to share and NTFS permissions. Variant two: user with AD DS account in non synced OU, member of a synced group. Access allowed through group SIDs, given default permission or group assignment. Variant three: cloud only user. Not allowed with AD DS source. They would be allowed only if the storage account used Entra Kerberos in a configuration that supports cloud only identities, which is newer, but the exam's answer is false for AD DS."
</Person1><Person2> "Give me a decision procedure."
</Person2><Person1> "Five questions. One: which storage account is the share in, and is identity based authentication enabled there, with which source? If not enabled, the answer is no for everyone with the account key excluded. Two: does the user have an account in that identity source, can they get a Kerberos ticket? Three: is there a share level permission, either a role assigned to the user or a group they belong to, or a default permission? Four: any restrictive NTFS ACLs mentioned? Five: for the exact verb in the question, read, write, change permissions, does the role cover it?"
</Person1><Person2> "Twists the examiner could throw."
</Person2><Person1> "Twist one: they set the default share permission to none, and then User one with only a group membership but no role assignment is denied, while User two with an explicit Reader assignment is allowed. Twist two: they say storage one uses Entra Domain Services as the identity source, and cloud only users are suddenly allowed, because Entra Domain Services synchronizes all Entra users, cloud only included, into the managed domain. Twist three: they mention an NTFS ACL that denies Group one, and Contributor at share level is overridden, because the effective permission is the most restrictive. Twist four: the question asks which role lets a user change NTFS permissions. Answer: Storage File Data SMB Share Elevated Contributor. Twist five: they ask what the client needs, answer port four four five open outbound, with SMB three, and a domain joined or hybrid joined machine for the Kerberos part."
</Person1><Person2> "What about the key restrictions on port four four five?"
</Person2><Person1> "Many internet providers block outbound port four four five, which is why mounting Azure Files from home often fails. The fixes are a VPN or ExpressRoute, a private endpoint, or SMB over QUIC on supported Windows Server versions. Good to know even if it isn't in your exam questions."
</Person1><Person2> "Recap."
</Person2><Person1> "Azure Files identity access is configured per storage account, with one identity source. For on premises AD DS you need an account in that domain for Kerberos. Hybrid identities get explicit role assignments. Non synchronized AD DS users can still come in through synchronized group SIDs or the default share permission. Cloud only users can't use the AD DS source. Share level permission is Azure RBAC, file level is NTFS, and the effective permission is the more restrictive.
