<Person1> "Welcome back. Episode four: groups. Group types, membership types, dynamic rules, nesting, role assignable groups, and group based licensing. This covers questions twenty seven, fifty nine, sixty, sixty one, sixty five, sixty six, eighty seven, eighty eight and eighty nine. It's the densest identity episode, so I'll go slowly and use many examples."
</Person1><Person2> "Start with the basic types."
</Person2><Person1> "Two group types. A security group is used to grant access to resources: Azure role assignments, application access, policies. A Microsoft three six five group, also called a unified group, is used for collaboration: it comes with a shared mailbox, calendar, a SharePoint site, and a Teams team. It can have members and owners, and, importantly, it cannot contain other groups as members. Security groups can contain users, devices, and other groups."
</Person1><Person2> "And the membership types?"
</Person2><Person1> "Three. Assigned, where an administrator adds and removes members by hand. Dynamic user, where a rule over user attributes decides membership automatically. Dynamic device, where a rule over device attributes decides, for example all Windows devices. A group has exactly one membership type. Dynamic groups need Microsoft Entra ID P one licensing for the tenant, and for the users included. Also, a dynamic group's membership cannot be edited by hand. If you want to add one extra person, you can't, you must change the rule or use another group."
</Person1><Person2> "Let me hear a dynamic rule being read."
</Person2><Person1> "A rule is a condition over properties. For example: user dot city dash startsWith quote m quote. That reads: users whose city starts with m. Another: user dot department dash eq quote Sales quote. Or user dot department dash ne quote human resources quote, meaning not equal. Or dash notIn, for several values. There are operators: eq, ne, startsWith, notStartsWith, contains, notContains, match for regular expressions, in, notIn. Rules can be combined with and, or, not. Comparisons are not case sensitive, so Montreal and montreal and MONTREAL all match starts with m."
</Person1><Person2> "Now question sixty five and sixty six."
</Person2><Person1> "The setup: three groups. Group one is a security group, dynamic user, rule city starts with m. Group two is a Microsoft three six five group, dynamic user, rule department is not human resources. Group three is a Microsoft three six five group, assigned, no rule. Two users. User one: city Montreal, department Human resources, has a Microsoft three six five license. User two: city Melbourne, department Marketing, no license."
</Person1><Person2> "User one, which groups? I said Group one and Group three."
</Person2><Person1> "Correct answer: Group one only. Evaluate each group separately. Group one: Montreal starts with m, so yes. Group two: department is human resources, which the rule excludes, so no. Group three: assigned, nobody was added, so no. You included Group three, probably because it is a Microsoft three six five group and User one has a Microsoft three six five license, so you linked the two. That's the distractor: a license has nothing to do with group membership. An assigned group has only the members someone added."
</Person1><Person2> "And User two?"
</Person2><Person1> "Group one and Group two. Melbourne starts with m, so Group one. Marketing is not human resources, so Group two. Not Group three, because it's assigned and empty. You got this right. Process to use every time: take each group, take its rule, plug in the user's attributes, ignore everything else. A trap in these questions is the negative rule. Not human resources includes everyone who isn't in HR, even users whose department is blank, in most configurations. Another trap: the order of attributes, such as user principal name versus mail, can matter in a rule."
</Person1><Person2> "Twists for dynamic groups?"
</Person2><Person1> "They might ask what happens if you change User one's city to Boston: they leave Group one automatically after the next evaluation. Or: can you add a user manually to Group two? No. Or: change Group three from assigned to dynamic, possible for an existing group in the portal, you can convert between assigned and dynamic membership type. Or: write a rule for all guests, user dot userType dash eq quote Guest quote."
</Person1><Person2> "Next: nesting and role assignable groups."
</Person2><Person1> "First, nesting generally. A security group can contain other security groups. In Azure RBAC, assigning a role to a parent group applies to members of its nested child groups, so if Group two is inside Group one, and Group one has Owner on a resource group, then users in Group two inherit that. The exam's explanation says nested membership works with ordinary security groups for Azure role assignments. But two big exceptions exist, and both showed up in your exam."
</Person1><Person2> "Exception one is licensing, right?"
</Person2><Person1> "Yes. Group based licensing does not support nested groups. Licenses assigned to a group apply only to direct members, not to members of groups nested inside. Question sixty: Group one has an Entra ID P two license. Group two is a member of Group one. User one is in Group one. User two is in Group two. Is User two assigned P two? Answer: False. User two is only a member of the nested group, so the license isn't propagated. You said True, using the intuitive idea that nesting passes things downward. Remember, for licenses, direct members only."
</Person1><Person2> "Exception two, the role assignable groups."
</Person2><Person1> "When you create a security group or Microsoft three six five group, there is an option: Microsoft Entra roles can be assigned to the group. Choose yes, and you've made a role assignable group. This flag can only be set when the group is created, and it can't be undone. These groups are protected because someone who could change their membership could gain powerful Entra directory roles, like Global Administrator. So restrictions apply: only assigned membership, no dynamic rules; only specific administrators can manage membership; and nesting is not supported, meaning you can't add a group as a member of a role assignable group. Members must be users or service principals."
</Person1><Person2> "Now questions eighty seven to eighty nine. I got them right, but explain what's really happening."
</Person2><Person1> "The setup: three users, each in a group. Group one and Group two are security groups, Group three is a Microsoft three six five group. All three are enabled for Microsoft Entra role assignments. Group one already has the Owner role on RG one. Question eighty seven: can you give User two Owner on RG one by adding Group two as a member of Group one? False. Because Group one is a role assignable group, and these cannot have groups as members. Question eighty eight: can you give User three Owner by adding Group three, the Microsoft three six five group, to Group one? Also False, for the same reason: Group one cannot accept a group as a member. The exam's own explanation says Microsoft three six five groups don't support nested evaluation, which is also a true statement in general, since Microsoft three six five groups can't be nested into others. Either way the answer is False."
</Person1><Person2> "And eighty nine says True."
</Person2><Person1> "Question eighty nine: assign the Owner role to Group three directly on RG one. True. A direct assignment, no nesting involved. Group three is allowed to receive role assignments, so User three, as a direct member, gets Owner. Pattern: direct assignment works, nesting into a role assignable group doesn't. Three similar statements, one scenario: always evaluate each statement alone."
</Person1><Person2> "Are role assignable groups relevant to Azure roles or Entra roles?"
</Person2><Person1> "The flag specifically protects assigning Microsoft Entra directory roles, like User Administrator, to the group. Azure RBAC role assignments to resources can be made to any security group, and that doesn't require the flag. In this exam question the flag is in the story to restrict nesting. A real-world tip: use role assignable groups for privileged directory roles, and combine with Privileged Identity Management for eligible, time bound access."
</Person1><Person2> "Now group based licensing in full. Question fifty nine."
</Person2><Person1> "Group based licensing lets you assign a license, a product like Entra ID P two or Microsoft three six five E five, to a group. Every direct member automatically receives it. When someone joins the group, they get the license, when they leave, it's removed. Requirements: Entra ID P one for the administrators and users, and the user must have a usage location set. In this scenario: Group one has the P two license assigned with the service plan enabled. User one is a member. Question fifty nine: can you remove the P two license from User one? False. The license is inherited from the group, so on the user's license page it's marked inherited from Group one, and cannot be removed there. To take it away, remove User one from Group one, or remove the license from Group one."
</Person1><Person2> "And sixty one, assigning another license feature?"
</Person2><Person1> "Question sixty one: can you assign User one the Microsoft Defender for Cloud Apps Discovery license? You said True. Correct: False. Reason: that's one of the service plans inside the product, and the plans enabled or disabled are defined where the license is assigned. If the group assignment has that plan turned off, a member can't switch it on individually for the same inherited license. You'd change it on the group, which affects everyone in the group. Generalize: an inherited license can't be edited per user. You could assign a different, separate license directly to the user, which is allowed, but you can't change an inherited license's plans."
</Person1><Person2> "How is it possible for a user to have the same license from both a group and directly?"
</Person2><Person1> "It happens. A user can hold a license directly assigned and also from one or more groups. The portal shows each source. If you remove the direct assignment, they still have it from the group. Removing the group source doesn't remove a direct one. When a user is in two licensed groups with overlapping service plans, there is no conflict as long as the plans don't conflict, and when they do, you get a license error in the group's licenses blade, to fix by correcting the conflict."
</Person1><Person2> "Deleting groups, question twenty seven."
</Person2><Person1> "The setup: User one in Group one, Group one has no license. User two in Group two, Group two has P two assigned. User three and four have no groups. Group two is a member of Group three, which has no license. Group three is a member of Group four, which has P two assigned. Question twenty seven: which groups can be deleted? Answer: Group one and Group three. You said all four. Rule: a group that has a license assigned directly cannot be deleted until you remove the license. Group two has one, Group four has one, so they're blocked. Group one and Group three have no direct license, so they can be deleted. Group three being a member of a licensed group, or containing a licensed group, does not matter. Only its own directly assigned license counts."
</Person1><Person2> "Why did the exam do users versus groups differently?"
</Person2><Person1> "Users: delete freely, licenses are reclaimed. Groups: protected, because deleting a licensed group would instantly strip licenses from many users, which could cause service outages, so you must consciously remove the license first and let the processing finish. Mnemonic: users, yes. Licensed groups, no."
</Person1><Person2> "Summarize the episode with a table of rules."
</Person2><Person1> "Dynamic groups: attributes only, case insensitive, no manual edits, need P one. Assigned groups: only who you added, licenses and other attributes don't matter. Microsoft three six five groups can't contain groups. Role assignable groups: set at creation, can't have group members, assigned membership only. Group licensing: direct members only, no nesting, inherited licenses can't be removed or edited per user, group with direct licenses can't be deleted. Azure RBAC to a security group: includes nested members, except where the group type forbids nesting. Next episode: Azure Files identity based access, the four questions that cost you marks."
