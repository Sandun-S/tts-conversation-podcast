<Person1> "Welcome back. Episode seven: Azure role selection, in the style of this second exam. Role based access control questions in this exam were fewer than in the first one, but the ones that came cost you marks: question nineteen on roles that support conditions, question fifty three on uploading blobs in the portal, and question seventy on least privilege for virtual machines and networks. We also revisit control plane and data plane, because everything hangs on it."
</Person1><Person2> "Give me the engine again, quickly, since I should hold it in my head."
</Person2><Person1> "Every role assignment is three things: a principal, a role, and a scope. The principal is a user, group, service principal or managed identity. The role is a bag of permissions, actions on the control plane, dataActions on the data plane. The scope is management group, subscription, resource group or resource, and assignments inherit downward and add together. There's no deny in standard RBAC, only allow, except deny assignments created by blueprints or managed apps. For any question, check three things: scope contains the target, role contains the verb, and plane matches the kind of operation. The control plane is Azure Resource Manager operations: create, configure, delete resources, list keys. The data plane is operations on the data inside a service: read a blob, send a queue message, sign in to a VM."
</Person1><Person2> "Question nineteen. You have a storage account storage one with blob data, you assign a role to User one so the user can access the blob data, and the assignment must support Azure role assignment conditions. Which two roles?"
</Person2><Person1> "Answer: Storage Blob Data Contributor and Storage Blob Data Owner. You chose Contributor, which is correct, and Storage Blob Delegator, which is wrong. Let me explain conditions first. A role assignment condition is an extra check, written as an expression, attached to a role assignment, that narrows when the assignment applies. This is attribute based access control, ABAC. Example: this person has Storage Blob Data Reader on the storage account, but only for blobs in containers whose name starts with project, or only blobs that have the tag Project equals Cascade. Conditions are supported on specific built in roles, the blob data roles and queue data roles: Storage Blob Data Owner, Contributor, Reader, and the Storage Queue Data roles. Not on Owner, Contributor, or Storage Account Contributor."
</Person1><Person2> "Why not those?"
</Person2><Person1> "They are management plane roles, with actions like write on storage accounts, and while the generic Owner role has a wildcard, the conditions feature for storage targets the blob and queue data actions. The options in your list: Owner gives full control over the resource management, and while it can read keys and so technically get to data using shared key, it doesn't use Entra data actions the same way, and it's not a condition supported role for blob data. Storage Account Contributor: management plane only. Storage Account Backup Contributor: manages backups. Storage Blob Delegator: its only job is to allow getting a user delegation key, which is used to create a user delegation SAS. It has no read or write on blobs. So the pair that both give blob data access and support conditions: Contributor and Owner."
</Person1><Person2> "How do you add a condition in practice?"
</Person2><Person1> "When you add the role assignment in IAM, there is a Conditions tab. You choose Add condition, build an expression with the visual editor or code, with attributes like container name, blob path, blob index tags, and actions like read, write, delete. The permission to add conditions on delegated assignments is controlled by the Role Based Access Control Administrator role, with its own condition that limits which roles the delegated administrator can assign. We covered that in series one."
</Person1><Person2> "Question fifty three."
</Person2><Person1> "The setup: you configure Entra based authentication for storage one. Users in Group one must upload blobs to a container using the Azure portal. Least privilege. Which two roles? Answer: Reader and Storage Blob Data Contributor. You selected Storage Blob Data Contributor, correct, but didn't select Reader."
</Person1><Person2> "Why do I need Reader? I thought the data role is enough."
</Person2><Person1> "Think about what the portal does. When you open the storage account in the Azure portal, you navigate to the account as an Azure resource: subscription, resource group, storage account, containers blade. To even see and open that resource, you need a control plane read permission. That's what Reader provides. Then, when you click upload, the portal chooses an authentication method. If you have a role that can list keys, the portal might use the account key. If not, it can use your Microsoft Entra account, and then you need the data plane permission, which is Storage Blob Data Contributor. So the two layers: Reader to get to the page, Blob Data Contributor to put blobs in. The documentation on authorizing data operations in the portal says exactly this: a user needs both a data access role and a role with the Reader action, minimum."
</Person1><Person2> "What about Storage Account Contributor or Contributor?"
</Person2><Person1> "Both are management plane roles, and both include the listKeys action. With listKeys, the portal could use the key, shared key authorization, and so uploading would work, but it's not Entra based authentication, which the question demanded, and they give far more than needed. Violates least privilege. Storage Blob Data Reader allows only reading, no upload. So the answer is the least pair: Reader plus Storage Blob Data Contributor."
</Person1><Person2> "Twist?"
</Person2><Person1> "They might say the users must be able to read blobs only: Reader and Storage Blob Data Reader. Or the users must manage the account settings but not the data: Storage Account Contributor alone. Or they must upload blobs using AzCopy with Entra login: just Storage Blob Data Contributor, because AzCopy talks to the data plane directly, no portal browsing needed. Good example to remember: the portal needs Reader, command line tools don't."
</Person1><Person2> "Question seventy."
</Person2><Person1> "You must grant User one permissions to create and manage virtual machines, and to create and manage virtual networks, least privilege. Options: Owner, Virtual Machine Contributor, Contributor, Virtual Machine Administrator Login. Answer: Contributor. You chose Virtual Machine Contributor. The thinking error: the role name matched the first half of the requirement, and you stopped reading. The second half, virtual networks, is outside Virtual Machine Contributor, which manages VMs but not the network they connect to. The two requirements together span compute and network, so among the offered roles, only Contributor covers both without allowing role assignment. Owner adds role assignment, so violates least privilege. Virtual Machine Administrator Login is a data plane role to log in as administrator, nothing to do with creating."
</Person1><Person2> "In a real design, would you really give Contributor?"
</Person2><Person1> "In real design you'd likely give a custom role, or combine Virtual Machine Contributor and Network Contributor at the resource group. But the question says which role, singular, from a list, and the least privilege among the offered ones is Contributor. In exam logic, when multiple requirements span several services, the answer is often the broader built in role that includes all of them but not Owner. Another example: Contributor is the answer when the question says full control of all resources but cannot grant access to others."
</Person1><Person2> "Give me a table of the roles that appear in this exam."
</Person2><Person1> "Owner: everything plus assign roles. Contributor: everything except assign roles, also can't manage Blueprint assignments. Reader: view only. User Access Administrator: manage access only. Role Based Access Control Administrator: assign roles, can be restricted by conditions. Virtual Machine Contributor: manage VMs, not the network or storage they use, no login. Network Contributor: manage networks. Storage Account Contributor: manage storage accounts, including keys, no data via Entra. Storage Account Key Operator Service Role: list and regenerate keys only. Reader and Data Access: read plus list keys. Storage Blob Data Owner, Contributor, Reader: blob data. Storage Blob Delegator: get user delegation key. Website Contributor: manage web apps, not the plan or access. Monitoring Contributor, Monitoring Reader: monitor settings. Disk Snapshot Contributor: snapshots. Virtual Machine Administrator Login and Virtual Machine User Login: sign in to VMs."
</Person1><Person2> "Combine it with the Ironclad requirements?"
</Person2><Person1> "Two Ironclad statements involve roles. NetworkUser must be able to create network resources in the subscription: Network Contributor at the subscription scope. CloudAdmin as service administrator: Owner at the subscription. Both covered last episode. If the case study also asked: external partners need secure temporary access to engineering documents, the answer isn't a role at all, it's a shared access signature, because partners are external and the access must be time limited. We'll treat that in the storage episodes."
</Person1><Person2> "Rapid recap of the rules."
</Person2><Person1> "One, scope, content, plane. Two, portal use needs Reader plus a data role when using Entra authorization. Three, conditions work on the blob and queue data roles. Four, when a requirement lists two services, the role must cover both. Five, least privilege is relative to the options offered. Six, management roles with listKeys give shared key access, not Entra data access. Next: governance, starting with Azure Policy, locks and moving resources."
