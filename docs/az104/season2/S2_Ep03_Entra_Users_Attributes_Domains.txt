<Person1> "Welcome back. Episode three: users in Microsoft Entra ID. We cover user types, who can edit which attribute, custom domains, bulk creation, external collaboration, and deletion. This covers questions fourteen, twenty, twenty six, eighty four, eighty five and eighty six."
</Person1><Person2> "Start with the types of users."
</Person2><Person1> "Two axes. Axis one, user type: member or guest. A member is an internal user of your organization. A guest is someone from outside, invited through B two B collaboration, for example a partner who signs in with their own company account or a personal email. Axis two, where the object is mastered: cloud only, or synchronized from on premises. So you get a small table. Cloud only member: created in the portal, mastered in Entra. Synchronized member: created in Active Directory, mastered on premises. Guest: always a cloud object, mastered in your Entra tenant, although the person's credentials live in their home tenant. That table answers the attribute questions."
</Person1><Person2> "Let's go to questions eighty five and eighty six."
</Person2><Person1> "The setup: a hybrid environment with three users. User one is a member, not synchronized. User two is a member, synchronized. User three is a guest, not synchronized. Question eighty five: you need to modify the job title attribute. For which users can you update it directly in Entra? The answer: User one and User three. You said User one and User two. The thinking error: you assumed that because User two is a member of your tenant, you can edit them. But User two is synchronized, so the source of authority is on premises. Edit the job title in Active Directory, and the next sync copies it up. In the portal, the field is read only."
</Person1><Person2> "And eighty six, usage location?"
</Person2><Person1> "Same three users, but the attribute is usage location. The answer: all three, User one, User two and User three. You picked User one and User three. Why is usage location different? Because usage location is a cloud attribute. It is a two letter country code, like LK for Sri Lanka or US, and it's required before you can assign a license to a user, since some services are not available in all countries. Active Directory has no standard attribute that sync maps to it, so it lives and is edited in Entra, even for synchronized users. Memory hook: job title, department, city, phone, those follow the source of authority. Usage location is always editable in the cloud."
</Person1><Person2> "Give me a rule for exam day."
</Person2><Person1> "When you see an attribute question with synced users, ask: is this attribute one that exists in Active Directory and flows up? Then the synced user cannot be edited in Entra. If it's a cloud only concept, such as usage location, licenses, group membership in cloud groups, or authentication methods, then it can be edited in Entra for everyone. Twist example: the exam could ask which users can have their display name changed in Entra, answer would again exclude the synchronized one. Or ask which users can be assigned a license. Everyone, once usage location is set."
</Person1><Person2> "Now custom domains, question eighty four."
</Person2><Person1> "The scenario: your tenant has the default domain ironclad dot onmicrosoft dot com. You own ironclad dot com at a third party registrar. You want users named at ironclad dot com. Which three actions in sequence? Answer: add a custom domain name, then add a record to the public ironclad dot com DNS zone, then verify the domain. The exam's marked answer is six, two, one in the action list. You chose two, three, six, which started with the DNS record and included creating an Azure DNS zone."
</Person1><Person2> "Walk me through why that order."
</Person2><Person1> "Step one: in Entra, add custom domain, type ironclad dot com. Entra can't just trust you, it must prove you own it. So Entra generates a verification value, a TXT record, or alternatively an MX record, and shows it to you. Step two: you go to the place where the public DNS for ironclad dot com is hosted, the registrar, and create that record. Step three: back in Entra, click verify. Entra queries public DNS, finds the value, and marks the domain as verified. Now you can create users with that suffix, make it the primary domain, and have synchronized users keep their ironclad dot com sign in names."
</Person1><Person2> "What about the other actions in the list, like creating an Azure DNS zone?"
</Person2><Person1> "Distractors. Create an Azure DNS zone is only needed if you want to host the DNS in Azure, and then you would also change the name servers at the registrar to point to Azure. The question says registered at a third party registrar and doesn't say to move DNS. Configure company branding is cosmetic, logos and backgrounds on the sign in page. Add a Microsoft Entra tenant is already done, you have the tenant. Memory hook: add, prove, verify. Twist: if the question said the domain is hosted in an Azure DNS zone, the record step would be in that zone, and Azure can even auto create it in some portals. Another twist: you cannot make the domain primary until it's verified."
</Person1><Person2> "Now bulk creation, question twenty."
</Person2><Person1> "The scenario: you plan to import a large number of user accounts at once, and new users must automatically be added to a group based on their department attribute, with minimal ongoing administrative effort. Two actions. One: create groups with the dynamic user membership type. Two: create a CSV file with the user information. You chose the dynamic group correctly but chose XML for the file."
</Person1><Person2> "Why CSV and not XML?"
</Person2><Person1> "Because the Entra admin center bulk operations accept a CSV template. In the portal: Users, Bulk operations, Bulk create. You download a CSV template that already has the right column headers. Required columns include name, user principal name, initial password and block sign in. You can add optional columns, like department, job title, city. You upload the filled CSV, Entra validates it, and starts a background job. There are sibling operations: bulk invite for guests, bulk delete, bulk download of the user list and group members, all using CSV. XML is not a supported import format here."
</Person1><Person2> "And why not a PowerShell script or an ARM template?"
</Person2><Person1> "PowerShell with the Graph module can create users, but you'd write and maintain a script, which contradicts minimal effort. An ARM template deploys Azure resources, not directory users. Assigned groups would require manually adding every user. The dynamic group with a rule like user department equals Sales does the grouping automatically, now and for every future user. Detail: dynamic membership requires Microsoft Entra ID P one licensing for the users who are members, and evaluation isn't instant, it can take minutes, sometimes longer in big directories."
</Person1><Person2> "Next, external collaboration, question fourteen."
</Person2><Person1> "The scenario: tenant contoso dot com, partner fabrikam dot com, you want invitations to go only to users from fabrikam dot com. Configure what? Answer: from External collaboration settings, configure Collaboration restrictions. You said cross tenant access settings, tenant restrictions. Let me lay out the whole area so you stop confusing them. In Entra External Identities there are three places."
</Person1><Person2> "Go."
</Person2><Person1> "Place one, External collaboration settings. These are tenant wide guest rules. Inside it: Guest user access restrictions, which controls what guests can see once inside, for example whether guests can enumerate users and groups. Guest invite settings, which controls who in your organization can invite guests, for example only admins, or members too. And Collaboration restrictions, which controls which external domains can be invited, with an allow list or a deny list. That's where you put fabrikam dot com. Place two, Cross tenant access settings. These are per organization, or default, policies for B two B collaboration and B two B direct connect, inbound and outbound, plus trust settings like accepting the partner's multi factor claims. And a section called Microsoft cloud settings, for collaborating between Azure commercial and sovereign clouds like US Government or China. Place three, tenant restrictions, which is about your own users, on your own networks, signing in to other tenants. It's an outbound control about which external tenants your users may use."
</Person1><Person2> "So you thought tenant restrictions because the word tenant sounded like it was about which tenants?"
</Person2><Person1> "Right. The thinking error was matching the vocabulary, tenant, to the problem, tenants being invited. But tenant restrictions deal with your users going out, not guests coming in. Rule: who can be invited by domain, Collaboration restrictions. What guests can see, Guest user access restrictions. Who can invite, Guest invite settings. Per partner trust and flows, cross tenant access settings."
</Person1><Person2> "Twists?"
</Person2><Person1> "They might say: block invitations to a particular competitor domain, deny list. Or: allow only admins to invite, guest invite settings. Or: prevent guests from seeing the user list, guest user access restrictions. Or: automatically trust the partner's MFA, cross tenant access settings, trust settings. Or, a tricky one: an invitation to a domain that isn't in the allow list fails even for an administrator."
</Person1><Person2> "Now question twenty six, deleting users."
</Person2><Person1> "The setup: a tenant with four users and four groups with licenses assigned directly or through groups. The question: which users can be deleted from Entra ID? Answer: all four, User one, User two, User three and User four. You picked User two and User four only, thinking that users without direct licenses were deletable and users with licenses weren't."
</Person1><Person2> "Why is that wrong?"
</Person2><Person1> "Deleting a user is not blocked by licenses. When you delete a user, they go to the deleted users list, a soft delete, and they stay there for thirty days, during which you can restore them, with their group memberships and license assignments. After thirty days they are permanently removed. When a user is deleted, their license is freed. A directly assigned license, or one inherited from a group, doesn't prevent deletion. The things that can block deleting a user are different, for example if it's a synchronized user, you delete it by removing it from sync scope or on premises, not directly, or it's the last global administrator."
</Person1><Person2> "Is the contrast with groups important?"
</Person2><Person1> "Very, it's the next episode, question twenty seven. The contrast table: users can be deleted regardless of license. Groups with directly assigned licenses cannot be deleted until you remove those licenses. Keep that pairing in mind: users yes, licensed groups no."
